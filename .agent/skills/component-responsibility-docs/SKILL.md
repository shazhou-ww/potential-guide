# 组件职责文档

将组件文档组织成可渐进阅读的 wiki：先看边界，再查术语和操作，必要时进入独立契约。
参考项目的[Task Engine 职责文档](../../../docs/axis/task-engine-responsibilities.md)的组织方式，不照搬其领域模型或业务规则，也不追求与 ISO 模板逐项一致。

## 工作方式

1. 先阅读目标组件的现有职责文档、相关讨论与契约，区分已确认决定、建议、现状和未决事项。
2. 以对外可观察的行为界定职责，不以当前代码结构或测试通过反推正确设计。
3. 按下面的结构整理；讨论请求不自动授权修改，文档整理不自动授权实现、删除、提交或发布。
4. 保留原有承诺和未决状态；移动内容时同步全部引用，不把未知补成默认成功。
5. 完成后检查 operation 编号、接口与纵表的一致性、契约覆盖及本地链接；遵守项目已有文档检查要求。

## 主文档结构

### 1. 概述

- 标题之后立即放“概述”，作为 TL;DR，不在头部堆日期、草稿定位、组织方式或标准模板说明。
- 概述下分“职责”和“非职责”，职责用少量能力分组，各组列出 operation 的一句话说明。
- 分组用 A、B、C，operation 用 A1、A2、B1 等编号；概述、详细章节和契约引用保持一致。
- 非职责只列已经明确排除的能力，不将尚未讨论的内容擅自判为非职责。

### 2. 术语表

- 放在概述之后，每个术语只用一句话解释。
- 定义领域词的准确范围，避免与通用词混淆，例如业务 Request 不等于任意接口调用。
- 有必要的详情链接独立 `.md`，不要为每个词机械创建空文件。
- 用“外部参与者”描述组件外部主体；调用、订阅等仅是交互角色。

### 3. 接口通用说明

- 集中说明操作的公共作用域、初始化绑定、共享类型与错误表达等必要约定，避免逐项重复。
- 接口草案与现有代码 API 明确区分，不擅自固定尚未讨论的数据字段或传输协议。
- 实例已绑定的上下文不重复塞进每个操作参数，也不由单次调用任意切换。
- 如有订阅句柄、分页等共享类型，只给必要示意；详细规则进入独立契约。

### 4. 按分类与 operation 展开

用两级标题：`## A. 能力分类`、`### A1. 操作名称`。
每项严格按以下顺序：

1. **概况纵表**：两列“项目／说明”，三行 `input`、`output`、`side effects`。
2. **接口签名**：TypeScript 项目直接写实例方法签名片段，不为每项操作另套一个无意义的 `interface`。
3. **详细文字**：先说明该操作具体做什么，只补充概述、纵表之外有价值的信息。
4. **契约引用**：逐条换行写“关于……的细则，参考……”，以完整契约标题为链接文字、相对路径为目标，保留何时需要查阅的上下文。

表达约束：

- output 用简洁自然语言描述，不套 `Response<T>` 等无必要的包装。
- 响应与后续事件流保留在同一个 output 中，通过文字区分，不强制拆列。
- 表格单元格保持简短，不依赖 `<br>` 或单元格内编号排版；详细限制放正文或契约。
- side effects 描述实际状态效果；查询无状态变更时写“无”，跨操作不变条件集中说明。
- 订阅返回包含事件流与取消能力的句柄时，取消订阅属于句柄行为，不重复列成组件顶层 operation。
- 不机械追求接口对称，例如集合查询不因此必然需要集合变更历史查询。

## 契约 reference 拆分

1. 主文档负责“提供什么能力”；独立契约负责跨操作的行为保证、约束及边界，不按 operation 一对一拆文件。
2. 同一语义主题的规则合并，例如生命周期中的时间、取消和回收；不同主题如幂等、匹配复用、分页独立成篇。
3. 在主文档相邻的 `<component>-contracts/` 下按主题建 `.md`；已有文档布局优先，不无故搬动其他组件文档。
4. 标题写清对象与约束主题，如“Request 受理与幂等处理”，避免只有“匹配”“分页”而不知作用范围。
5. 每篇开头一句话说明作用范围、制定意图和要避免的问题，随后标明关联 operation 编号并链接回职责入口。
6. 正文按核心概念、规则和必要示例渐进展开；多维状态模型先解释维度，再解释阶段与行为，示例不得变成强制部署或实现限制。
7. 接口或约束共享的输入和输出应一起描述，例如分页契约同时覆盖 query 参数、返回页、顺序、一致性与失效行为。
8. 未决项显式标注；内部 timer、类名、存储算法等机制不混为对外契约，必要架构约束应明确其性质。
9. 各 operation 只引用直接相关的契约，契约间可继续链接；不在主文档末尾重复堆统一契约索引。
10. 同一规则只保留一个权威正文，其他位置用简述加链接，避免 wiki 页面复制后逐渐分歧。

## 审阅标准

- 快速阅读概述即可理解能力与排除范围，不需要先读元信息。
- 术语、operation 编号、签名、纵表与契约引用一致。
- 当前状态、历史、后续事件流，以及受理、完成、资源释放等不同承诺没有混淆。
- 事实、时间派生状态和实际动作的关系按该组件已确认模型表达，不强制事件溯源等架构。
- 查询完整性不被误写成单次返回所有数据；错误或历史缺失不伪装为空结果。
- 有用的“概述／详情”和对称对象结构可以保留，不为消除重复而引入难懂的抽象。
