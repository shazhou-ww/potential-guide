# Task 匹配与 Run 启动

本契约界定 Task 如何匹配并共享完整 Run，区分请求幂等、独立 Task 与运行复用，避免重复运行或推导出不符合政策的匹配关系。

关联 [职责入口](../task-engine-responsibilities.md)：operation A1 的运行协调，以及 operations B1–B5、C1–C5 中可观察的状态、历史与事件。

1. Request 幂等防止同一次提交重复创建 Task；共享复用则允许不同 Task 使用同一个完整 Run，不合并 Task。
2. 匹配基于原 Input、`matchPolicy` 及其他匹配条件，不要求接收 Task 独立完成准备。
   [输入结构判等](./task-bundle.md#输入校验与结构判等)包括 Schema 允许的额外字段，不能忽略这些字段的差异。
   类型内容身份使用已验证 Task Bundle 的根 CID，不同根 CID 不能共享 Run；
   相同 CID 仍须满足原 Input、可信边界及时间等其他条件。
   Bundle 引用形式、hint、获取节点、网关和缓存位置不参与类型内容身份或匹配。
3. matching 是根据截至源序位置的 Task、Run 事实、可信资格观测边界及匹配条件推导出的关系，不是独立的绑定动作。
4. 多个 Task 共享 Run 时仍保留各自的时间约束、取消意图与结果资格。
5. 向正在订阅的外部参与者发送匹配实际引起的状态变更事件。
6. 已进入终止流程的 Run 不再接受新的 Task 匹配或共享，包括 `matchPolicy: terminates-after-eligible`；不能等到协商成功或强制终止完成后才停止匹配。
7. 新匹配与进入终止流程须互斥裁决，不能依赖 Worker 是否已报告 `stopping`；细则见[Task 取消、超时与 Run 终止](./run-termination.md)。

## 唯一匹配与开始顺序

1. 一个 Task 在同一事实边界最多有一个有效匹配 Run；多个 Task 可以共享同一个 Run。
2. 在满足匹配条件的候选 Run 中，取开始顺序最早的一个，不另设任意选择的绑定动作。
3. Run 开始顺序由数据域内唯一、严格递增的序号确定，不依赖可能同刻或回拨的墙钟时间。
4. Run ID 只有保证上述顺序时才能兼任开始序号；后来的 Run 不能排到已有 Run 之前。
5. 候选资格依据相关事实成立时的边界判断，不在每次读取时仅按 Run 的当前状态重新筛选。
6. 允许新匹配与保留既有匹配分别判断：Run 进入终止流程后排除新匹配，但不抹去已经成立的匹配。
7. 仍成立的匹配不因 Run 停止、后续候选出现或历史清理而切换到其他 Run；Task stage 只跟随该 Run。
8. 已成立的匹配不因当前 now 回拨而撤销；但新增终结事实因时钟回拨不满足政策时，
   按下述[匹配失效与巡检](#时钟回拨导致的匹配失效与巡检)处理，不是任意改选 Run。

## 持久资格观测边界

独立的 pending/eligible/timeout 标签推算仍不生成事实事件。本节是对原“纯时间不产生事件”的限制性澄清：
**实际协调新匹配资格的可信观测可以形成源事实**，不再把墙钟到点与匹配同步成立等同起来。

1. 协调器依据已提交的事实前后边界处理资格。真实 Run 开始或其他已经可以证明资格的源事件优先充当边界；
   不为同一资格额外生成见证。
2. 如果既有源事实尚不能证明资格，而协调器实际观察、处理时会使至少一个尚未匹配且可处理的 Task 获得新资格，
   则提交一次数据域级 `qualification-time-observed`。其领域载荷仅含 `observedAt`，
   不含 Task→Run 绑定、所选 Run、Task 状态或受影响 Task 列表；标准事件元数据与源 revision 照常存在。
3. 额外见证必须位于相关 Task 受理与 Run 开始之后。后来受理的 Task 或后来开始的 Run 不能借用先前见证。
   复用真实源事件时，按该事件的事实前后边界评价，不以实体当前状态补历史。
   可信时间观测与其事实前缀必须一致；提交前源前缀变化须重新评价，不把过时观测借给后来出现的对象。
4. 在该源序位置，结合可信 observedAt、Task 生效/超时与取消事实、Run 可用事实及严格开始顺序，
   确定满足条件的唯一最早候选。尚无已提交资格依据时允许 `initial + eligible`，直到协调器处理；
   不承诺墙钟到点同步完成匹配，查询也不提交见证或改变生命周期。
5. 资格成立与进入终止流程仍须互斥：资格先成立则计入需求判断；终止流程先成立则不得借后续见证新增匹配。
   已取消的 pending Task 不新增匹配，后续见证也不能复活已撤回的需求。
6. 同一见证可以影响多个 Task，所有派生变化沿用该源 revision；不为每个 Task 写新事实或权威状态缓存。
7. 没有实际新资格的 timer tick、GET、心跳或仅时间标签变化不生成见证；反复处理同一资格不追加见证，
   不将资格观测退化成无限时间水位日志。

既定匹配根据当时资格事实重放，不按读取时 now 或 Run 当前状态重新筛选；
后续新增的终结事实仍可按下述规则使提前匹配失效。
持久与恢复要求见[持久化与重启后的行为](./persistence-recovery.md)。

## Match Policy 的时间条件

在候选资格的判断边界，Task 必须未取消且时间状态为
[`eligible`](./task-lifecycle.md#时间状态与处理)，才可由规则推导出新的匹配。
`pending`、`eligible`、`timeout` 是互斥的时间状态；这里的“Task 已生效”指处于 `eligible`，
不是仅指曾经越过生效时间。以下政策的时间条件不替代这一前提。
已经成立的匹配不因 Task 后来超时而撤销，也不按读取时的时间状态重新筛选；
关联 Run 的迟到结果仍可推进 Task stage。
以下条件不是对已成立匹配作持续重新准入检查；终结回拨的失效依据是新增终结事实，不是读取时 now。

| `matchPolicy` | 时间条件 |
| --- | --- |
| `starts-after-eligible` | Run 的开始时间不早于 Task 的实际生效时间 |
| `terminates-after-eligible` | Run 的终结时间不早于 Task 的实际生效时间，终结包括 `completed`、`failed`、`stopped` |

1. 两个名称中的 `after` 均包含等号；实际生效时间为 `effectiveEligibleAt`。
2. 在已提交的可信资格观测边界，Task 已生效、Run 已开始且尚未终结时，可推导满足 `terminates-after-eligible`，
   无需等待终结事实。这不保证系统时钟不会回拨；终结事实形成时仍须满足该政策的时间条件。
3. Run 开始时 Task 处于 `eligible`，两种政策的时间条件均可在开始事实成立后判断。
4. 匹配仍须满足原 Input 及其他匹配条件；时间条件成立不承诺 Run 必然成功或在有限时间内终结。
5. 启动计划不是开始事实，不能据此提前推导 Run 已开始。
6. 当前 now 越过 eligibleAt 只先改变时间标签；实际匹配还需要上述已提交资格边界。

## Run 事件边界

1. 开始边界针对完整 Run，即将完整尝试交给 TaskType 的 `run(input, context)` 入口，不等待类型内部准备、分配或业务执行开始。
2. 先确立并持久化 Run 开始事实，再投递调用；开始事实不证明类型代码已经执行到。
3. 正常运行时，用于匹配的终结时间为宿主观察到 Worker 退出的时间；`completed`、`failed`、`stopped` 均遵循此边界，不以提前上报结果的时间代替。
4. 终结包含 `stopped` 不改变禁止新匹配的规则：已进入停止流程的 Run 不接受新匹配，
   仍满足政策的既有匹配继续保留。
5. 重启失去跟踪的恢复裁决属于例外，见[持久化与重启后的行为](./persistence-recovery.md)；它不伪造旧 Worker 的实际退出时间。

## 时钟回拨导致的匹配失效与巡检

1. 正常退出的 Run 终结时间可能受系统时钟回拨影响。若其早于 Task 的 `effectiveEligibleAt`，
   先前提前推导的 `terminates-after-eligible` 匹配失效；不能为了保留匹配而改写终结时间、
   Task 的生效时间或 deadline。`starts-after-eligible` 不因终结时间回拨而失效。
2. 匹配失效是按新增终结事实重新推导关系的结果，不是取消 Task 或撤销 Run 的真实结果。
   Task 不依据这个不再匹配的 Run 形成终结结果；没有有效匹配时，其 stage 为 `initial`。
   原先的匹配变化历史继续保留，不把历史改成从未发生过匹配。
3. Engine 提供额外巡检，发现因上述失配而未能继续推进的 Task，并重新进行匹配与调度判断，
   按需启动新的 Run，避免这种“僵尸 Task”一直停滞。“僵尸 Task”不是新的 stage。
   巡检不强行绑定 Run、不复活或重演旧 Run，也不改变 Request 身份或重置 Task 时间边界。
4. 巡检不豁免原匹配与调度条件。只有未取消且当前处于 `eligible` 的 Task 才能参与新的匹配与调度；
   `pending` 时不能提前启动，`timeout` 或已取消时不能为了消除失配而启动新的 Run。
   仍须遵守输入及身份条件、最早开始顺序、唯一有效匹配和禁止匹配已进入停止流程 Run 的规则。
5. 匹配失效及后续成立引起的 Task 状态变化按[观察契约](./observation.md#最小事实范围)进入历史和订阅，
   遵循源事件 revision；巡检本身不使未改变的事实重复产生事件。
   巡检的具体周期与实现机制不在此固定。

Task 状态见[Task 生命周期与三维状态](./task-lifecycle.md)；
取消、超时及运行约束对终止和回收的影响见[Task 取消、超时与 Run 终止](./run-termination.md)。
