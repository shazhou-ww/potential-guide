# Task 与 Run 的查询范围及订阅粒度

本契约区分单体与集合、当前状态与历史及后续变化，避免查询与订阅承担不明确或过量的数据范围。

关联 [职责入口](../task-engine-responsibilities.md)：operations B1–B5、C1–C5，Task 与 Run 的查询和订阅。

1. 单个实体的当前状态与变更历史分别查询：前者返回当前状态快照，不默认包含历史；后者返回不可变变更记录，可独立分页。订阅提供后续变更事件。
2. 集合查询提供绑定数据域内符合条件的完整实体列表，以摘要呈现；集合订阅提供加入、摘要更新和移出事件，不包含每个实体的全部详情变化。
3. 两个层级均覆盖仍在进行和已经结束的实体；整体概况不是多个单体详情订阅的简单合并，也不预先要求统计聚合。
4. 每个层级分别提供查询和订阅操作。订阅成功返回订阅句柄（subscription handle），包含事件流及取消订阅能力；取消订阅由句柄提供，不另列为 Engine 顶层操作。
5. 摘要及事件的最小事实范围见下文；方法名称与传输编码不改变这些边界。
6. 单体历史查询与订阅统一使用 TaskEvent / RunEvent：历史读取已保存的事件，订阅读取后续的同类事件，不另设通知模型。
7. eligible、timeout 是时间派生状态，时间越过边界本身不产生事件，也不重复进入历史或订阅流。
8. 当前状态由已知事实与观察时间共同确定；客户端可依据生效时间和超时期限自行推算，时钟差可能带来展示差异，不依赖到点事件刷新。
9. 时间状态按当下时间推算，不因取消或 Run 终结而冻结；UI 聚合标签不作为 Engine 的逻辑判断依据，详见[Task 生命周期与三维状态](./task-lifecycle.md)。
10. 状态快照与集合查询均返回一致的 revision；订阅从该水位之后补历史并接续实时事件，见[数据域事件序号与查询 Revision](./revision.md)和[订阅句柄与订阅生命周期](./subscription.md)。
11. Task stage 与匹配 Run 依据已提交的资格边界，不由 GET 的当前 now 自行新增或撤销匹配。
    协调器处理前可为 initial+eligible；实际新资格需要见证时，按[匹配契约](./run-matching.md)提交
    qualification-time-observed，其派生 Task 变化进入同一历史/订阅模型，而不是额外时间通知。

历史和集合查询的分页输入及返回页遵守[历史与集合查询的分页契约](./pagination.md)。

## 集合事件

对每条事件，计算其前后实体是否符合 query，再生成集合的派生输出；不要求先对 Task 状态做事务性修改。

| 变更前 | 变更后 | 集合事件 |
| --- | --- | --- |
| 不符合 | 符合 | 加入，携带实体标识及摘要 |
| 符合 | 符合 | 摘要变化时发送更新，携带实体标识及新摘要 |
| 符合 | 不符合 | 移出，携带实体标识 |
| 不符合 | 不符合 | 不发送 |

1. 移出仅表示不再属于该查询结果集，不取消 Task 或停止 Run。
2. 观察范围覆盖数据域内相关变更，不限于首次查询返回的成员；原先不符合条件的实体变化后可以加入。
3. 历史补读按事件当时的变更前后事实判断，不用实体现在的状态代替，也不为每组 query 穷举保存独立历史。
4. 同一条事实事件可以使多个成员发生变化，这些派生输出沿用源事件的 revision，按[订阅契约](./subscription.md)完整封装交付。
5. 资格见证也按其前后事实边界推导全体受影响成员，覆盖此前不在结果中的 Task；
   不在旧水位追加资格变化，不冻结匹配时间来规避成员发现，也不为每组条件保存独立资格历史。

## 与重新查询的一致性

1. 同一数据域、同一 query 下，完整查询基线加上按序应用的集合事件，应与相同 revision 的重新查询得到的成员及摘要一致。
2. 基线须包含全部分页；revision 标识源事件，不能把同一源事件对不同成员的影响误当作重复而丢弃。
3. 实时流尚未追上查询水位时允许暂时落后，不将这种延迟当作结果不一致。
4. 涉及时间派生状态时，还需对齐观察时间；纯时间流逝不产生 eligible 或 timeout 事件。
5. 首轮集合查询与订阅只接受事实字段筛选，不支持 pending/eligible/timeout、相对 now 的年龄或 UI 聚合标签条件；遇到此类条件明确拒绝。
   客户端可对完整事实候选集本地展示时间标签，但不能声称服务端按时间派生条件提供了完整成员变化。
6. Task stage、匹配 Run 等筛选以已提交资格事实为边界；now 单独推进尚未提交资格时不会改变这些事实成员。
   协调器处理见证后，新增成员及摘要变化沿用该见证源 revision，因而可从原基线水位完整补读。

## 最小事实范围

1. 快照包含实体标识、数据域归属、查询 revision 与观察时间。Task 提供 Request 定位、receivedAt、
   effectiveEligibleAt、deadlineAt、stage、canceled、唯一匹配 Run（如有）及结果/失败依据（如有）。
   时间状态按边界推算，不独立持久化；单 Task 不提供 Run progress。
2. Run 快照提供类型/匹配身份、严格开始顺序及开始时间、stage、停止流程是否已进入与 Worker 是否接纳、
   可靠结果/失败、终结时间及正常退出/恢复裁决依据（如有）、资源回收的已知或未知状态。
   progress 和完整业务载荷属于单 Run 观察；TaskType 提供的实际环境证据仍可经 Run 历史独立核验。
3. TaskEvent 表达该 Task 可见的创建、取消、匹配成立、关联 Run stage/结果变化，沿用源 revision；
   Run progress 载荷本身不生成 TaskEvent。独立时间推算和读取不产生事件；
   实际资格观测引起的匹配变化沿用证明该资格的源 revision。
4. Task 摘要包含标识、类型、scope/series、创建/更新时间、时间边界、stage、canceled、匹配 Run；
   Run 摘要包含标识、类型、scope、开始顺序与时间、更新时间、stage、停止流程及终结依据。
   不含原输入、完整结果、progress 或消息载荷；额外公开的摘要事实（例如回收结论）改变时也必须生成摘要更新。
5. Task updatedAt 只随创建、首次取消、匹配成立、关联 Run stage/结果变化；
   Run updatedAt 随开始、进入停止流程、接纳停止、progress、结果、退出/恢复裁决及公开回收事实变化。
   使用 max(先前 updatedAt, 源事实时间)，并列排序以稳定实体标识打破；事件先后只由 revision 确定。
   重复取消、时间经过、读取及心跳不改变 updatedAt；取消不冻结后续事实。
   协调器提交资格依据而形成的新匹配属于实际匹配变化，不是时间标签刷新；
   不因见证存在就批量改写所有 Task/Run 的 updatedAt。
6. 集合查询与订阅支持对应实体适用的身份、类型、scope/series、匹配 Run、事实 stage、canceled、
   创建/更新时间等事实条件；时间区间下界包含、上界不含，缺省不限制。未知或不适用字段明确拒绝。
   同一事实筛选可用于查询与订阅，查询排序不改变订阅的源事件顺序。
