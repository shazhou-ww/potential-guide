# Run 诊断日志

本契约定义显式作者诊断的输出、保留与消费边界。
关联 [RunContext](./run-context.md) 与 [职责入口](../task-engine-responsibilities.md) operations C6、C7；
具体 API、默认限额和 HTTP 编码见 [运行文档](../../task-run-logs.md)。

## 独立诊断通道

1. 作者通过 context.log 显式输出 level、message 和可选 JSON fields；
   SDK 与宿主绑定可信 Run、Worker generation 和 scope，作者不能提交身份、时间或序号字段。
   默认不捕获 console/stderr、环境变量或任意子进程输出，不自动转储输入或凭据。
2. 日志不属于 TaskEvent/RunEvent，不推进数据域 lifecycle revision，
   不改变 Task/Run 的生命周期 updatedAt、集合摘要、匹配、复用、结果或回收裁决。
   多个 Task 共享 Run 时共享该 Run 的诊断，不复制成每个 Task 的日志历史。
3. 同一 Run 已接纳日志按宿主分配的单调 sequence 排序，receivedAt 是宿主接收时间；
   sequence 不是生命周期 Revision，也不用于比较不同 Run 的先后。
4. 声明 `$schema` 同时确定通信协议：唯一 Task v1 已包含诊断通道。
   项目未正式发布，v1 可原地演进；已移除的 v2 和未来未知版本在执行前明确拒绝。
   禁用或自定义宿主不支持诊断的状态与“支持但没有输出”必须区分。

## 日志级别约定

level 必须显式填写，取 `debug`、`info`、`warn`、`error`，
严重性按 `debug < info < warn < error` 排序；不接受自定义级别或用缺省值替代。
级别表达这条诊断的意义，不表达 Run stage、Result 是否通过或日志是否成功持久化。

| level | 约定含义 | 典型场景 |
| --- | --- | --- |
| `debug` | 排查实现细节所需的细粒度信息，正常操作无需逐条关注 | 选定分支、逐项执行细节、非敏感计数 |
| `info` | 正常执行中值得保留的重要事实或摘要，不要求异常处理 | 操作开始/结束、检查汇总、预期的业务结论 |
| `warn` | 值得关注的异常、风险或降级，当前操作仍可继续或已经恢复 | 有界重试、采用降级路径、需要操作者处理的检查问题 |
| `error` | 当前操作发生未恢复的执行故障，某项工作未能完成，通常需要修复 | 必要资源不可用、执行步骤异常、无法完成预定操作 |

选择规则：

1. 正常循环的细节使用 debug，不将每次迭代、轮询或心跳提升为 info；
   info 保留关键事实与汇总。任何级别仍遵守容量预算，不承诺 error 优先保留。
2. 预期的业务否定结论不是执行故障，例如检查发现不合规或断言不通过：
   正常结论/汇总用 info，需要操作者关注的具体问题可用 warn；
   不仅因为 Result 为 `{ok:false}` 就记录 error。业务问题仍由 Result 表达。
3. 可恢复问题用 warn，并明确恢复、重试或降级路径；必要操作最终未恢复时才用 error。
   有界重试的每次底层细节可用 debug，避免为同一故障反复输出重复 error。
4. error 日志不会自动抛错、终结 Run 或改变匹配；warn 也不意味着 Run 成功。
   若故障应使业务失败，作者仍通过抛错或既有结果契约表达，不能只写 error 代替失败上报。
   外层仍可能恢复某项操作的 error，因此不能由最高日志级别反推最终结果。
5. message 说明发生了什么；warn/error 应尽可能提供非敏感的影响范围与可采取的动作，
   fields 放选定的结构化诊断信息。级别不能代替错误码、业务问题 ID 或可靠证据。
6. 宿主校验级别合法性，但不根据文案推断或改写作者选择；
   UI/消费者按上述顺序理解严重性，不从级别推导控制动作或日志完整性。

## 写入、容量与完整性

1. stored 回执仅表示宿主确认持久化，保留策略仍可随后清理；
   dropped 明确表达容量或单条预算拒绝，unavailable 表达禁用、不支持或基础设施不可用。
   无效级别、非 JSON 字段和未知输入键明确拒绝，不返回成功形状的默认值。
2. ACK timeout 表示写入结果未知，不证明没有写入；不自动重试，
   不能因重试或迟到确认重复累计丢弃。作者主动将回执作为业务错误是其业务策略。
3. 单条字节、待确认请求、累计丢弃通知、每 Run 条数/字节、全局字节、metadata 数、
   保留时间、查询页和订阅容量均有有限预算。容量拒绝聚合为有界计数，
   不为每次丢弃再排入无界通知，也不阻塞取消、必要输出或资源回收。
4. 日志状态分别表达 availability 与 completeness：
   不支持、禁用、截断、过期、不可用不能伪装成完整空日志；
   可用但没有条目才表示当前没有保留输出。状态存储也失败时明确报错。
5. 已确认的正常输出与宿主观察的非强制退出可确立日志尾部 complete；
   业务失败也可能拥有完整尾部。取消、强制退出、恢复或清理未知等情况保持 unknown。
   截断状态可以同时有 complete 尾部：这只表示尾部确认，不表示未丢失条目。
6. 保留清理或全局容量压力可移除日志正文；metadata 也受限，淘汰后明确报告不可用，
   不重新从 1 开始给同一 Run 分配序号。逻辑预算不承诺 SQLite 文件即时缩小、
   安全擦除或同步磁盘 I/O 的硬实时延迟。

## 查询与实时续接

1. 查询按 Run、afterSequence 和有界 limit 读取仍保留的日志，
   返回条目、状态、限额、nextSequence、hasMore 和 gap，不包含生命周期 revision。
   它不是生命周期历史的 Page，不能套用该历史的分页 cursor 或 fromRevision。
2. 实时订阅先补读最后确认 sequence 之后的保留条目，再跟随输出；
   首屏与建立订阅之间不能遗漏保留内容。消费者按 Run+sequence 去重，
   不承诺永久回放或 exactly-once。
3. 游标落在已清理范围或超出宿主已知日志序号时明确返回 gap；
   不把静默跳至最新位置称为完整续接。状态变化即使没有新条目也需可观察。
4. 慢消费者使用有界拉取/缓冲，断连、容量或状态故障显式报告；
   取消或断开只释放日志观察资源，不取消 Task/Run，订阅容量独立于生命周期订阅。
5. 查询与订阅复用可信服务的 Run 读取权限及 scope 校验，不能仅凭 runId 获取别人的日志。
   不存在、未认证、未授权和旧宿主接口不支持均明确失败。
6. 查询可以触发日志保留清理，但不改变业务事实；历史、状态或断流均不能充当退出/回收证明。

## 消费端展示

Task Engine Web UI 在 Run 详情提供独立 Logs 区域，与业务结果、进度和生命周期历史分开。
实时跟随、暂停、历史分页及重连使用同一 Run 的确认序号；
切换 Run 关闭旧订阅并拒绝迟到响应，浏览器窗口保持有界。
诊断文本按非可信文本显示，结构化字段可展开；
无输出、不支持、加载失败、断连、截断、过期和完整性未知有不同提示。
