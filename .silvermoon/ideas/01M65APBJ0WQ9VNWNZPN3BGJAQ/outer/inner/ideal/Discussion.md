## 已有目标与约束

本项交付 `@potential-guide/regulate-task`，向同一通用 task-engine-server
注册 `type=regulate`，同时支持进程内调用。基于准确 Objective 引用、subject、
目标等级和治理参数，执行有界的 Probe、授权 Agent 修复、新 Probe 验证。

必须保留的边界：

- 复用或提取 objective-regulator 单次治理语义，不另建 Regulation Host，
  不复制引擎调度、任务状态机或 SQLite 真相。
- `target-reached`、`exhausted`、`dependency-required`、
  `authorization-required` 是不同正常业务结果，与执行故障分开。
  Agent 自报完成不是目标达成证据，修复后必须有真实新 Probe。
- 权限由受信任组装或调用上下文授予，与业务 Request、Agent 请求、动态 requirements 分离；
  默认拒绝未授予动作，不跨 scope 扩权。
- 区分 Task 总预算、单次治理配额和 Agent 单次限额；父任务等待 Probe/Check
  不能占满下游槽位。取消只撤销本执行拥有的需求，不伤其他 owner。
- 物理清理确认前不得复用实际资源，不承诺回滚副作用或 exactly-once。
  未知已启动修复不能自动重跑；重连、重复请求不能隐式新建修复。
- 准确版本、执行环境、因果与授权证据必须可追溯。
- 明确 Coordinator 通用周期与持久化职责的交接及其剩余跨目标策略，
  不全量迁移旧调用方，不自动删除仍有效的授权或依赖治理策略。
- 只在拥有的隔离目标上验证，不修复真实业务资源，不发布 npm，
  不修改其他 idea、工作树或服务，不启动 Web UI 工作。

已有 [Implementation.md](../Implementation.md) 与
[Deployment.md](../../Deployment.md) 是可调整的准备种子，不是本轮已接受设计。
后续验证仍需覆盖独立打包消费者、真实 HTTP/SSE、受控 Agent、权限拒绝、
配额、并发副作用、物理回收、SQLite 重启及相关回归和 `pnpm check`。

## 讨论经过

### 第一轮：需求清晰度与三个待定边界

Agent 判断核心目标明确，但提出三个尚需讨论的行为边界：

1. 同目标的不同请求冲突时，排队、拒绝还是允许安全协作。
2. 重启后修复结局未知时，何时允许该目标的新修复。
3. 首版 Agent 是受信任适配端口与受控验证，还是必须接通已有真实 Agent。

当时给出的默认建议是串行等待、确认物理清理后解锁、先交付适配端口与受控验证。
这些建议未获得用户选择，表单未得到实际回答，不是已定需求。

### 第二轮：先展开同目标并发

场景是两个独立请求可能同时修改一个项目：

- A 希望达到“测试通过”。
- B 希望达到“可发布”。
- 两者可能同时修改依赖、源码或锁文件，并在对方修改到一半时验证。

这不是同一幂等请求的网络重试。相同幂等请求必须保留原任务身份；
不同请求则可以有不同目标等级、权限、配额和取消意图。

Agent 最初建议串行执行完整治理过程：
后到请求等待，等待消耗自己的 Task 总预算，前一执行清理确认后重新 Probe，
若目标已经达成则不再调用 Agent。该建议是候选方案，不是已接受规则。

Agent 最初把“同目标”和“访问同一物理资源”混在一起，用户随后明确纠正，
以下一轮定义为准。不同 Objective 访问同一目录仍可能冲突，但那是独立的资源互斥问题。

### 第三轮：用户明确同目标定义并提出 join

用户明确：

> 同目标的定义一定是同一个 objective，同一个 subject。

目标等级不属于目标身份。同一 Objective、同一 subject，A 请求测试通过、
B 请求可发布，确实属于不同 input，当前 task engine 不会直接合并。

用户提出的理想方向：

- 同目标的治理应有机会协作，取更高的目标 level，而不是必然运行两条互相独立的修复链。
- 探讨在协议中允许一个 execution 返回“它 join 到了另一个 execution”，
  是否能实现这一结果。

这是用户提出的设计探索，尚未确定具体协议、实现范围、兼容规则或验收修订。

### 第四轮：Agent 对 join 方向的分析

Agent 认可探索价值，提出如下示例：

1. A 请求较低等级，E1 开始治理。
2. B 请求同目标的较高等级。
3. B 的需求被 E1 接纳，治理目标提升。
4. 共享一条实际修复链，修复后用新的 Probe 获取证据。
5. A、B 保持独立 Task，根据各自要求解释证据。

仅增加一个普通 `{ joined: E1 }` 结果并不足以做到上述行为：

- 指向 E1 不代表 E1 接受了更高等级；必须有可靠的需求接纳机制。
- 需处理 E1 正在结束时的加入竞争，不能把需求挂到已结束的执行上。
- join 不等于治理成功；若作为普通业务结果完成 E2，会过早结束等待者。
- E2 尚未开始副作用时，可以考虑直接绑定 B，无需为了 join 先创建业务执行。
  E2 若已开始修复，则需要安全交接，不能登记 join 后两边继续写。
- 相同观察可以对 A 表示目标已达成，对 B 表示仍未达到；不能机械复制同一个
  `target-reached` 或 `exhausted` 给所有请求。
- 可探索 A 达标后先完成、共享执行继续服务 B；也可以所有请求等到执行结束再分别解释，
  两种行为尚未选定。
- 较高 level 应按同一准确 Objective 修订的等级声明顺序确定，
  不能比较字符串，也不能把 `terminal` 当作固定业务等级。
- 等级可合并不意味着权限可取并集、配额可取最大值或加入可重置期限。
  取消一个请求不能自动终止其他请求仍需要的执行。

Agent 建议的职责划分是：
引擎负责通用绑定、生命周期和持久化；Regulate 负责需求兼容、等级合并和观察结果解释。
可考虑首版只支持授权、环境及策略兼容的请求合流，其余隔离。
以上均是讨论建议，用户尚未确认采用。

### 第五轮：共享成果、接续投入与实际资源限制

以下是用户在独立讨论 session 中明确的需求，不是精确修订验收或实施授权：

- 倾向动态合流以减少不必要的 execution；协作对象仍是同一 Objective + subject。
  B 可以利用 A 的治理成果，A 也可以受益于 B 的追加投入，不是只允许单向接力。
- 新 Probe 证明 A 达标时立即告知并完成 A，不等 B 的更高目标达成。
  B 仍未达标时可在已有成果上继续投入；同一观察若已证明 B 达标则无需再修复。
- A 自身修复额度耗尽并不直接结束其任务：只要 A 没超时、没取消，
  且已有兼容请求还能投入资源，A 可以继续等待并接受后来达标的结果。
- B 等待 A 的治理也消耗 B 自己的时间预算；追加投入不重置任何请求的期限。
  不把 B 到来前的时间追溯计入 B 的等待。
- 最后一次修复及新 Probe 结束后，若目标仍未达成且所有现有请求均无可用投入，
  未达标请求立即以额度耗尽结束，不等待尚不存在的 C。
- 用户将该模式类比为众筹：投入接续，成果共享。同一治理对象上时间接续的投入
  可以累加；这不意味着仅凭时间接续就能合流、期限相加、权限取并集或复活已结束请求。
- 移除连续停滞限制。不同 Objective、不同 Level 间的难度跨度不同，
  尚未跨到下一 Level 不足以证明实际没有进展，不应独立据此停止治理。
- 以实际资源消耗约束治理，资源可包括修复轮数、时间、Token。
  所有已启用资源预算均未耗尽才允许继续，任一耗尽就不能继续使用该份预算；
  其他现有兼容投入是否仍可支持下一次修复需分别判断。
  不要求首版一次覆盖所有资源统计，Token 统计不是首版必需项。
- `completed-after-eligible` 向 `terminated-after-eligible` 的命名与语义迁移
  [独立跟踪](../../../../01M66MH9YKNJ406ESX7J1HTY7J/outer/inner/ideal/Idea.md)，
  不在本次讨论中顺带实施。

仍未决定：投入扣减顺序、共享修复如何归属额度、各类时间预算的精确起算与归属、
加入时已有进行中修复如何记账、退出后未用额度如何处理、共享执行的独立硬上限，
以及一条还是多条 execution 承载接续治理。Agent 提出的“分别记账”“执行硬上限”
是候选方向，不能替代用户对具体规则的选择。

## Open questions

以下保留待讨论索引，已明确部分以第五轮更新为准；顺序不是实现计划。

### Q01: 是否把同目标合流作为本次交付要求

用户已选择动态协作、接续投入与共享成果的需求方向。
仍需细化本次兼容范围，以及哪些不兼容请求排队、明确拒绝或隔离处理；
不能将早先“串行”或立即取最高目标建议当作已定方案。

### Q02: join 的协议位置和安全接纳

是 Task 在分配阶段加入既有 Execution，还是允许 Execution 到 Execution 的显式交接，
或两者都有？join 是受控动作还是一种由引擎解释的特殊返回？
如何处理承接执行已结束、正在结束、两个执行同时互相加入以及重复 join？
已开始副作用的执行能否交接，何时才能确认只剩一个实际写入者？

### Q03: 目标升级与准确身份

怎样在保留原始 input、Prepared 和准确版本证据的同时，持久记录新增需求和目标升级？
同一逻辑 Objective 的不同准确修订是否允许参与同一治理，还是只能互斥而不能合流？
subject 的相等规则如何沿用现有契约，而不把用户定义替换成物理路径身份？

### Q04: 每个请求的完成时机与结果

已确定各 Task 在真实新 Probe 证明自身达标时即可完成，不等待整个共享执行结束。
仍需决定如何分别生成业务结果并关联原始证据；
后续治理导致等级退步时，如何解释此前已完成 Task 的时间点证据？

### Q05: 授权与策略兼容

哪些差异禁止合流，哪些可由受信任策略安全接受？
共享修复中的每个实际操作归属哪份授权，如何避免权限拼接或跨 scope 扩权？
默认拒绝和动态请求不自授权限已确定；是否只支持相同权限策略仍待决定。

### Q06: 预算、取消与 executionMatch

已确定资源可接续投入、期限各自计时，自己的投入耗尽不妨碍等待其他已有投入的成果，
所有现有投入不可用时在末次重查后立即耗尽；不再使用连续停滞限制，
继续修复要求所有已启用资源预算均未耗尽，Token 统计不强制首版交付。
每个 Task 的期限、单次治理配额、Agent 单次限额仍需明确归属和计数。
新需求是否能延长物理执行，以及如何保证其仍有界，不能默认取最大值或重置预算。
较高目标请求取消后是否降低治理目标？最后一个 owner 离开时如何安全退出？
后到请求加入较早执行时，如何遵守或明确扩展既有 executionMatch，而不是悄悄绕过？
`terminated-after-eligible` 的命名及终结语义由独立 idea 推进；时间匹配本身不授予合流权限。

### Q07: 同目标协作与物理资源互斥

同目标定义已定，但不同 Objective 或不同 subject 仍可能触达相同物理资源。
是否由受信任组装单独声明资源互斥，首版支持什么范围？
无法合流但发生冲突的请求排队还是拒绝，等待预算和清理屏障怎样约束？

### Q08: 未知修复的恢复与解锁

原已启动修复不自动重跑已确定。未定的是：
重启后是否阻塞该目标的新修复直到旧执行器退出及清理被证明？
能够自动证明清理时是否可解锁，还是必须人工解除隔离？
无法确认退出时怎样保留占用、显式报告并提供恢复路径？
join 关系和目标升级恢复时如何维持相同边界，不因重连或重复加入触发新修复？

### Q09: 首版 Agent 的实际交付范围

交付受信任 Agent 适配端口及受控真实副作用验证是否足够，
还是必须接通仓库现有真实 Agent；若必须接通，应选哪一种？
无论选哪种，操作权限必须由执行适配器强制约束，不能仅写进提示词。
首版支持的隔离目标、可强制终止的执行边界及清理证明尚需具体化。

### Q10: 引擎扩展与旧治理职责交接

若采用 join，哪些能力属于通用引擎协议，哪些留在 Regulate？
是否在本 idea 内扩展通用协议，还是需要先明确一个前置交付？
如何复用单次治理算法并保持旧调用方行为，交接 Coordinator 的通用职责而保留有效策略？
不得借 join 在业务包里再维护一套任务真相。
