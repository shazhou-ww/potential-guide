# Implementation

## Steps

### I-S01: 建立制品与观察任务边界

落实 v2 协议和 Host 内制品管理，定义准确版本、任务身份、时序与结构化错误；复用既有制品格式和安全原语，不让底层模块互相循环依赖。

具体分层、限额、来源策略和短期双栈选择见[实施设计](./architecture.md)。

### I-S02: 实现共享执行与生命周期仲裁

以统一调度状态机实现版本确认、三类匹配时点、worker pool、独立 Task 期限、Execution 墙钟和取消清理；针对竞争条件建立确定性测试。

### I-S03: 接入 API SDK 与业务消费者

提供统一事件过滤和 CheckTask 对象，迁移 Pilot/regulator 等调用面并保留准确来源证据；明确 v1 兼容/退出和 schema 策略，更新直接相关文档。

SDK 在任何请求序列化前验证 subject 与已提供的 context 为有限 plain JSON，
不得调用其中 accessor/toJSON 或静默转换无效业务值；合法可选字段仍可省略。

## Acceptance criteria

### I-AC01: 来源与准确内容不混淆

测试证明 URL 必填、digest 可选，浮动来源重新确认、固定缓存复用、V2/V3 共存、下载/校验限额及可信来源边界成立，没有静默回退。

### I-AC02: 共享不降低时间与隔离保证

确定性竞争测试覆盖请求/版本解析/开始/结束/超时/取消的不同顺序，验证匹配、晚到结果、独立期限和多 worker 隔离，真实 worker 测试证明协作与强制清理。

### I-AC03: 公共接口与调用链一致

公开 API/SDK 测试覆盖单/多 Task 快照和事件、重连、取消、幂等以及业务未达标/调用失败的区别；相关回归及项目要求的完整检查通过。

实际命令、失败修复与通过范围集中在[执行证据](./verification.md)，不把缓存命中或源码测试当作外部部署。
