# Task、Execution、Worker 的调度与生命周期

## 时间语义

Task 表达对准确 Check、subject 和执行上下文的一次观察需求。
在 Host 通过鉴权/结构校验并准入时记录受理序号和单调时点 a，建立期限 a + timeoutMs。
freshness 和总期限使用同一个锚点，不采用客户端墙钟，也不在下载完成时重置。

设 Execution 的逻辑开始序号为 s，正常完成序号为 c：

| freshness | 正常结果可满足该 Task 的时间条件 |
|---|---|
| started-after-request（默认） | s > a |
| completed-after-request | c > a |

公开 acceptedAt/executionStartedAt/executionCompletedAt 是展示时间戳；
正确性使用同一 Host 的单调时序或事件序号，避免回拨、相同毫秒和跨进程时钟差异。
还必须在交付时确认 Task 尚未取消、尚未超过独立期限，并验证执行结果及清理要求。

completed-after-request 可以加入受理时已运行的 Execution，但不保证它在请求后读取事实。
默认强语义用于修复后重查；即使强语义也不能证明 Check 自己没有使用旧业务缓存。

## Task 不合并

每个 Task 都保留自己的 taskId、受理时间、期限、状态、取消权和结果交付。
Execution 的一个结果可以满足多个 Task，不是把 Task 记录或取消权合成一份。
多个订阅者与多次 snapshot/result 只是同一 Task 的观察，不触发新执行。

执行兼容性至少比较：

```text
准确制品 digest
+ subject 的规范化 JSON
+ 影响执行的 context
+ 权限及资源访问作用域
+ 必须一致的执行策略
```

对象键排序、数组保序、值不转换；不得用 URL、Check 名称或执行 revision 代替制品 digest。
不同权限或上下文不能因为输入看起来相同就共享。freshness 是每个 Task 的匹配条件，
不必加入兼容键：同一次 Execution 可能同时满足两种 freshness。
只对满足 Check 观察契约及执行策略的调用共享，不能用去重隐瞒需要独立执行的副作用语义。

## 三类匹配时点

### Execution 开始

在提交给 worker、允许它执行代码之前，原子记录开始序号，并关联已经绑定准确版本、
输入兼容且满足开始条件的等待 Task。多个排队请求可以响应于同一 Execution。
后来才到的强 freshness 请求等待下一次执行，不强行加入旧执行。

开始序号是实际执行的保守下界，不能使用迟到的 worker “已开始”通知接收时刻，
否则会把实际上晚于事实读取的请求误判为 started-after-request。

### Execution 运行与结束

弱 freshness 的兼容 Task 可以在运行中关联。结束时，原子确定准确结果和结束序号，
向满足条件且仍有效的 Task 交付。正常结果只有在业务结果验证和所需清理确认后成立。
执行失败/超时不能包装为正常检查不达标，也不承诺自动另起一次执行掩盖失败。

### Task 完成版本解析

先固定实际 digest，再在同一状态机中查找保留结果、正在运行的兼容 Execution，
或预约下一次执行。查找与“决定新建”必须原子完成，避免两个解析完成事件各建一次。

```text
T1：Execution E 开始
T2：Task B 受理，completed-after-request
T3：E 完成并保留结果
T4：B 解析完成
```

若内容/输入兼容且仍在 Task 期限内，T4 应能用 T3 的结果响应 B。
若 T4 先于 T3，则先关联后交付，得到一致结论；若 B 实际解析为新版，则不能匹配 E。
started-after-request 在这个例子不能匹配，因为开始序号早于受理。

应在明确的保留和容量边界内照顾已准入、仍解析中的 Task，避免仅靠结束时扫描而
漏掉候选；容量不足时背压/拒绝，不承诺无界结果保留。历史记录已合法回收时可以安排
新的合格观察，不能伪造命中或交付不满足时间条件的旧结果。

## 统一的短临界区

由一个 Scheduler 状态机通过短锁、串行队列或等价机制仲裁：

| 事件 | 原子状态变更 |
|---|---|
| Task 受理 | 身份、时序、期限和幂等绑定 |
| 版本解析完成 | 固定 digest 并完成匹配/预约决定 |
| Execution 开始 | 开始序号、worker 占用、匹配集合 |
| Execution 结束 | 结果与完成序号、结果保留和 Task 交付 |
| Task 取消/期限 | 撤销需求，判断执行是否仍被需要 |
| Execution 墙钟到期 | 封闭结果和新关联，形成停止动作 |

网络、解压、hash、worker 运行、等待进程退出及慢客户端写入都不在锁内。
临界区只提交状态和待执行动作；外部完成后携带身份/代次回到状态机。
Node 单线程不自动消除含 await 的竞争，也不能靠开始/结束两个无锁扫描保证正确性。
定时器可能迟到，结果交付和每次仲裁仍需检查实际单调期限，不能仅依靠 timer 先触发。

## Worker 与 pool

```text
同一准确制品的 pool
  Worker W1 → Execution E1 → Tasks A、B
  Worker W2 → Execution E2 → Tasks C、D
```

Worker 跨时间复用，同一时刻只承载一个 Execution。独立并发由 pool 的多个 worker 提供；
全局和每制品并发、队列及初始化均有界。不是一 Task 一进程，也不承诺同线程内任意调用可抢占。
不同制品版本共存，新版不会覆盖或中断正在执行的旧版。

Execution 具有不可延长的执行墙钟上限，Task 期限各自独立：

- A 超时/取消，而 B 仍需要 E1：只撤销 A，E1 继续。
- E1 达到墙钟上限：确定执行失败，仍依赖 E1 的 Task 获得明确 execution_timeout。
- 新 Task 加入 E1 不延长 E1 的墙钟。
- 初始化和清理也需有界；准备和排队不能占住执行 worker 假装已开始工作。

## 协作取消、强制终止与迟到消息

Task 取消或期限到达后，撤销其观察需求；最后一个需求离开时，可以停止排队/执行。
Execution 开始取消时先封口，后来的请求不能再关联它，改等下一次执行。

```text
确定取消或执行超时
  → 封闭关联入口和正常结果
  → 对该 Execution 发 AbortSignal
  → 等待协作退出和请求资源清理
  → 超过宽限则强制终止其独占 Worker，并确认退出/子资源回收
```

Execution 超时后迟到的成功不能反转结果。Task 可以先报告失败/取消，但这不证明物理
资源已经清理；Worker 只有在确认清理完成且健康时才复用，否则退役补充。
不能因一个 Task 取消就杀死仍服务其他 Task 的执行，也不能用发送 kill 信号代替退出确认。
无法确认清理时明确失败并隔离资源，不向 pool 返还未确认安全的 Worker。

每个控制动作、完成回报和超时回调携带 executionId/代次；旧执行迟到的输出、取消指令
或计时器不得污染已经复用该 Worker 的新执行。执行结果与 Task 终态只提交一次。

## 必须覆盖的竞争场景

这些是设计验收场景，不是已执行测试结果：

- 同版本同输入的多个排队 Task，共享一次新 Execution；任务身份独立。
- 强/弱 freshness 在正在运行的执行到来时得到不同匹配结果。
- Task 解析早于或晚于 Execution 完成，符合条件的结果不因事件顺序丢失。
- 同 URL 已有 V2 运行，新请求确认 V3，产生独立内容和执行。
- 两个版本解析同时完成，只预约必要的下一次执行。
- 一等待者取消/超时不影响其他等待者；最后一个离开触发协作取消。
- 新请求与“最后一个需求离开”竞争，不关联已封口的执行。
- 执行结束与墙钟/Task 期限竞争，迟到成功不反转终态。
- W1 失控退役不破坏 W2；W1 的迟到代次消息不影响后继执行。
- Task 列表订阅与执行完成竞争，不遗漏终态，不因重连重新执行。
