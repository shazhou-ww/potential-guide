# 制品获取、版本确认与缓存管理

## Host 内的职责

Artifact Manager 负责来源确认、获取、校验、并发准备去重、缓存、内容物化和回收。
执行 Kernel 只消费准确执行内容，不理解网络、GitHub、Objective 或场景化文档。
这两个能力在同一个 Host 服务内组装，不要求再运行一个管理服务进程。

现有制品库继续是可复用实现基础。服务组装层可以依赖制品与执行能力，底层文件、
摘要和私有目录原语应共享或抽离，不能为了同进程服务把依赖变成相互引用。
本构想不预先规定拆成几个 npm 工具包，也不改变业务制品不必是 npm 包的方向。

## 三种身份不可混淆

| 标识 | 回答的问题 |
|---|---|
| URL | 到哪里获取，以及当前选择哪个内容 |
| 制品逻辑 digest | 这份 Check 的全部准确交付内容是什么 |
| 执行 revision | 实际运行的 worker/resources 内容是什么 |

逻辑 digest 包括 manifest、References 和显式资源；Host 执行 revision 不必包含
纯说明变化。归档传输 digest 又是另一层，覆盖压缩包原始字节。
不因为执行 revision 恰好相同就把不同制品 digest 的 Task 当作同一版本。
版本号或 Check 名称可以展示，但不是准确身份，也不用于执行去重。

## URL 必填，digest 可选

1. 只有 URL：为这个新请求确认来源当前内容，计算并记录准确逻辑/传输摘要。
2. URL + digest：只接受指定逻辑内容；已验证的准确缓存可以直接复用，不必确认 latest。
3. 不支持只有 digest 的创建形式；URL 保留获取位置和来源能力，即使本次命中缓存。

计算出摘要只说明取得了什么，不证明它就是调用方事先认可的版本。
预期摘要可以来自调用方、已经固定的引用或可信发布描述；没有预期值时是显式浮动来源模式。
TLS、发布者信任、来源授权与内容一致性是不同问题，不能用 digest 代替认证。
缓存命中也不能绕过该调用方的来源/执行授权。

## 浮动来源确认与并发

每个新的浮动请求都需要适用于本次受理时点的来源确认。可用 HTTP 条件请求及发布
manifest 降低传输量，但不能单凭 URL 缓存或“已有下载在跑”认定这是新请求的最新版。
可以批处理尚未开始确认的请求；不能把早于某请求的旧映射悄悄当作其当前版本。
同一个确定 digest 的下载、验证和物化可以合并，等待者仍独立计期限和取消。

“当前”是本次来源观察选定的内容，不是对整个互联网发布状态的全局线性一致承诺。
确认和下载必须得到自洽的内容：来源中途改变且与固定描述/预期摘要冲突时，应明确失败
或在有界策略内重新确认，不能把 V2 manifest 与 V3 worker 拼成一份可执行制品。

同一幂等请求的重试先恢复原 Task，不能重新确认 latest；新请求使用新受理时点。
已绑定 Task、一次 regulation 中的固定 Check 以及历史恢复不会因别的请求选择新版而升级。
Objective 原有内联固定 digest 的方式保留；更新版本是显式修改或新绑定，不新增 lock 文件。

## V2 与 V3 并存

```text
请求 A → URL 确认为 digest-V2 → 准备/执行 V2
请求 B → 同 URL 确认为 digest-V3 → 准备/执行 V3
```

两份内容各有不可变缓存，不覆盖正在运行的目录；B 不能加入 V2 Execution。
如果都确认 V2，只是可以共享制品，是否共享 Execution 还需满足 subject、上下文、
权限和 freshness。新版到来不是停止旧版执行的理由。

服务保存并返回安全的来源证据与准确摘要；查询参数、认证信息、签名 URL 和下载错误
必须脱敏。不能把复现所需的凭据以“provenance”名义持久化到普通任务日志。

## GitHub Release 与重定向

`https://github.com/<owner>/<repo>/releases/latest/download/<asset>` 是仓库级 latest，
不是每个 Check 独立的更新通道。若一个仓库发布多个 Check 或 CLI，最新 Release
不一定包含所需 asset。发布方案应选择完整集合 Release 或明确的逐 Check channel
manifest，不能假设 GitHub 自动提供这种粒度。

当前获取库拒绝自动重定向；支持 Release 下载需要有意增加受控重定向：
限定协议、次数、时间和目标策略，每一跳重新授权，跨来源不泄露凭据，不降低 TLS 校验。
不能为了支持 latest 就开启无限重定向、任意协议或不受控的服务端网络访问。
来源不可用时浮动解析明确失败，不悄悄使用旧版本兜底。

## 准备、限额与缓存

- 不安装 Check 依赖，不执行消费端构建或生命周期脚本；worker 仍自包含。
- 沿用完整树摘要、显式声明、路径/NFC/大小写检查、链接/特殊文件拒绝及提取限额。
- 下载、解压和 hash 有单独有界的并发、内存、字节与准备保护，不占用执行 worker 配额。
- Task 总期限涵盖准备；一个等待者取消不终止其他等待者仍使用的共享下载。
- 私有 owner/ACL、不可变发布和准确读取不能被“有缓存”或 Windows 平台差异绕过。
- 损坏或不完整缓存 fail closed，不以覆盖修复掩盖内容变化。
- 正在准备、执行或被结果/References 有效引用的内容不能被 GC 删除；容量不足时背压或拒绝。
- 任务/来源/缓存/执行记录各有有界保留与回收策略，具体数值在实施阶段给出并测试。

Host 可保管 manifest 和通用 Check/problem References，通过准确 digest 读取。
Objective 的继承、局部覆盖、语言和等级指导仍属于 Objective/Pilot 层；
服务化的资源地址不得丢失原有 owning artifact 证据，也不能把地址当内容身份。

## URL 查询与消费者接入

`POST /v2/artifacts/resolve` 回答此 URL 本次选中了什么，必要时下载并准备，返回
digest、checkedAt 和 manifest 等安全信息。它既不是历史版本枚举，也不是未经确认的缓存读取。
已有制品的 GET 查询只读取准确缓存，不通过一个不明 URL 查找缺失内容。

Pilot/regulator 应通过服务获取版本信息、References 及准确执行证据，不再在每次调用中
自行物化 Check 或传递服务器本地路径。已固定的 Objective Check 引用继续携带预期 digest；
服务化不是把严谨流程全部改为 latest，也不把 Host 变成 Objective registry。
