# Implementation

## Steps

### I-S01: 定义通用调用契约

细化 Task Context 与 Worker/宿主消息契约，明确调用输入、结果、权限、截止时间和组合预算，不把服务配置传入业务 Bundle。

采用 `context.invokeTask({ key, cid, path, input, timeoutMs })`：key 在父 Run 内稳定，重试必须保留同一意图；path 必须位于父 Bundle 已验证的 resources DAG，目录根必须等于 cid。宿主继承父 Task 的 caller，不接受 Worker 提供 scope、地址或凭据；授权默认拒绝，独立本机服务显式启用同 scope 的嵌入子 Task。

### I-S02: 实现宿主组合与生命周期

复用普通 Task 提交和校验路径；处理父子关联、取消、退出清理、故障恢复以及有限执行容量下的等待。

清理不确定性必须同时保留原始调用失败和清理失败的上下文，不能用汇总错误抹去 primary cause。

将父 Run、根 Run、深度、key、原始意图和绝对截止时间与 admission 原子持久化。子 Task 的宿主 isolation identity 避免与无关运行合并。每层单独执行容量，父等待不会占据下一层容量；默认深度 4、每层容量/每父并发 4、每根总量 64。所有调用受父 Task 截止时间、父执行墙钟和独立截止时间共同约束；默认调用预算 30 秒，清理预算 5 秒。恢复不重新启动死亡父 Worker，先取消其持久化子请求；没有物理释放证明时保留 unknown，不宣称成功。

### I-S03: 接入 Probe 与标准运行入口

Probe 通过 Context 调用 Check，移除作者包中的固定服务地址和演示凭据；提供构建与独立 Engine 提交分离的入口及文档。

独立提交入口只对明确的暂态传输/丢失回复使用原 request ID 查询状态；认证、校验及其他已知失败直接传播。重整与未知状态显式记录，失败保留原始 cause；观察和清理分别有截止预算，不隐式构建或启动 Engine。

## Acceptance criteria

### I-AC01: 通用接口与校验成立

以类型检查及协议测试证明普通 Task 和 Probe 都能使用同一接口；非法输入、结果、越权及内容身份不匹配明确失败。

### I-AC02: 调度与清理有界

以低容量执行、嵌套调用、父取消/退出和丢失响应等测试证明无等待死锁、无重复提交，且清理失败显式可追踪；检查恢复时的父子关系。

证明包括容量 1 的父/子/孙任务、深度/并发/总量拒绝、相同 key 的丢失确认重试、父取消/超时/退出、preparing 子请求回收和带持久化关系的恢复。恢复边界必须区分“已取消 demand”与“已证明资源释放”。

### I-AC03: Probe 不再绑定部署地址

检查源码与构建产物，证明不含固定服务地址或凭据；运行同一 CID 的 Probe 于不同服务端口，并运行相关测试和仓库检查，单独记录环境限制。

主体阶段使用受控服务实例验证地址解耦；现实阶段由 Deployment 执行 Windows 独立进程、持久化数据库和内容来源验证。证据汇总见[实现证据](./evidence.md)。

入口测试覆盖正常提交、已知拒绝/forbidden、丢失回复、重整失败、观察截止及有限清理，并验证 import 无副作用。
