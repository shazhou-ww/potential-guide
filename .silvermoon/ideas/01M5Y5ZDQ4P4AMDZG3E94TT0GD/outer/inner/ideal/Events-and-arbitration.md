# 耗尽事件、追加投入与同 Target 共存

本文支撑 [Idea](./Idea.md)，与[请求与派发模型](./Request-model.md)共同解释周期请求的业务边界。下述事件名称为概念名，不预定最终公共 API。

## 耗尽是值得上层关注的事件

任何 Run 未能在本次 quota 内达到期望目标，都必须留下可追溯的 exhausted 结果并向外提供事件；是否来自周期请求不影响上报语义。

Coordinator 不提供预先配置的 continue / wait-next-interval 策略，不因 exhausted 自动启动追加 quota 的 Run。周期后继已经在初始派发时生成，不等待结果来决定是否生成；耗尽不会提前后继时间，也不会阻止它按原规则排队。

上层 Agent 或其他监听者根据本次进展、阻塞原因与剩余投入能力，决定是否另提交一个无 recurrence 的请求。该请求表达一次额外推进，不修改或取消原周期链。

### 事件所需事实

- 可用于消费去重的稳定事件标识或 Host 内事件游标，及事件所属 Host。
- requestRef、runId、确切 ObjectiveRevision、Target、期望级别及必要的前驱关联。
- 耗尽原因：区分时长、Agent 调用次数、连续停滞等限制，不让外部解析任意 message 猜测。
- 本次生效的执行限制、可获得的实际消耗，以及最近有效观察、观察失败和进展证据；未知值保持未知。
- 后续调度事实：是否已有周期后继及其 eligibleAt，便于上层避免误判为已经自动续跑。

事件与终结事实一起持久化，外部可从游标重读，不依赖一次性的回调通知。不承诺端到端 exactly-once；重连允许重读，消费者使用稳定事件身份去重，并为追加请求提供稳定引用，避免重复追加投入。

观察失败、资源拒绝、授权问题和执行异常须与 quota 耗尽区分，不能统一伪装成 exhausted。事件传输与订阅协议在实施中按现有公共状态 / 事实能力确定，不在此指定 MCP 或消息基础设施。

## quota 与 Budget 不能混淆

quota / executionLimits 约束单次 Run；累计 Budget 若存在，约束更长作用域的投入。资源容量只约束并发度。

新增请求、周期后继、到期、恢复、资源释放或新 Run 身份，都不能被解释为可信预算自动补充。上层追加 quota 的决定须经真实可信执行配置路径生效，固定在新 Run 上；请求来源不自动获得提高执行额度的权限。

当前新版并未引入共享累计预算或动态调账协议。本 Idea 不借周期支持补建整个预算系统；实施须明确已有执行限制如何应用于每次派发，并保留真实耗尽原因、停滞历史和有限依赖推进边界。

预算不足时，应显式暴露阻塞事实，不能报告成功，也不能因下个 interval 到来绕过限制。

## 共存不等于并行，也不等于替代

同一 Objective / subject 的周期链与额外一次性请求可以同时存在：

```text
周期请求 A -> Run A 耗尽，同时已有未到期的后继 B
上层收到耗尽事件 -> 提交额外请求 X
X 和 B 按到期时间、优先级及资源条件参与调度
```

- X 不自动替代 B，不重置 B 的 eligibleAt，也不修改原周期规则。
- 同一 Host 内同一 Target 的实际执行保持互斥；不同确切版本仍须避免对同一 Target 并行治理。
- 时间资格不代表抢占；即时追加表示立即具备排队资格，不承诺立刻启动。
- 各请求保留自己的期望级别、确切版本、执行限制与结果，不自动合并 quota 或拼接证据。
- 更高或更低 level 的额外请求不修改原周期目标。level 表达至少达到的要求，不是命令现实降级。
- 只有明确针对旧请求或周期链的替代 / 停止才撤销旧意图，不能继续用“同 Target 新请求一律替代旧请求”的规则。

首版不要求一个 Run 自动完成其他请求，不复用旧达标结果来跳过后继，也不因额外推进成功而隐式调整周期。正常调度继续观察真实状态；跨请求优化以后另行定义证据时效与版本一致性规则。

## 必须能验证的行为

| 场景 | 可观察结果 |
| --- | --- |
| 普通请求派发 | 只初始派发一次，不生成周期后继 |
| 周期请求派发 | 前驱不变，生成唯一新引用后继，时间按实际派发计算 |
| 持久化后、runner 启动前崩溃 | 恢复核实同一执行身份，不重复生成后继 |
| Run 长于 interval 或 Host 长时间离线 | 本地不重叠执行，不补跑所有错过的时间点 |
| 普通或周期 Run 耗尽 | 可重读耗尽事件，不自动追加投入；周期后继维持原计划 |
| 监听者重读同一耗尽事件 | 使用稳定请求引用追加时不产生重复请求 |
| 额外请求与周期后继同 Target | 两者共存、按规则串行，任一结果不撤销另一意图 |
| 周期前驱等待依赖 | 依赖续接不再生成周期后继，也不与周期后继重复推进 |
| 显式停止周期链后重启或重投 | 不再派发旧链后继，不靠从快照省略记录取消 |
| 额度不足或观察失败 | 原因明确，既不虚构达标，也不伪造自动补充的预算 |

## 既有语义的证据边界

- [早期 Portfolio 架构](../../../../01M552FP55CNYV3FQKTPV1M29E/outer/inner/Architecture.md)将 exhausted 视为结束一次 Run、保留需求，并为续跑分配单次 quota。
- [独立 Coordinator 的 legacy 预算规则](../../../../../../packages/regulation-coordinator/README.md#dependency-ownership-and-budget)要求显式 retry，retry 不刷新累计 Budget。
- [当前新版实现](../../../../../../packages/regulation-coordinator/src/coordinator.ts)在普通 Run 终结后通常关闭本地请求，保留依赖解除后的多 Run 能力。

三者不是同一个已实现契约。本 Idea 明确选择事件驱动的外部追加决策与不可变周期后继；不得把历史文档中的自动续跑、共享预算或旧替代规则不加区分地沿用。
