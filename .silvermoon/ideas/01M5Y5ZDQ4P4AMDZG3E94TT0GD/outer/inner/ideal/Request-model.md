# 不可变请求、派发与周期后继

本文支撑 [Idea](./Idea.md)，记录已讨论的语义边界，不预定最终类型名称、存储 schema 或迁移实现。

## 责任分层

- 上层 Agent、人或自动化程序决定目标、优先级及是否追加投入；不要求 Potential Guide 自带上层 Agent。
- Coordinator 接受意图，处理时间资格、排队、资源、执行互斥、依赖、持久化及恢复。周期检查不再要求独立 Portfolio Supervisor。
- Regulator 在单次执行限制内观察、改善并重新验证；Pilot 提供真实观察。
- MCP 可以是 Coordinator 的外部适配入口，但不是领域模型或调度器生命周期；本 Idea 不交付 MCP server。

现有 Supervisor 中仍被复用的 helper、类型和兼容入口须在实施时盘点。职责收敛不等于立即删除旧包或把所有旧接口接到新服务。

## 请求是一份不可变的派发意图

保留现有 Objective、ObjectiveRevision、Target 和调用者提供的请求引用。请求固定确切版本、subject、期望 level、priority、来源，并增加以下概念：

- eligibleAt：该请求最早具备时间资格的时刻；不是截止时间，也不保证此刻实际启动。
- recurrence：可选的周期后继规则，首版仅需正的有限 intervalMs；术语是 recurrence，不是 recursion。

没有 recurrence 就是普通一次性请求，不再设置 achieve / maintain 类型。同一引用和相同内容仍是幂等重投；同一引用的不同时间或重复规则是冲突，不能原地修改。

修改目标、版本、时间或重复规则，需要新请求及明确的替代关系。recurrence 不隐含跟随 Objective 最新发布版本，后继继承前驱固定的目标与版本。

## 调度生命周期与执行结果分离

```text
ineligible -> eligible -> emitted
```

ineligible / eligible 是根据不可变 eligibleAt 和显式时钟输入得到的时间资格视图；事实重放本身不读取时钟。到期后仍须满足资源、额度、优先级、依赖和同 Target 互斥等条件。

emitted 表示本次派发已被持久确认，不能解释成进程已启动、现实已达标或执行已结束。启动失败也必须留下明确的执行故障，不能静默回到未派发并重复启动。

请求至多发生一次初始派发。Run 的 running、blocked、exhausted、target-reached 等执行事实不使请求回到 eligible。取消或被替代是独立的撤销事实，允许取消尚未派发的请求。

## 派发时生成后继，不修改前驱

```text
Request A: eligibleAt = t0, recurrence = interval
  -> 初始派发 Run A
  -> 生成 Request B:
       eligibleAt = 本次派发时间 + interval
       recurrence = 同一规则
       前驱 = A
```

- 后继有新的稳定请求引用，携带相同目标、版本和重复规则，显式记录前驱来源。它不是 A 的内容更新，也不替代 A 的活动执行。
- 派发事实、对应 Run 启动意图和后继接纳须在同一个持久化边界提交，再调用具有副作用的 runner。
- 每次初始派发至多生成一个后继。恢复或幂等重投不得重新分配后继引用、重复追加后继或重复启动外部执行。
- 时间以实际持久派发时刻为基准，不以原 eligibleAt 或 Run 结束时刻为基准。
- 未派发的后继即使逾期也不自行产生更多请求；错过多个周期不积累补跑。
- 原执行超过 interval 时，后继可已到期，但仍等待同 Target 的实际执行释放。调度不意味着抢占。

每次重新生成的后继使用新的排队位置，不能因为继承历史身份而永久占据同优先级队首。明确时钟、派发时间与事件顺序各自职责；跨 Host 不用墙钟比较推导唯一顺序。

## Request 与多个 Run 的关系

现有模型允许一个 Request 有多个历史 Run，例如依赖阻塞后重新执行。保留这个能力不等于允许同一请求重复初始派发。

- 周期执行属于不同的后继 Request，不通过复活旧请求或给旧请求追加周期 Run 表达。
- 既有依赖续接如需多个 Run，须显式关联前一次尝试，并受现有有限执行约束控制；它不是再次初始派发，不能再生成周期后继。
- 依赖 provider 的成功只允许消费者重新观察，不替代消费者自己的达标证据。
- 同一 Target 上，前驱的活动执行或尚未结束的依赖推进不能与后继重复推进；实施时须明确依赖等待与后继就绪的仲裁和清理规则。
- 不在本次设计中增加 Cycle，也不先拆出 observe / regulate 两类 Run。重复规则只影响 Coordinator 派发，不能改变 Regulator 的单次执行契约。

## 停止周期链与恢复

周期链需要可追溯来源和明确的停止语义，不能仅取消已 emitted 的前驱而留下后继继续自我生成。

外部应能明确停止一条周期链的未来派发：取消已有未派发后继，并阻止旧链继续生成有效后继。实现可以从前驱关系推导链身份，不预先增加独立业务实体。并发停止与派发须有持久化顺序；是否终止已经启动的 Run 另按明确执行策略处理。

先恢复、核实活动 Run，再处理到期请求；恢复不能刷新已消费额度、重新计算更晚的超时或制造新后继。无法核实的外部执行仍占用资源，不能启动同 Target 的重复工作。

这些保证首先限于单个 Host / Coordinator 的状态与所有权边界，不承诺跨 Host 唯一派发或全局请求满足。
