# R-09：让启动超时和物理回收失败有可复验的因果诊断

**产品与责任**：Task Engine 生命周期、Probe 预算控制、对应测试链路。**覆盖**：A-28、A-29、A-30，关联 A-27。证据见[问题清单](../../../../01M6Q8VHHGG4G49XZE1VWS3W2Z/outer/inner/ideal/Acceptance-issues.md)的 E1、E5、E6。

## 判断

本次有并发启动超时、Windows 观察窗口内仍 running、Node 24 物理清理无法确认三类现象。它们不一定同根；重跑通过也不能证明根因消失。最合理的第一项修改是提升可诊断性与复现质量，而不是先放宽 timeout 或清除 ownership。

## 建议修改

1. 在失败时生成有界生命周期诊断快照：运行/工作代身份、关键事件顺序、预算和停止原因、停止请求到达与确认、实际退出观察、待释放资源和最终 ownership 判断。能从现有事实导出的不要重复制造另一套状态机。
2. 把“测试等待窗口耗尽”“执行预算耗尽”“资源退出未被确认”区分为可读失败阶段。若只有部分证据，明确未知，不把未观察到当成已释放。
3. 为现有失败案例增加可控的时序/资源隔离 fixture：并发启动、迟到的退出确认、预算级联停止、Windows 退出处理。先重现再修改归属组件，测试夹具错误只修夹具，产品竞态才改产品。
4. 在 CI 中保存失败快照，并让重试关联首次失败；重试成功不能删除首轮诊断。压力/重复运行用于发现概率问题，不作为“直到通过”为止的门限策略。

## 复用入口与取舍

围绕[Engine](../../../../../../packages/task-engine/src/engine.ts)、[Probe 测试](../../../../../../packages/probe-task/test/probe.test.ts)及[既有日志契约](../../../../../../docs/task-run-logs.md)扩展诊断。业务 Run 日志不是退出/回收证明，不能靠添加 `context.log("closed")` 代替宿主物理事实。

诊断要限量、避免任意环境变量和私有载荷，只记录必要状态与时间关系。跨进程先依赖序列/关联身份，不能把不同机器时钟相减当成精确因果。保持无法确认 cleanup 时保留 ownership 的保护，不用“看起来结束了”替代。

## 验收方式

- 三类已观察失败各有独立复现目标；暂时无法复现的保留待查，不伪造修复结论。
- 注入迟到退出、丢失确认或启动阻塞，诊断能指出最后已知阶段和缺少的证据，而非只有通用错误字符串。
- 任何实际修复都让对应可控回归稳定通过，且错误路径仍不提前标记 reclaimedAt。
- CI 重试后仍可找到首轮失败身份和快照；正常运行的诊断开销有界，不阻塞回收。
