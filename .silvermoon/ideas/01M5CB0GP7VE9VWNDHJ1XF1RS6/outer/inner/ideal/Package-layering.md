# 三层与包归属

本文补充 [Idea.md](./Idea.md) 的架构边界，与其共同构成构想范围；描述拆包后的目标，不声称现有代码已符合约束。具体包名和文件迁移在实施阶段细化。

## 仅有三层

由高到低固定为：

```text
工具层
  CLI 主入口、命令包、工具侧共享服务与运行环境适配
    |
    v
业务逻辑层
  Pilot 观察、单目标调节、多目标监督
    |
    v
协议层
  effects 核心原语、Pilot 定义规范、schema、解析与校验
```

工具层可直接依赖协议层，无须经过业务逻辑层。不存在额外的基础层、适配层或具体需求层；未归入三层的包是后续外迁对象，不是第四层。

## 各层职责

| 层 | 应包含 | 不应包含 |
| --- | --- | --- |
| 工具层 | 参数与输出、命令发现分发、配置管理、声明管理、来源加载、Agent 连接、持久化和运行环境组装 | Pilot 规范的另一份定义、供业务逻辑反向调用的工具实现 |
| 业务逻辑层 | 与具体需求无关的观察、调节、监督算法及执行协调；通过协议和注入能力调用外部环境 | CLI 参数、用户配置路径、具体 Objective 规则、对工具包实现的依赖 |
| 协议层 | effects 核心原语；Pilot 定义规范、契约类型、schema、解析、结构与语义校验，以及跨层需要的能力接口 | 实际观察、调节、监督、Agent 连接、来源获取或命令执行 |

协议层不是只能放类型的空壳：必须保留 effects 及其生命周期原语，也允许规范要求的可执行解析与校验。校验负责判断定义是否合规，不通过运行 checks 或 Agent 判断目标是否达成；后者属于业务执行。

## 现有包的目标归属

| 当前包或职责 | 目标归属 | 边界 |
| --- | --- | --- |
| `@potential-guide/effects` | 协议层 | 必须保留，作为核心原语；不得依赖业务逻辑层或工具层 |
| `@potential-guide/objective-pilot` 的定义规范、类型、schema、解析与校验 | 协议层 | 从执行职责中分离，提供独立消费入口，不经业务执行包间接引入上层 |
| `@potential-guide/objective-pilot` 的观察与执行职责 | 业务逻辑层 | 消费协议定义，不重复维护 schema 或规范校验 |
| `@potential-guide/objective-regulator` | 业务逻辑层 | 单目标调节，依赖协议及 Pilot 业务能力 |
| `@potential-guide/objective-portfolio-supervisor` | 业务逻辑层 | 多目标监督，依赖协议及调节业务能力 |
| `pguide` | 工具层 | 瘦身后的发现、分发和必要内建命令 |
| 从 `pguide` 拆出的业务命令包及工具侧共享服务 | 工具层 | 包含七个待拆命令；共包方式不得破坏按需安装和分层 |
| `@potential-guide/config` | 工具层 | 配置命令；共享配置读写不要求其他命令依赖此命令包 |
| `@potential-guide/cli-core` 的 CLI、配置、Agent 和状态实现 | 工具层 | 按职责整理，不把具体实现下沉为协议 |
| `@potential-guide/cli-core` 中确需跨层共享的契约 | 协议层 | 如业务执行需要的能力接口；按真实使用提取，不整体把 cli-core 改称协议包 |

一个包应有明确层级；当前混层包须在拆包中分离职责，不能以同一个包的名称同时属于两层来豁免反向依赖。协议层可以由多个包组成，不强制把所有协议与 effects 合并为一个包。

## 三层之外：后续外迁清单

| 当前包 | 定位 |
| --- | --- |
| `@potential-guide/git-source` | 通用 Git 来源能力，后续外迁；不是协议原语，也不新增适配层容纳它 |
| `@potential-guide/objective-devbox-health` | 具体设备健康需求，后续外迁 |
| `@potential-guide/objective-monorepo-standard` | 具体仓库规范需求，后续外迁 |
| `@potential-guide/objective-pguide-setup` | 具体安装配置需求，后续外迁 |
| `@potential-guide/objective-pguide-self-check` | 具体自检需求，后续外迁 |

这些包在本轮暂留工作区，但不因物理位置而成为三层成员。本轮不选择目标仓库、不迁源码、不改变其独立维护安排。

工具侧来源加载仍可消费 git-source 的公开能力，这是使用待外迁依赖，不是把它重新归入工具层。具体 Objective 可消费三层的公开协议、SDK 或工具；三层生产代码不得反向依赖具体 Objective 实现。测试所需的最小协议夹具不等于内建具体需求。

待外迁清单必须显式列举，不能成为新包或混层代码的默认去处。第三方依赖与 Node.js 平台能力不是新增的架构层。

## 依赖规则与可验证结果

- 三层内允许工具层依赖业务逻辑层和协议层，允许业务逻辑层依赖协议层；禁止所有下层到上层的引用。
- 同层包允许相互依赖，不额外施加层内单向排序；这不豁免现有构建工具对循环依赖的限制。
- 包清单、源码导入、类型导入、重导出和跨包源码路径均须遵守分层，不能通过工具包或相对路径绕过协议边界。
- 自动检查应区分三层成员与显式待外迁包；未知包归属报错，不把待外迁包自动归入协议层，也不因其不在三层内而漏掉三层内部的违规引用。
- 用正反例证明向下依赖和同层依赖允许、向上依赖拒绝，并证明独立使用 Pilot 定义、schema 与校验无需安装业务执行包或 CLI。

实施与验证步骤由 [Implementation.md](../Implementation.md) 细化；本支持文档不增加独立生命周期或验收入口。
