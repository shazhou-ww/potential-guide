# Implementation

本项同时交付 Check 业务包和通用 Server，以一个可运行 MVP 验收。
先接入 Check，再完成 Server 与组合验证；以下为可细化的实施种子，不以旧证据代替新验收。

## Steps

### I-S01: 接入 Check 类型与受控执行

建立 `check-task` 包、TaskType 工厂及输入、Prepared、结果和进展校验。
复用现有制品工具，明确来源授权、选定摘要、实际运行环境和可恢复内容的边界；
Prepared 遵守有限 JSON 与不可变执行内容约束，业务字段不改写通用任务外壳。
复用或提取既有 worker 加载与清理能力，通过通用执行端口及资源池接入启动、报告和回收。
不以旧 Host TaskService 或旧调度器嵌套承接新任务；隔离启动、真实退出和 cleanup 有明确所有者。
由受信任组装注入来源策略、资源与环境，调用方输入不授予权限。

### I-S02: 提供通用服务与 CLI

建立 `task-engine-server` 的程序化启动入口及 CLI，组合现有 Engine、HTTP 适配与 SQLite 默认存储，
保留程序化注入 Store 的能力。受信任本地配置模块注册 TaskType、版本、环境、权限及资源，
HTTP 输入不可指定模块或授予权限；Server 不依赖 Check、Probe、Regulate 或制品包。
实现真实 Node HTTP/SSE 桥接、监听与就绪、显式认证、受限请求处理及退出信号处理；
库入口不隐式监听或安装全局信号处理器。
明确启动失败回滚、订阅关闭、任务资源回收、存储所有权和有界退出顺序，失败不强行宣称已清理。

### I-S03: 打通 MVP 与交付边界

提供 Check 进程内示例及 Server 的 Check 注册配置，使用同一公共任务协议打通提交、查询、历史和 SSE。
通用 Server 另用无业务依赖的测试类型验证。补齐包导出、打包、分层检查和启动文档，
固定新旧入口边界，保持既有调用方行为，不承担全量迁移或制品查询路由。

## Acceptance criteria

### I-AC01: Check 契约与资源可靠

用有效、篡改、未知字段、不支持 runtime 和非法结果样例证明严格校验；
明确验证业务不通过不是执行故障，准确内容和实际环境可追溯，缓存不能绕过授权或摘要约束。
确定性时间测试结合真实 worker 测试证明幂等、执行兼容、独立取消、迟到完成、
强制终止与清理后再分配；共享执行的其他 owner 不受误伤。

### I-AC02: Server 通用且退出可信

无制品任务测试与依赖检查证明 Server 不内置业务类型，程序化和 CLI 入口均可启动，
认证和作用域在真实 HTTP/SSE 上有效。测试端口占用、无效配置、重复存储所有者、
启动中途失败及退出时活动流，证明错误明确、已取得资源正确回收且失败退出不伪装成功。
SQLite 进程重启测试证明原身份与期限保留、未启动工作可恢复、未知已启动工作中断且不自动重跑。

### I-AC03: MVP 闭环与既有行为兼容

真实 HTTP/SSE 测试证明 Check 的提交、结果、分页历史、断线续接和取消与进程内语义一致。
打包消费者与依赖检查证明无需旧 Host 或源码路径即可运行，CLI 导出可执行；
运行相关回归及 `pnpm check`，证明提取复用没有破坏仍保留的旧入口。
