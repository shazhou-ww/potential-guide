## 已明确的进程与并发模型

用户进一步明确：同一 Pilot 实例对应同一个服务进程，每次 check 调用是最小并发单元，
可单独在线程中执行；服务不绑定一个具体 regulation object，各次请求可使用不同 subject。
因此不再以“一个 Pilot 服务只串行执行一个 check”作为默认模型。
regulation、观察、subject、输入视图、证据和取消状态须随请求隔离，不能存成进程全局的当前对象。

这没有改变 Q01 的顶层 CLI 生命周期：同一 CLI 调度上下文可为不同 regulation object
借用同一兼容 Pilot 实例，但不据此要求跨独立 CLI 常驻共享。
线程是执行 check 的机制，不意味着每个 check 定义永久占一个线程，也未要求每次请求
创建并销毁新线程。线程池/复用、最大容量、依赖等待和终止隔离仍需具体设计。

用户进一步要求每个 Objective Pilot 模型拥有一个独立的 Pilot 进程 executable。
这是 Pilot 级统一启动入口，不是恢复每个 check 各自 run.* 的一次性进程模型。
CLI 负责启停、绑定和路由；Pilot 进程自己管理 check 请求排队及线程分配，
并遵守宿主传入的截止、取消和观察约束，不接管 Regulation 的业务决策。
指令通过本地 HTTP RPC 或其他方式下发留待 Q10；此前 HTTP 专属描述按候选方案理解。

## Q01: 谁拥有调度器，服务驻留多久（已明确）

用户明确：check 落为 probe 协议的一部分，形成统一入口；调度器就是 CLI，由 CLI 利用协议调度。
顶层调用 regulation 时先启动所需服务，顶层调用 probe 时也如此；
regulation 内再次调用 probe，若匹配的服务已经存在，则复用而不重复拉起。

因此复用范围为本次顶层 CLI 调用，内层 probe 借用外层已建立的调度上下文，
不能每次重新创建服务管理器。服务按需启停，退出由顶层 CLI 统一负责，
不要求设备级常驻调度器或跨独立 CLI 调用共享。
probe 协议沿用现有术语，不引入新的协议名称；具体服务声明与字段后续设计。
未知的动态依赖如何在首次请求前补充启动、退出如何 drain 及失败回收仍归 Q03/Q06/Q09。

## Q02: 新服务入口与旧 executable/HTTP 入口如何兼容（已明确）

用户接受破坏性升级、全量迁移、无旧协议运行时兼容。新运行时只接受新的 probe check
服务契约，不回退 run.*，不识别旧裸 subject HTTP 为新服务协议，也不长期维护两条执行链。
仓库内所有 Objective、脚手架、示例、测试、生成物和直接相关消费入口同步迁移。

旧输入明确拒绝并给出迁移要求；发布过的 schema 字节/URI、历史源码和固定证据不改写，
改变契约时使用新版本/URI。业务检查函数可复用后接入新 handler，不算旧协议运行时兼容。
这不授权顺带改变层级、Regulation 等无关业务语义；具体 probe 服务声明字段仍待设计。

## Q03: 依赖请求回到谁，如何保持原观察作用域（方向已收敛，协议闭环待讨论）

当前候选方案由 CLI 调度上下文提供请求级受限依赖回调，根服务只发起依赖请求，不自行创建独立 probe。
回调绑定顶层调用、观察、父 check 请求及准确服务实例，并由 CLI 路由回原观察宿主，
继续使用既有来源绑定、深度/次数预算及同轮证据验证。跨 regulation worker 等进程边界时，
可转发控制消息，但必须保留原观察作用域，不能在回调端新建无关的观察来冒充。

回调地址及短期能力由 CLI 在运行时提供，不从 subject 或规则文件接受任意 URL；
仅暴露依赖观察能力，不允许服务要求启动任意程序或读取任意宿主文件。
观察结束/父请求取消时吊销能力，迟到或身份不匹配的回调拒绝。
具体消息字段、能力传递及就绪握手随 Q10 设计；依赖回传可走双向通道，
不一定需要一个反向 HTTP 地址。它们不改变 CLI 为进程调度与宿主证据路由入口的归属。

### 尚未定稿的六个问题

1. **回调入口与宿主路由**：是否由顶层 CLI 启动本地 HTTP 回调入口，
   同时作为 check HTTP 客户端和依赖回调服务端？regulation 在执行 worker 中运行时，
   入口如何把请求送回实际持有观察作用域的进程？这属于本次 CLI 内的临时能力，
   不等于另设常驻 daemon。该双向 HTTP 方案尚未获用户确认。
2. **观察身份与迟到响应**：顶层调用、观察、父请求、服务代际及依赖请求如何关联？
   原观察的短期能力何时失效，怎样拒绝上一轮或已取消请求的回调，而不误接到复用服务的下一轮？
3. **证据登记与响应次序**：依赖结果必须先在原宿主作用域登记来源和观察证据，
   再返回服务并允许父 check 报 dependency problem；不能仅信任服务自报的 HTTP 结果。
   具体关联字段及跨进程转发的上下文恢复方式尚未定稿。
4. **预算和取消传播**：依赖排队、来源准备与检查继续消耗原观察的剩余预算，
   不因回调重新起算；父请求取消后如何吊销能力、取消在途子请求并确认停止？
   资源何时可释放需与 Q04 保持一致，不能只关闭客户端连接。
5. **依赖等待与死锁**：A 等 B、B 再请求 A 时，即使 subject 不同而未触发逻辑递归，
   有限线程容量仍可能被等待中的父 check 耗尽。容量处理、重入拒绝或支持策略需与 Q06 一起明确。
6. **失联及结果未知**：CLI 退出、回调链断开、响应丢失或服务崩溃时，
   子请求和父请求何时失败、哪些结果标为未知、谁清理请求上下文？
   不允许服务无限等待、自行重新发起 probe 或透明重放，具体状态与清理协议需与 Q08/Q09 对齐。

按最新要求，建议先讨论 Q10 的指令传输；若选择 HTTP，再讨论第 1 项的临时回调入口；
随后明确身份与证据登记闭环，再与 Q04/Q06 联动收敛取消和重入。
本次仅记录疑问，不将上述候选接线记为已接受的 wire 契约。

## Q04: 服务端同步执行卡住时，取消保证到什么程度（仍需讨论）

线程执行模型为请求级取消提供了基础：建议进程控制线程不执行 check 的同步 CPU 工作，
每个工作线程一次只运行一个 check 请求；协作取消超时后终止对应执行线程并等待退出，
将该请求标为失败或结果未知，不重放，也不连带取消其他线程的请求。
线程重新投入使用前必须确认旧任务停止并完成请求资源清理。

仍需验证所选运行时的终止和资源清理保证，包括 check 自行启动子进程或调用原生资源的情况；
线程终止不天然等于其全部外部工作已停止。整个服务崩溃/失控时仍需 CLI 兜底回收，
并明确所有在途请求的失败。具体保证待设计验证，不把 HTTP 断线视为终止确认。

## Q05: 本机托管服务与远程 HTTP 服务是否同属本次范围（仍需讨论）

建议首轮只支持本机托管、同用户受限访问；若 Q10 选 HTTP，显式绑定 loopback，
若选本地管道则限制连接访问。仍需能力校验和秘密日志边界。
远程服务的输入视图传输、文件系统可见性、来源信任和授权不同，不能沿用本地路径引用。
按 Q02 不保留原始裸 subject HTTP 运行链路。若要支持远程服务，它同样必须满足新的 probe
契约，而不是兼容旧 endpoint；是否将远程自管服务纳入首轮仍需决定。

## Q06: 排队、并发与依赖重入（部分收敛）

CLI 调度器持有顶层调用的服务上下文；check 调用是最小并发任务，
同一 Pilot 进程可通过多个线程处理不同 check、regulation object 与 subject。
Pilot 进程自行管理内部队列、执行容量和线程分配，CLI 不另建一套逐线程调度队列。
执行容量与队列须有界，控制/依赖调度独立推进；线程并发不允许绕过业务层级顺序。
可明确：不同已就绪服务之间的依赖请求不能被等待中的父请求占满全局调度槽；
控制面和依赖派发不排在该父请求后方。现有递归/深度/逻辑观察预算仍由观察宿主执行，
排队时间计入请求及整体剩余预算，过载明确失败而不无限积压。

同一服务忙并不再是拒绝依赖重入的充分理由；有可用线程时可执行不同 subject 的子请求，
但仍检查逻辑递归和证据作用域。有限线程全被等待依赖的父 check 占满时仍会死锁，
需选择释放/挂起执行容量、预留依赖容量或明确拒绝不可调度请求；
不能只把父请求移出全局计数而仍让它占着所有实际线程，也不能无限扩线程。
线程复用策略、并发数、队列上限和容量耗尽错误仍待设计。
在 Node.js worker_threads 等独立执行环境中，模块初始化通常仍按线程发生，
不能假设主线程加载一次 TypeScript 就自动供全部线程共享；需实测线程复用的收益。

## Q07: 实例共享的身份与升级边界（技术方案已收敛）

不同 subject 可共享同一 Pilot，但不同用户、权限、启动配置、规则目录树和支撑来源
不能默认共享。首轮保守地将规范 Objective ID、准确 commit、directory tree、
repositoryTree、probe 协议版本、启动及执行权限配置纳入实例兼容判定；
同 tree 不同 commit 也不合并，避免增加逐请求跨来源证明。

就绪握手绑定由 CLI 启动的实例代际和来源，不能仅信任 PID 或端口。
同一顶层调用固定来源，不热替换运行中服务代码；确需不同版本时创建隔离实例，
旧实例在其任务结束后回收。服务异常后的新实例是新代际，旧响应不能满足新请求。
subject、语言和观察 ID 仍是请求身份，不因包不同重复启动同版本服务。
regulation object 同样是请求关联身份，不作为一个服务只能绑定一个对象的限制；
跨对象请求也必须使用各自的输入视图、观察作用域、回调能力、预算和证据。

## Q08: 请求去重、超时后结果未知与重试（技术方案已收敛）

结果未知的 check 不自动重放；CLI 区分未受理、执行中、已完成、确认取消和状态未知。
请求身份绑定顶层调用、观察、实例代际及 requestId；重复提交不能二次执行，
同 ID 不同内容必须拒绝。后续状态查询/取消不能隐式成为重新执行请求。

首轮不提供跨服务重启的持久去重或 exactly-once 保证；故障后在途结果可为未知，
不能把“重启服务”当作重试旧 check 的授权。去重记录及容量须有明确运行期边界：
未过期身份不可因容量淘汰后又被当成新请求；容量耗尽明确拒绝，具体值后续设计。
CLI 或 Regulator 已有显式重试策略若允许新尝试，仍需新身份、独立证据并记录次数，
不能被 HTTP 适配层的透明重试替代。

## Q09: 服务与来源资源的管理面放在哪里（所有权已收敛）

调度所有权已由 Q01 确认为 CLI，不再要求选择独立常驻调度器。
顶层 CLI 持有服务注册、启动仲裁及来源 checkout，内层 probe 借用服务句柄；
跨执行 worker 边界传递受限的会话连接/能力，而不是在各进程各建一个同身份服务。
已知根服务在执行前准备，动态依赖在首次派发 check 前由同一 CLI 调度上下文确保就绪。

退出顺序明确为停止受理、取消/等待活动任务、确认服务终止、再释放来源和输入资源；
内层 probe 返回不触发顶层服务关闭。按 Q04，确认失败不能伪装成已回收。
CLI 非正常退出的孤儿服务检测/父会话失联机制必须覆盖，不引入跨 CLI 服务发现。
probe 协议的 ready/status/cancel/shutdown 字段和具体模块拆分属于后续设计，
不再把“另起独立常驻调度器”列为架构选项，也不另造业务 Coordinator。

## Q10: Pilot executable 接收 check 指令的传输方式（待讨论）

已明确的是每个 Pilot 的统一 executable、驻留进程、内部 check 队列及线程模型，
未明确的是下发请求/接收结果的传输。现有 idea alias `http-check-services` 保留用于定位，
不构成必须采用 HTTP 的契约要求。

| 候选 | 可取之处 | 需要补齐的边界 |
| --- | --- | --- |
| 本地 HTTP RPC | 跨语言、易诊断，已有 HTTP probe 的部分校验逻辑可复用 | 就绪地址、认证、请求取消与依赖回传；普通 POST 不自带双向回调 |
| 标准输入/输出上的双向消息 RPC | CLI 已拥有子进程，连接与寿命直接关联，不需端口或反向监听 | 消息分帧、requestId、多路复用、背压；stdout 专用于协议，日志与之分离 |
| 本地 socket / Windows named pipe RPC | 可分离启动通道和数据通道，支持本机双向连接 | 跨平台寻址、访问限制、连接认证、清理及依赖回传 |

候选是取舍列表，不要求一次实现所有传输，也不将 RPC 自动等同于某个具体标准。
统一 probe 请求语义应先明确：实例/请求身份、check ref、subject、输入视图、预算、
取消、结果和依赖请求。最终选定传输承载这些语义；进程复用本身不依赖 HTTP。
Node 专有 process.send 虽可复用部分现有代码，但会限制跨语言 executable，不能不经讨论就作为统一要求。
