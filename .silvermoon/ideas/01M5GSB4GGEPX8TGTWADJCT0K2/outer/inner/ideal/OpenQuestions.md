# 待讨论问题

以下均为未决事项。每项区分当前建议与需要用户决定的边界，不把未作答视为接受。
Q01-Q05 直接影响构想范围，应优先讨论；其余在进入实现前收敛。

## Q01: 谁拥有调度器，服务驻留多久

候选 A：一次 Regulation/执行会话持有，独立 probe 自建临时服务，结束统一回收。
候选 B：设备用户级外部调度器，独立 CLI 共享服务，以租约、空闲截止和显式关闭回收。
候选 C：二者均可，公开接口支持注入已有调度器，无需所有消费启动全局服务。

建议以执行接口和所有权分离为基础；若要求跨独立 CLI，必须至少提供 B，
不能把一次 withPilot 内的进程表称作跨 CLI 共享。用户尚未明确默认采用哪种。

## Q02: 新服务入口与旧 executable/HTTP 入口如何兼容

需要决定是可选服务 descriptor、manifest 新契约，还是全面替换 run.*。
已有 createHttpCheckProbe 发送裸 subject；托管服务若需要请求上下文，应定义新绑定方式，
不能静默替换旧 body。建议首轮显式 opt-in 并保留旧入口，但是否接受维护两种形态待讨论。

## Q03: 依赖请求回到谁，如何保持原观察作用域

候选为调用者宿主的受限回调、调度器中转，或 HTTP 请求挂起后由宿主解析依赖再续传。
建议来源解析与证据验证继续归调用者宿主，但回调连接、认证、存活及失败传播没有定稿。
服务不得借 HTTP 自行另起 probe、绕过同轮版本绑定，或接受任意回调 URL。

## Q04: 服务端同步执行卡住时，取消保证到什么程度

普通 AbortSignal 只取消客户端等待，TypeScript 同步 CPU 工作又可能阻塞服务控制面。
需决定首轮接受“终止整个实例且显式影响所有在途请求”，还是要求执行线程/子执行单元
提供逐请求强制隔离。前者简单但共享客户端有连带失败，后者实现复杂且不能又每请求重载。

## Q05: 本机托管服务与远程 HTTP 服务是否同属本次范围

建议首轮只支持本机托管、显式 loopback、同用户受限访问；仍需鉴权和秘密日志边界。
远程服务的输入视图传输、文件系统可见性、来源信任和授权不同，不能沿用本地路径引用。
是否一开始就支持远程自管 endpoint，还是仅保留原始 HTTP adapter 能力待决定。

## Q06: 排队、并发与依赖重入

建议业务请求初版串行、队列有界，控制/依赖调度可独立推进。
需决定全局与实例级额度如何协调、等待依赖是否释放额度、过载返回什么，
避免父请求占满全局槽导致子服务等待。现有递归/深度/逻辑观察预算不能因服务共享失效。

## Q07: 实例共享的身份与升级边界

不同 subject 可共享同一 Pilot，但不同用户、权限、启动配置、规则目录树和支撑来源
不能默认共享。相同内容树而检索 commit 不同是否允许复用，服务如何逐请求证明准确来源，
与服务升级时旧请求 drain/新请求切换的策略需明确。

## Q08: 请求去重、超时后结果未知与重试

建议默认不自动重放结果未知的 check，明确区分未受理、执行中、已完成、已取消和状态未知。
是否保留有界 requestId 去重记录、保留多久、跨服务重启能否查询结果，都未定。
HTTP POST、自称只读或连接断开本身不提供 exactly-once 保证。

## Q09: 服务与来源资源的管理面放在哪里

需确定调度器作为独立 app/package、库托管宿主还是 CLI 的服务管理命令，
以及启动入口、ready 握手、状态查询和显式关闭的最小接口。
来源 checkout 目前随 withPilot 结束删除；长期服务需由谁持有代码与输入资源、何时回收，
不能仅让服务进程多活几分钟而留下失效文件路径。
建议协议、执行机制与宿主装配分层，不把新管理器变成业务 Coordinator。
