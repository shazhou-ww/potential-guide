# Deployment

## Steps

### D-S01: 固定版本隔离消费

通过独立安装的 CLI、共享 Check Host 与 Node worker 包，使用真实本地 HTTP RPC
验证多客户端、多 Pilot、不同 regulation object/subject 的检查和连续观察；
记录准确来源、Host/线程及请求身份，不借用工作区模块。
覆盖全部内置 Objective 的迁移入口，并核验结果/错误、取消、依赖和证据消息正确关联。
通过实际 HTTP 接口验证异步受理、任务查询、事件读取/确认和依赖回传，不以内部 API 替代。

### D-S02: 检验复用收益与故障回收

比较首次及连续调用的时延和初始化计数；验证 Host 竞争启动、Pilot 版本冲突、
目标变化、依赖等待、部分客户端退出、取消和最后回收，以及旧协议明确拒绝。
持续交错执行不同 subject 的成功/失败/取消请求，按已确定的负载与回收窗口记录
heap、外部内存、Host RSS 和存活资源，检查复用后清理与 worker 退役。
观察同版本替补预热、正常退役与异常隔离的真实任务流转和峰值资源，不执行预热业务 check。
不执行未授权的 npm 发布、远程部署或生产变更。

## Acceptance criteria

### D-AC01: 真实消费证明复用

固定版本公开入口证明多个 CLI 和 Pilot 共用同一 Host HTTP endpoint，
内部 worker 经消息通信复用，准确版本和业务结果不变、跨 subject 证据不混淆。
记录线程初始化、冷/热耗时和可复现命令，不以源码测试替代真实消费。

### D-AC02: 失败与资源边界成立

真实操作证明 Host 发现、启动、版本冲突、依赖、客户端失联、取消及回收符合已确认契约；
不误杀其他客户端任务，不提前释放来源/视图或静默重放，不改写历史固定证据，旧协议明确拒绝。
连续复用的原始记录证明请求资源不持续累积、缓存符合上限，失败/取消后仍能正确处理新请求；
不得通过每次重启 worker 或一次强制 GC 代替内存回收验收。
丢响应与重复事件不导致二次业务执行；替补预热不突破资源上限或造成新旧版本并存。
