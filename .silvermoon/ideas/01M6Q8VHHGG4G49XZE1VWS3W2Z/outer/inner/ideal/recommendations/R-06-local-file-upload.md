# R-06：让二进制文件通过授权通道直传，不经过模型转抄

**产品与责任**：读取本地文件的 Agent 宿主 / MCP 适配层为主，Pinboard MCP 服务配合。**覆盖**：A-18，关联 A-13、A-23。证据见[问题清单](../Acceptance-issues.md)的 E4、E8。不是要求远端 MCP 服务直接访问操作者磁盘。

## 判断

一个约 23 KB 的 CAR 被编码成三万多个字符后，由模型拼接进入工具参数，多出一个字符即导致失败。这类转抄不应是正常产品路径；让模型更仔细或使用更多子代理，都不能消除该结构性风险。

## 建议修改

1. 在本地宿主提供“选择已授权文件 → 确认目标与公开性 → 上传”的文件桥接能力。模型传递不透明文件句柄及预期摘要，不接触文件的整段 base64；宿主在明确文件访问授权范围内读取同一个稳定快照。
2. 宿主自行完成大小限制、哈希计算和编码，并调用现有已授权 MCP 工具。对当前允许的内联大小，可以先在宿主内可靠编码，无需改成新的 HTTP 上传协议；MCP OAuth 仍留在现有客户端内部。
3. 把来源哈希、字节数、期望根与目标 endpoint/name 绑定给该次调用，回执返回摘要和服务结果。发送前发生文件变化则明确拒绝；结果未知则先核实，不自动重复发布。
4. 超过 MCP 内联上限时提前拒绝，给出实际支持的替代通道。若将来需要直传，可设计范围受限、短期的上传授权，但必须经过服务端协议和权限审查；不能拿 MCP OAuth 冒充普通 HTTP API token。

文件句柄、桥接动作和摘要校验是拟议宿主能力，不是现有 Pinboard 工具已经支持的参数。CLI 在拥有独立合法 token 时已有文件导入路径，应优先复用；没有 token 时不能通过窃取另一通道凭据“修复体验”。

## 取舍与边界

此建议与 [R-05](./R-05-pinboard-import.md)互补：宿主保证发送原字节，服务保证内容满足导入契约。桥接不能允许任意远端工具请求读取任意本地路径；用户授权应绑定文件、服务和操作，公开上传需要明确确认。凭据、短期上传 URL 和文件内容均不进入不必要的聊天日志。

先支持已有大小范围，避免为了一个小 CAR 引入复杂的分片上传系统。大文件能力是后续范围，不是本建议的隐含承诺。

## 验收方式

- 本次三个 CAR 经桥接上传，源快照与实际发送字节哈希一致，模型上下文无需出现 base64。
- 文件被替换、句柄越权、大小超限、错误 endpoint 均在发送前明确拒绝。
- 包含中文路径、空格和任意二进制内容时不受 Shell 引号或 stdin 编码影响。
- 授权只对正确通道生效；OAuth 不被导出，失败与未知结果不会被显示成上传成功。
