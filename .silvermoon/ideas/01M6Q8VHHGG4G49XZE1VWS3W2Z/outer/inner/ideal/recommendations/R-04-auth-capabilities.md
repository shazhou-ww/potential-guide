# R-04：按 endpoint 和调用通道报告认证能力

**产品与责任**：Pinboard CLI 负责自身 API token 诊断；MCP Portal/客户端负责连接及 OAuth 通道。**覆盖**：A-12、A-13、A-14、A-15。证据见[问题清单](../Acceptance-issues.md)的 E3、E4、E8。这些产品不在本仓库实现，本篇是可交给相应维护者的建议。

## 判断

“pinboard 命令可运行”“MCP 已授权”“可以上传到某 endpoint”是不同事实。仅测试环境变量或工具是否被列出，会得到错误的可用性判断。本次 `unknown chat session` 的根因未确认，不应笼统归为 Pinboard OAuth 故障。

## 建议修改

1. CLI 增加明确的只读诊断入口，报告命令版本、规范化 endpoint、凭据来源类别（不含内容）和实际能力探针结果。没有凭据、服务不可达、凭据被拒、只读可用、写权限未知分别表达。
2. MCP 客户端显示“发现 → 连接 → 授权 → 具体工具能力”各层状态。路由错误引导重新连接/发现，OAuth 拒绝引导对应授权，不把所有失败都显示成“请配 token”。
3. 两条通道各自给出准确恢复动作：CLI 的安全输入方式、MCP 的授权入口，以及“不自动互通”的说明。汇总面板只能汇总已验证事实，不能让 CLI 读取宿主 OAuth 或声称知道另一通道的私有状态。
4. 能力包含可用上传种类、大小上限、是否接受原文件，以及验证时间。若服务没有只读写权限探针，明确返回“上传权限未验证”；不要创建公开测试 pin 来伪装成无副作用的健康检查。

以上描述的是拟议诊断契约，现有 help/list/set-token 不等于已有该统一入口。

## 取舍与边界

保留 MCP OAuth 与 API token 的隔离，不做自动同步、导出或代填。只读 list 成功不能证明所有写权限；一次诊断成功也不能免除执行时校验。错误回执只保留安全的类别、endpoint 和恢复入口，不带 Authorization、token、私有文件路径或完整原始配置。

## 验收方式

- CLI 无 token、MCP 已授权时，同时正确显示两者状态；CLI 不再被误报为可写。
- 连接未就绪、OAuth 失效、endpoint 不可达、只读成功但写权限未知可被分别诊断。
- 诊断没有公开写入副作用；日志/JSON/错误回执均不泄露秘密。
- 用户完成对应恢复动作后只重新验证受影响通道；不要求无关服务反复授权，也不无限重连。
