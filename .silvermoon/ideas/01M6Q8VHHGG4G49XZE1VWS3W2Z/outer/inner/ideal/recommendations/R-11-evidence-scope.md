# R-11：按当前验收范围展示证据，保留历史而不混淆结论

**产品与责任**：Silvermoon 的审阅呈现与仓库交付报告适配。**覆盖**：A-33，关联 R-01、R-07。证据见[问题清单](../Acceptance-issues.md)的 E2、E3、E4。

## 判断

“本地验证通过”“npm 已发布”“MCP 已授权”“九个用例通过”都是真实事实，但各自证明的范围不同。用户不应通读全部历史段落才能知道今天还缺什么。Silvermoon 已有准确 world revision、提交和接受门禁；缺口在本次证据呈现和范围绑定，不应再造一套并行生命周期。

## 建议修改

1. 先由仓库交付报告适配层输出按验收项组织的证据摘要：要求标识、观察时间、环境、制品身份、实际检查范围、结果与来源链接。区分通过、失败、阻塞、未执行及范围不适用，不从 prose 或上传回执推导完整成功。
2. 把证据绑定到执行时的契约/要求来源和制品身份。新增要求后，原证据仍保留，但新增维度标为未验证；未变化的要求可经明确复核复用，不能因为添一份结果文件就机械否定所有历史证据。
3. Silvermoon 的 gate review 优先呈现“当前可接受范围 / 尚缺证明 / 沿用依据”，历史错误和恢复过程保留为链接。工具只展示记录与一致性检查，不自动向 endpoint 发请求，也不从 checkbox 生成 acceptance。
4. 当前清单与详细报告用同一投影生成，减少手工勾选与叙述漂移。若报告缺必需字段，明确显示证据不充分；不能生成默认成功。

## 最小实施边界

第一阶段可只改仓库中的结构化交付报告和呈现约定，复用现有 supporting files、稳定 D-* 标识及准确修订门禁。不立即改变 Silvermoon 核心 event schema，不给事件日志塞入外部操作细节，更不在泛用 Silvermoon 中硬编码 npm、Pinboard 或 Task Engine 的业务字段。

只有跨项目需求得到验证后，再将通用摘要能力提给 Silvermoon 维护者。外部操作的真实性仍来自相应产品和验收工具，报告不能自行“证明”上传、退出或回收。

## 取舍与边界

“已恢复”不等于“根因已修复”，“旧失败”也不等于“当前仍失败”。显示最新适用观察时必须保留冲突或未知状态；环境、CID 或要求不同的结果不能静默覆盖。明确的人工验收仍针对准确同步修订，任何摘要都不能代替该决定。

## 验收方式

- 本地 Kubo 通过、公共 Gateway 未测时，报告明确公共项未执行，不误勾选。
- 从“CLI 无 token”发展到“MCP 上传成功、Reference 未通过”时，当前摘要呈现新状态，历史失败可追溯且不误作当前阻塞。
- 契约追加 Ubuntu 要求后，相应证明被标记待补；已验证且未变化的包身份事实可明确复用。
- 记录缺失、相互冲突或来自不同 CID 时，门禁摘要显示不充分；没有自动 submit/accept 或篡改历史事件。
