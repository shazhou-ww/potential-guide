# R-08：让 Check 消费契约可执行、可校验、可正确解读

**产品与责任**：Check SDK、check-environment 及其消费者示例。**覆盖**：A-26、A-27，关联 A-24。证据见[问题清单](../Acceptance-issues.md)的 E2、E4、E8。

## 判断

已有 README 提供工具、目录和网络输入；问题不是完全没有文档，而是示例与实际 Schema、问题码和运行终态之间仍需要消费者自行拼接。把缺目录当成另一错误码、假定所有取消都 stopped，说明契约未在消费入口充分体现。不能为了让夹具好写而改变既有业务结果或通用 Engine 状态。

## 建议修改

1. 为每种 Check 提供可直接执行的最小消费范例，示例输入在测试中对实际打包 Bundle 的 Schema 验证；从相同作者声明核对问题码，不另维护一份人工字符串全集。README 的 JSON 应被这些测试覆盖或从受测 fixture 派生。
2. 在提交前或本地 dry validation 中输出字段路径、所违反的约束及对应公开说明。例如 network 缺 `dns` 或 HTTP 参数时，不让消费者只得到难以关联的拒绝；保留现有严格 Schema，不添加静默默认值来掩盖漏填。
3. 明确展示三个独立维度：业务 `{pass:true|false}`、Task/Run 执行终态、资源实际回收。提供“缺目录”“工具超时”“工具取消”“网络取消”的受测解读示例，不把 canceled、failed、stopped 和 reclaimedAt 合成一个模糊“成功/失败”。
4. 工具取消可能是 canceled=true 且 failed、网络取消可能是 stopped；先如实记录和回归。若要统一语义，需另行论证并选择明确版本边界，不在这项消费改进中暗改。

## 复用入口与取舍

复用[Check SDK](../../../../../../../packages/check-sdk/README.md)、[环境输入与结果说明](../../../../../../../packages/check-environment/README.md)及实际打包契约；公开示例使用普通本地项目和支持的 exports。不在 SDK 根运行时引入 TypeBox 作者工具、文件扫描或发布逻辑。

该建议不建立旧 Check Host 的替代注册层，也不把每种业务知识搬进 Engine。字段诊断属于 Schema/消费层，资源回收事实仍来自 Engine；展示时结合，职责上分开。

## 验收方式

- 文档示例用安装后的包独立运行；对网络必填字段、无效问题码和额外结果字段的负例有准确诊断。
- 不存在目录得到真实 `directory-unusable`，问题码变化会让关联 fixture/文档检查失败。
- 超时和取消不生成伪业务结果；工具与网络的既有不同终态被准确展示，并单独验证物理释放。
- 作者声明、Schema、运行时允许码和消费示例保持一致，没有第二份容易漂移的业务定义。
