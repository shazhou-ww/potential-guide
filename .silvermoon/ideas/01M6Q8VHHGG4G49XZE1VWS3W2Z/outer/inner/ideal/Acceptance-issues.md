## 构建、字节与制品身份

### A-01: Reference 的 CRLF/LF 改变交付身份

- **现象/影响**：Windows 工作树 Reference 曾为 CRLF，提交规范化为 LF；同一业务源码的页面字节、CAR 与 CID 因而变化，早期证据不能直接沿用。
- **状态/措施**：本次已规范化相关输入并重建；未通过修改协议自动归一化来掩盖字节差异。证据 E1、E2。
- **后续方向**：将实际输入字节与提交快照的一致性纳入发布前检查。

### A-02: Turbo 恢复旧 CAR，源码正确也不等于输出正确

- **现象/影响**：完整检查曾因缓存恢复的旧 CRLF 制品与当前 LF Reference 不一致而失败。
- **状态/措施**：对 SDK/environment 强制重建，五项制品测试及随后完整 `pnpm check` 通过；缓存键或跨环境复用原因未被系统修复。证据 E2、E8。
- **后续方向**：复现并明确换行、输出及缓存输入的边界，保留精确字节拒绝测试。

### A-03: 远端操作目录遗留了旧 CAR

- **现象/影响**：远端三个手工暂存 CAR 是旧 CRLF 版本，但已发布包的 `references.json` 指向正确 LF CID；暂存文件名相同，不能证明身份相同。
- **状态/措施**：已用已安装 npm 包中的 CAR 替换操作目录副本，并用标准 `readTaskArtifact` 校验根 CID。旧根与新根、SHA-256、大小见 E4。
- **后续方向**：从一个已验证来源生成部署清单，禁止把可变操作目录视为权威。

### A-04: 监督者给出了与期望 CID 不配套的“批准哈希”

- **现象/影响**：监督者最初把旧暂存文件的大小/SHA-256 与正确 LF CID 拼在一起交给上传代理，导致代理先拒绝了实际上正确的 dist CAR。这是验收编排错误，不是实现者篡改制品。
- **状态/措施**：已交叉核对 E2 的历史机器证据、当前标准 CAR 解析结果及已发布 npm 包，纠正输入。证据 E2、E4、E8。
- **后续方向**：同一次机器读取必须同时产出根 CID、文件 SHA-256、大小和来源版本，不手工拼接清单。

### A-05: 不应仅靠手写 CAR 头解析确认身份

- **现象/影响**：上传代理用 CBOR 字节标记定位根 CID；这不能替代完整 CAR、块哈希及规范目录树验证。
- **状态/措施**：监督者改用仓库公开 `readTaskArtifact` 复验；确认当前 dist 的三个正确根与历史独立执行证据一致。证据 E4、E8。
- **后续方向**：部署预检统一复用标准制品读取器。

### A-06: 新包暴露了仓库声明与数量断言的接线遗漏

- **现象/影响**：新增 SDK 后，包自有 Objective subject 声明/数量、分层、打包和生成文件识别等配套检查需要同步，否则不能把业务单测通过当作仓库集成通过。
- **状态/措施**：相关接线及断言已修，最终完整检查通过；不是待修产品故障。证据 E1。
- **后续方向**：明确新增包的仓库集成清单，继续保留结构校验。

## npm 发布与安装前置条件

### A-07: 两个 Check 包原先没有正式发布路由

- **现象/影响**：仅有可打包包定义/verification inventory，不等于已有独立 tag、workflow choice 和 release inventory。
- **状态/措施**：已补齐 SDK/environment 发布路由、顺序测试和文档，通过既有 Action 发布两个 `0.1.0`；未另开本地发布通道。证据 E7。
- **后续方向**：发布准备应同时验证包本体与发布控制面。

### A-08: 本机安全策略阻止访问 npmjs

- **现象/影响**：本机直接 registry 查询受阻，无法据此判断版本占用或发布结果；npmx.dev 查询又曾返回 404。
- **状态/措施**：研究遵循用户指定的 npmx.dev；权威版本及安装验证在获准的 Ubuntu/Actions 执行。没有绕过本机策略。证据 E3、E8。
- **后续方向**：分开记录研究来源与实际 registry 验证环境。

### A-09: `latest` 可能仍是占位版本

- **现象/影响**：两个新包原先只有占位版本；Task Engine 多个包的 `latest` 也并非要安装的 RC。省略版本会装错“全套”。
- **状态/措施**：逐包确认并安装 13 个明确版本；SDK 必须先成功发布，再发布依赖它的 environment。证据 E3、E7。
- **后续方向**：维护可复验的产品套件版本清单，而不是依赖所有包的 `latest`。

### A-10: 发布依赖 exact-main CI，不能以本地通过替代

- **现象/影响**：发版必须满足准确 tag SHA 对应 main push CI 的 Release verification；本地通过、其他 SHA 通过或部分矩阵通过都不足够。
- **状态/措施**：等待 E5 全绿后才打 tag，两次发布均验证 metadata/provenance。此为正确门限造成的前置等待，不是应绕过的缺陷。证据 E5、E7。
- **后续方向**：更早展示发布就绪状态，减少门限与 npm 授权的混淆。

### A-11: npm 默认阻止 esbuild 安装脚本

- **现象/影响**：Ubuntu npm 12 安装时发出 esbuild postinstall 被默认策略阻止的警告，安装退出 0 不能单独证明作者工具可用。
- **状态/措施**：未放宽脚本权限；之后用已发布 SDK 的示例和独立 npm 项目实际构建成功，得到与本地一致的 text CID。证据 E4。
- **后续方向**：保留真实作者构建探针，不把警告直接判为失败，也不盲目开放安装脚本。

## Pinboard、认证与上传

### A-12: CLI 缺少 endpoint 的独立 API token

- **现象/影响**：本机与 Ubuntu `pinboard import/list` 返回 `TOKEN_REQUIRED`；命令可执行与网络命令已授权是两回事。
- **状态/措施**：CLI 仍未授权；用户恢复 MCP 后改走已授权 MCP 上传。没有搜寻、导出或记录凭据。证据 E3、E4、E8。
- **后续方向**：预检明确报告可执行性、endpoint、授权通道和所需恢复动作。

### A-13: MCP OAuth 与 CLI 授权互不等价

- **现象/影响**：用户完成 MCP 授权后，CLI 仍返回 `TOKEN_REQUIRED`；MCP OAuth 只支持其内联上传，不能作为普通 HTTP/CLI token 搬运。
- **状态/措施**：分别实测，MCP list 成功后用 MCP 上传；Deployment 显式纳入替代通道。证据 E4、E8。
- **后续方向**：在认证说明中明确凭据边界，不让用户重复授权错误的通道。

### A-14: 工具发现与连接状态曾阻塞 MCP 使用

- **现象/影响**：先前连接失效/需重新授权；恢复后还遇到一次工具路由 `unknown chat session`，不能仅凭工具名称存在声称可用。
- **状态/措施**：重新连接对应 server、发现工具并用只读 list 验证成功。具体客户端路由原因未确认。证据 E8。
- **后续方向**：区分发现失败、连接未就绪、OAuth 失效及服务端业务拒绝。

### A-15: Shell 的“token 可用”检查曾给出误导信号

- **现象/影响**：一次环境检查受 Shell 引号/条件表达影响，输出看似可用；实际 CLI 拒绝才是有效授权观察。
- **状态/措施**：已撤回该推断，全部认证结论以真实 endpoint 操作决定；没有读取 token 内容。证据 E3、E8。
- **后续方向**：用不泄露秘密的真实能力探针代替环境变量真假推断。

### A-16: MCP 的 `cid` 参数没有阻止错误根 CAR 被接受

- **现象/影响**：对旧 tools CAR 提供正确期望 CID，返回回执却是 CAR 自身的旧根；不能假定参数承担 expected-CID 断言。是否属于接口缺陷须先确认该参数对 `kind:car` 的契约。
- **状态/措施**：监督者拒绝把它当成功交付；正确三个根后来均有匹配回执。证据 E4。
- **后续方向**：明确参数语义，并始终比较上传回执根与预期根。

### A-17: 曾误上传一个旧 tools pin

- **现象/影响**：受 A-03/A-04 影响，旧 CRLF tools 根以正式标签上传了一次；这是本次操作失误。
- **状态/措施**：该操作自有 pin 已 unpin；这是移入可恢复删除，不保证公开块字节立即消失。没有删除原有用户 pin。证据 E4。
- **后续方向**：上传前绑定来源、标准根校验和标签；误上传清理保留回执及公开数据边界。

### A-18: 大段 base64 手工转抄产生单字符损坏

- **现象/影响**：一次 tools 内联上传返回 `400 Invalid base64`；应为 31336 字符，实际多一个 `J`，定位在零基偏移 9610。
- **状态/措施**：修正该字符后上传成功；三个最终 payload 均与源 CAR 的字节/SHA-256 核对一致。未重建或改写制品。证据 E4、E8。
- **后续方向**：减少需要模型转抄的大块二进制；在可授权的文件上传入口中直接传文件，或提供可靠的参数文件桥接。

### A-19: Pinboard 回执大小不是 CAR 文件大小

- **现象/影响**：例如正确 tools CAR 为 23500 字节，pin 回执 size 为 22797；直接比较不同口径会误判上传损坏。
- **状态/措施**：以原始文件 SHA-256、根 CID、块验证及实际消费核对，不把回执 size 当 CAR 容器字节数。证据 E4。
- **后续方向**：接口和验收报告标明容器大小、内容/块大小各自口径。

## 远端执行与跨平台脚本

### A-20: SSH 默认身份未能登录

- **现象/影响**：默认 SSH 认证失败，安装不能直接开始。
- **状态/措施**：使用设备既有合适 identity，并显式限制为该身份后成功；没有读取私钥内容或索取新凭据。证据 E8。
- **后续方向**：远端安装前验证目标、身份和非交互登录能力。

### A-21: 非交互 SSH 没有加载 NVM 的 Node PATH

- **现象/影响**：远端有合适 Node/npm，不代表非交互命令能找到它们。
- **状态/措施**：仅在操作脚本内显式设置该已安装版本的 bin PATH；未改用户全局 Shell 配置。证据 E3、E8。
- **后续方向**：安装探针同时记录真实执行版本和 PATH 来源。

### A-22: Windows CRLF 使 Bash 脚本无法执行

- **现象/影响**：`set -euo pipefail` 因行尾 CR 变成无效选项；早期 stdin Bash 命令也曾被尾部 CR 破坏。
- **状态/措施**：安装脚本格式化为 LF、重新传输并通过 `bash -n`；不依赖临时忽略 CR 的技巧。证据 E8。
- **后续方向**：传输前验证脚本编码/行尾，不把 Windows 文本直接假定为 Linux 脚本。

### A-23: PowerShell 原生命令与多层 SSH 引号失真

- **现象/影响**：一次 `node -e` 失去字符串引号报 SyntaxError；一次远端 curl 的 write-out 文本被拆成多个 URL，打印 DNS/URL 错误但最终退出码仍为 0。
- **状态/措施**：改用文件或传给 Node 的脚本，并记录结构化 HTTP 状态；不再采信该 curl 输出。证据 E8。
- **后续方向**：避免多层 Shell 嵌套引号；验证每个有意义步骤，而不是只看最后退出码。

### A-24: 用 CJS resolver 定位 import-only ESM 包失败

- **现象/影响**：验收脚本的 `createRequire().resolve` 报 `ERR_PACKAGE_PATH_NOT_EXPORTED`，虽包已成功安装。
- **状态/措施**：改为 ESM public export 解析；当前脚本显式启用所需 parent-URL resolve 支持。没有绕过 exports 指向内部源码。证据 E8。
- **后续方向**：独立消费者脚本按公开模块条件解析，尽量避免实验性 resolver 依赖。

### A-25: 语法检查遗漏了验收脚本运行时自由变量

- **现象/影响**：公开 CID 首个 tools 用例实际完成并回收后，记录结果的 `finish` 使用未定义 `request`，抛出 ReferenceError。`node --check` 不会发现这一类错误。
- **状态/措施**：改为 `submitted.request` 后重跑，九个业务用例均走到预期终态；不能把本次失败归咎 Engine。证据 E4、E8。
- **后续方向**：把复用验收脚本纳入类型/静态检查或实际小型运行测试，确保报告代码本身受测。

### A-26: 初版夹具对契约的假设错误

- **现象/影响**：曾把缺失目录预期为 `not-directory`，实际是 `directory-unusable`；网络请求也需遵守 `dns`、HTTP expectedStatus 和 followRedirects 的实际必填形状。
- **状态/措施**：修正夹具而非改业务语义，当前用例通过。证据 E2、E4、E8。
- **后续方向**：从公开 Schema/类型生成或校验验收输入，不凭印象填写字段或问题码。

### A-27: 工具取消与网络取消的终态并不统一

- **现象/影响**：工具取消会因既有 `Command cancelled.` 表现为 failed，网络取消为 stopped；一律预期 stopped 的夹具曾失败。
- **状态/措施**：保留原行为，核对 canceled、停止请求、无 Result 和真实物理回收；不能仅靠终态字符串判断取消正确性。证据 E2。
- **后续方向**：先澄清统一取消语义是否是独立需求，再决定是否改产品；不在本次迁移中暗改。

## 不稳定测试、公开消费与证据门限

### A-28: 实施阶段全量运行曾有 Engine 并发启动超时

- **现象/影响**：首次完整运行失败，但限定相关测试并发后通过，后续完整运行也通过。
- **状态/措施**：未更改通用 Engine 实现或降低断言；未确认系统性根因。证据 E1。
- **后续方向**：区分资源争用、测试隔离与产品超时，采集可重复环境数据。

### A-29: 较早 Windows packed CLI 用例未在观察窗口结束

- **现象/影响**：旧 MVP Check 仍为 running，断言预期 completed；该远端 CI 不能声称全绿。
- **状态/措施**：保留失败事实，不通过放大超时或跳过旧测试来掩盖。证据 E2、E6。
- **后续方向**：复现运行时间及资源争用，确认是夹具窗口还是执行/回收问题。

### A-30: Node 24 CI 既有 Probe 物理清理失败

- **现象/影响**：E5 首次 attempt 的旧 Probe 预算测试出现 `Engine retains ownership because physical cleanup is unconfirmed.`，Release verification 因而失败。
- **状态/措施**：仅重跑失败 jobs 后通过，未改代码或门限；重试成功不是根因已修复。证据 E5，测试位置 `packages/probe-task/test/probe.test.ts`。
- **后续方向**：单独调查 wall/depth/check-count budget 与物理释放的时序证据。

### A-31: 未上传时 Gateway 404 被正确投影为获取失败

- **现象/影响**：目标 CID 原先返回 `404 Block not found`，真实提交被拒绝 `bundle_fetch_failed`；不是 `{pass:false}` 的业务检查结果。
- **状态/措施**：恢复授权、上传正确 CAR 后九个真实业务用例已执行。网站首页、CLI help 或 Engine/UI 返回 200 不能证明该 CID 可消费。证据 E3、E4。
- **后续方向**：前置检查目标块和客户端所需协议，并保留获取失败与业务结果的边界。

### A-32: raw Gateway 可执行，不代表 UnixFS HTTP 路径可读取

- **现象/影响**：正确三个 CID 可由已安装 Engine 通过 raw Gateway 消费，九项通过/问题/故障/取消用例均观察到物理回收；随后请求 `/ipfs/<cid>/resources/check.json` 返回 404，Reference 阶段没有完成。
- **状态/措施**：当前仍待澄清。需区分 Pinboard 路径路由能力与验收夹具对 Gateway 的假设；不能据此认定制品缺页，也不能声称所有 Reference 验证通过。证据 E4。
- **后续方向**：确认应通过 HTTP UnixFS 路径、受支持 CAR 导出还是 raw DAG 客户端按 CID 读取，并逐字节复验。原 IDEA 的 Outer 仍未提交/接受。
