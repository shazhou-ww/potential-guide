# Implementation

## Steps

### I-S01: 统一输出格式和关键信息

按[24 项实测问题](./ideal/output-findings.md)和[输出规范方向](./ideal/output-conventions.md)统一列表、详情、回执、诊断、观察、执行、帮助和错误。每项明确处理结果；涉及流、分类、参数或机器结果的行为变动先确定兼容方案。复用既有模式，不预设渲染框架。

本次拆分为资源/诊断、观察/执行、帮助/迁移三组，由实现 Agent 分别修改独立文件。共享 Markdown 转义及代码围栏、结构化输入错误、跨命令集成与最终验证由主 Agent 负责。使用现有 TypeScript、Biome、Node/tsx 测试，不增加第三方依赖或渲染框架。

### I-S02: 补充兼容性测试和说明

以[覆盖矩阵](./ideal/output-coverage.md)和[实际样例](./ideal/output-examples.md)为回归基线，在现有 CLI 测试中断言格式与关键信息，覆盖主入口、独立命令和迁移器；更新帮助、README 及原文/协议边界说明。为尚未实测的终端和真实 Agent 分支补充必要证明，不把 fixture 当作生产能力证据。

## Acceptance criteria

### I-AC01: 人类输出可判断且一致

每个问题有对应修复或明确的兼容处置与证据。测试证明关键身份、来源、结果、停止/错误原因及适用下一步可见，空态不含糊、帮助不误导；默认/Markdown 和主入口/独立入口采用一致内容规则。

### I-AC02: 机器契约及原文出口不变

回归测试证明 JSON 成功和失败均有明确结果、既有字段含义和退出码保持兼容，脱敏仍有效；补全脚本、元数据、配置原值、check/runtime 协议及报告产物保持各自用途。动态字段归一化后比较，运行相关测试和 `pnpm check`，明确暴露非本次改动导致的失败。

## Compatibility decisions

- F14：保留观察、调节和监督既有 JSON 错误类别及退出码；统一人类根因和目标上下文，不在展示层重构中悄悄重分类外部失败。
- F16：普通命令结果和错误继续使用现有 stdout，迁移器默认错误继续使用 stderr；README 明确这两个兼容边界。JSON 编辑器输出转到 stderr，避免污染最终 JSON，但不移动既有错误 envelope。
- F20：机器帮助补充共享用法、选项、约束和示例，保留已有 `options`、`types`、`subcommands`、`resourceSchema` 等字段。
- F21/F22：迁移器继续用 `--format` 选择文档种类，新增 `--output-format markdown|json` 选择回执格式；产物格式仍由输出文件扩展名决定。保留旧 JSON help 用法、拒绝覆盖、输入不变和 pinned evidence 边界。
- F23：明确拒绝未识别的 validate 参数，沿用 `CliError` 的 invalid/退出 2；这是本次有意修复的误导性成功行为，不将旧退出 0 伪装成兼容不变。
- F24：领域输入错误携带类型化校验问题或可用语言；CLI 单独渲染人类说明，原始机器错误文本、状态和退出码不变，不通过解析错误字符串恢复结构。
- 固定协议、命令发现元数据、补全脚本、配置原值和报告产物保留其用途；不引入交互 TUI 或隐式分页，不自动发布 npm。
