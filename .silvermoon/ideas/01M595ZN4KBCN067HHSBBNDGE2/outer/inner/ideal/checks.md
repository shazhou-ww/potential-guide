# 两层检查范围

本文细化 [Idea](./Idea.md) 的需求与边界，不预定实现架构、描述文件名或最终 schema 字段。

## 检查依据

项目在仓库中维护结构化需求描述，明确交付物的稳定身份、用途、类型、关联 workspace、交付入口、运行或交付目标，以及必要的关系与独立交付约束。

交付物、package 和部署环境分别描述，不要求一一对应。一个需求可以关联多个包，一个包可以支撑多个需求；内部共享包无需伪装成独立交付物。跨包约束按这些关系检查。

需求描述声明意图，已有工具配置承载实现。优先引用已有配置，避免复制所有工具参数形成第二套配置。目录规范具有明确、可版本化的来源：默认约定与项目显式覆盖均须可追溯；不将检查器隐含偏好视为项目要求。

## 第一层：项目结构合理

本层回答：仓库骨架是否完整，全局契约是否有效并对应实际结构？

| 检查面 | 要求与典型问题 |
| --- | --- |
| 目录 layout | 检查应用、共享包、文档、scripts、migrations 的位置与职责归属。区分项目级文档与包级文档；服务专属迁移随服务或数据包归属，跨服务迁移有项目级协调归属，不强制全部集中到根目录。 |
| 必要文件 | 按已声明需求和结构规范检查 workspace 配置、包清单、文档及适用的构建、发布、部署配置是否齐全；不要求没有线上服务的项目提供部署文件。 |
| 现有文件归位 | 不仅检查缺少什么，也检查现有文件是否符合所在目录的职责与允许内容；识别散落文档、临时输出、过期副本、错放脚本或迁移文件等候选问题，依据明确规则提示应归入的目录，不将名称或扩展名作为违规的唯一依据。 |
| 全局 schema | 需求描述及受支持的全局技术配置可解析，并符合各自格式与 schema；缺失文件、非法字段、未知版本须显式报告，不能静默忽略。 |
| 引用一致性 | 需求引用的包真实存在、被 workspace 收录、包身份匹配；文件引用不悬空，映射无歧义，重复或矛盾声明可定位。 |
| 覆盖关系 | 所有 workspace 有明确职责；实际发布或部署入口不遗漏声明；允许有支撑交付物的内部包与开发工具包，不要求每个包独立交付。 |

全局需求契约或关键映射无效时，先报告并修复第一层，不能从现有代码猜测并补成已确认需求，也不能将无法开展的第二层判为通过。

### 归位诊断与边界

结构规范既说明必要内容，也说明各目录允许的职责、生成物和缓存的处理方式，以及显式例外。平台强制位置的配置、合法根目录文件、第三方或生成内容按其适用规则处理，不把未出现在需求描述中的每个文件都当作杂物。不能仅依赖 Git 跟踪状态或忽略规则决定文件是否合规。

对明确错放的文件，报告当前位置、违反的规则、预期职责归属及建议目标目录；例如服务专属文档归入对应服务文档位置，数据迁移归入对应服务或数据包的迁移位置。可能涉及导入、脚本、文档链接或工具固定路径时，提示迁移后需同步相关引用。若规范未定义归属、存在多个合理位置或用途无法确认，报告待分类及所缺依据，不臆造目标、不默认删除。

归位是给 Agent 或维护者的修复建议，检查本身不移动、删除或覆盖文件；后续授权整理须保留内容、维护引用，并在目标已存在时显式处理冲突。

## 第二层：逐个需求的配置合理

本层回答：每项已声明需求对应的包与配置，是否具备完成交付的条件？

按需求遍历全部交付物，找到入口包和关联包，汇总适用检查，不因首个失败跳过其余有效对象。共同依赖不必重复执行相同检查，但结果必须可追溯到受影响需求。

### 通用包检查

- 检查内部依赖声明、允许的依赖方向、禁止的循环以及绕过公共入口的跨包引用。合法例外须显式声明，不把所有依赖边一概视为问题。
- 区分运行、开发及 peer 等依赖用途；检查目标运行时和包边界兼容性，防止浏览器交付物引入服务端专用实现或秘密供应入口。
- 检查构建、类型检查、测试等任务与项目任务图的一致性，构建前置关系及输出路径是否支撑交付。仅在声明需要独立发布或部署时验证相应独立性。

### 按包角色与交付物类型细化

| 类型或角色 | 细化检查项 |
| --- | --- |
| npm 公共库 | 发布身份与渠道、公开 exports、适用的类型声明、发布文件范围、运行时兼容性；内部依赖在发布后可解析，或已按明确构建策略包含；不遗漏必需文件、不混入秘密与无关产物。 |
| CLI | 可执行入口及其打包内容、目标 Node 或其他运行环境、构建与启动方式；支持的命令发现或扩展入口与交付配置一致。CLI 可以同时是 npm 发布包，适用规则叠加而非互斥。 |
| 浏览器前端 | 浏览器入口、构建产物与部署目录一致；公开配置的注入阶段明确；服务端秘密不进入客户端；引用的 API 等外部服务与目标环境声明一致。 |
| Worker 或其他线上服务 | 服务入口与目标运行时兼容；部署文件、构建产物、环境选择一致；普通配置、秘密引用、资源 bindings 或平台身份有明确归属和供应方式；需要迁移时，有对应目标资源和执行入口。Cloudflare 是首批明确支持的部署目标，其他目标不可默认视为已验证。 |
| 内部共享包与开发工具包 | private 或其他交付声明符合角色；公共边界、依赖方向、构建方式与消费者一致；不因位于共享包目录就强制要求发布配置。 |

多角色包应用所有适用检查，不强制前端与 API 拆包，不要求每个包都有独立部署文件。仅有发布元数据不足以证明包内容可消费，仅有构建脚本也不足以证明产物存在；报告须标识实际采用的是配置证据、构建或打包验证证据，不能混淆。

### 部署配置的深度

运行与部署契约按需要描述普通配置、秘密、平台资源的分类、可见范围、供应来源和环境映射。声明引用名称而非秘密值，不固定要求将秘密存储到某个文件。

OIDC、数据库等是按需能力，不是所有包的核心字段或必检项。其配置归属和供应路径属于交付准备；远端身份提供方是否生效、部署是否成功、线上登录是否可用不在本 Objective 的默认验收范围。

## 两层边界与报告

同一主题可有不同深度：第一层检查部署文件存在并归属正确，第二层检查其入口和环境配置；第一层检查 migrations 位置与归属，第二层在适用时检查执行入口及资源映射。

问题至少能追溯层次、需求或交付物、相关包、规则、配置位置和观测证据，并给出修复方向；全局问题不伪造所属包。区分满足、不满足、未验证和不适用：缺少证据、缺少工具、外部不可达或不支持的类型不等于满足。适用且必需的检查未验证时，不宣称整体通过。

检查本身不执行安装、发布、部署、数据迁移或其他修复。涉及执行构建、测试、打包的验证须明确执行边界和副作用，不执行任意不可信仓库脚本。修复由 Agent 在授权范围内完成后重新观察。
