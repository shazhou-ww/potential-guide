# 任务操作面板：需求确认稿

版本：构想候选 v0.3，2026-10-31 已对齐完成的三个依赖；等待本 idea 的独立构想决定。

这是 [Idea.md](Idea.md) 的用户评审附件，用“用户故事 + 验收例子”整理已经谈到的需求，不是另一份独立契约。[访谈记录](UseCases.md)保留原始表达和分析过程。

本文确认的是产品要帮助你做什么、怎样判断做到了，不是确认已经交付。本轮有效故事为 US-01 至 US-06、US-10 至 US-12；用户已将 US-07 至 US-09 的资产管理需求移出通用 Engine/Web UI 范围，下文仅保留延期标记。

## 本轮真实试用反馈（2026-10-31）

第一轮已完成，用户实际试用后要求调整，而不是继续照着草图纵向堆 Block：

- 仅保留“任务 / 执行”两个主 Tab；任务页包含当前与历史任务，不再有独立历史页。
- 新建和编辑后重做在任务页的 Popup 完成；收藏不是独立页面或 Popup，而是任务上的星标，支持“只看收藏”筛选。
- 执行页必须覆盖整个 Endpoint 获授权且保留的记录，包括其他客户端触发、从未打开过关联任务的执行；不能只显示本机已知关联。
- 用户指出 Echo 已完成并回收，但 Observation 仍不断刷新，造成仍在运行的错觉。明确展示主结果与独立观察状态；充分证明终结/回收后收尾，手动停止观察不取消后端任务。
- 用户明确要求：“那你去调整一下，调整好之后，我再在浏览器里查看一下新的页面长啥样。” 本轮需要可运行产品而非另一份静态草图。

[当前接口核对](Research.md#当前接口核对)记录三个已完成依赖的最终公开契约；后面的早期调研保留历史基线，不再把已补齐能力描述为当前缺口。依赖的接受决定不表示本 UI 已获接受或交付。

[交互设计](Design.md)及[离线草图](Wireframe.html)已按反馈明确 Task/Execution 分区与统一提交任务栏；其余标为候选的交互不自动成为已确认需求，示例数据不代表服务能力已经实现。用户将 UX 细节交由 Agent 收敛，待真实产品可用后再反馈使用体验，不要求逐项审草图。

## 1. 要解决什么问题

你已经有 Task Engine Server，希望不用每次写命令或代码发送 HTTP 请求，就能亲手尝试它；同时看清任务排队、合并、取消、超时等行为到底怎样发生。

日常以单条提交为主，偶尔批量创建任务做调度实验。还需要复用常用输入，查询目标 Endpoint 上的全部可访问历史任务并重做；历史保留与清理由 Service 配置和治理。首版不提供资产管理，也不假设所有 Task 都有资产或资产必然按类型独占。

## 2. 从使用者的角度看全流程

| 我想做的事 | 我会经过的步骤 | 对应故事 |
| --- | --- | --- |
| 尝试一个任务 | 看服务支持哪些类型 → 按类型填表 → 提交 → 观察过程与结果 | US-01、US-02、US-04 |
| 做一次调度实验 | 准备一组任务 → 调整提交顺序 → 一次发送 → 观察排队与合并 → 尝试取消或超时 | US-03 至 US-06 |
| 少做重复输入 | 收藏常用任务 → 原样一键再发，或修改后发；也能从历史任务重做 | US-10、US-11 |

“阶段”对应任务的 stage；“事件”是执行过程中产生的事实记录，不是界面猜测。某些类型输入可以含 artifacts、URL 或 digest，它们在通用 UI 中只是普通参数，不意味着 UI 获得资产解析或管理职责。

“任务栏”是此前“任务篮”的统一提交容器：容纳草稿、单条或多条批次及逐项回执。它与服务端 Task、实际 Execution 是不同层次，不是新增服务端批量实体。

## 3. 用户故事与验收例子

### US-01：知道能运行什么，并按类型填表

作为尝试服务能力的人，我希望看见这个服务注册了哪些任务类型，并按所选类型填写对应表单，而不是自己记住输入格式。

怎样算做到：

- 服务支持的类型不同，显示的类型及表单也随之对应，不把 Check 或其他类型写死为唯一选择。
- 选择某种类型后，表单依据该类型的输入说明（schema）提供相应字段。
- 通用 UI 只消费 Task 公开输入 Schema，不根据业务 URL 下载或解析制品以取得动态 subjectSchema；仅声明为 object 的字段可使用通用对象编辑，不猜测其内部业务字段，也不因此阻塞整个任务表单。
- 输入不符合要求，或取不到类型及输入说明时，明确说明问题，不编造可提交的表单。
- 从填写到提交期间类型契约发生变化时，保留用户输入并明确提示，不静默按过期表单发起；输入契约 revision 与业务参数中的 digest 不是同一种版本锁定。

### US-02：方便地提交一个任务

作为日常使用者，我希望填好后直接提交一个任务，不必先手动加入多条集合再发送；直接提交自动创建并发送一个单任务栏批次。

怎样算做到：

- 一份填写完整的输入可以直接提交，提交后能定位到对应任务并观察它。
- 任务栏始终存在；直接提交是创建单条批次并立即调用统一发送流程的快捷方式，校验、提交身份及回执处理与多条流程一致。
- 单条快捷不清空或发送已有多条草稿；收藏再发与历史重做也复用同一提交机制。
- 提交失败会明确显示；无法确定是否已创建时，不冒充确定成功或失败。
- 重复点击或重试同一次提交不应意外多创建任务；主动再做一次则是新的提交。

### US-03：在任务栏准备多条并按顺序提交

作为做调度实验的人，我希望按类型逐个准备任务，像购物车一样加入待发送集合，调整顺序后一次点击发送。

怎样算做到：

- 加入任务栏时只是准备草稿，尚未向服务创建 Task；单条快捷与手动多条都是任务栏中的提交批次。
- 发送前可调整顺序；发送时按这个顺序提交，不等前一任务完成才提交下一条。
- 某条提交失败，显示该条结果并继续提交后面的任务，不暂停整批等待处理。
- 提交顺序不承诺执行顺序；实际开始、合并和完成仍由服务调度。

### US-04：看清任务经历了什么

作为观察任务的人，我希望看见当前阶段及其变化、关键过程的起止、进度事件，并能展开事件详情，而不只是等一个最终结果。

怎样算做到：

- 任务运行时可查看当前 stage、阶段变化和关键过程的开始与结束；过程与阶段不混为一谈。
- 提交任务栏、Task 与 Execution 分成清晰区块；通过关联标识导航，不混放提交回执、任务状态和执行生命周期。
- 能查看中途的 progress events，以及所观察任务的各类事件详情，不只显示 UI 预选的几种事件。
- 能查看任务输入、可获得的状态快照、结果和故障；正常完成但业务结论为否，不显示成系统执行失败。
- 断线、旧数据或历史已过期会明确标识，不把不完整记录伪装成完整实时过程。

### US-05：观察排队、合并与资源分配

作为验证调度的人，我希望观察多个任务如何等待和获得执行资源，以及可合并任务是否真的合并执行。

怎样算做到：

- 在执行并发度有限时提交多个任务，能看清哪些在等待、哪些在执行，以及随后怎样变化。
- 对可以合并的任务，能依据服务提供的事实辨别任务与实际执行的关联，而不是因为结果相同就认定发生了合并。
- Task 区显示任务事实及关联入口，Execution 区显示执行与回收事实；取消某个 Task 不得让关联 Execution 被误标为已取消或已回收。
- 不在没有服务证据时声称资源已经分配、共享或释放；缺少必要观察能力要显式指出并作为依赖解决。

本故事不默认增加“在 UI 调整执行器并发度或调度策略”的功能。

### US-06：尝试取消、超时等生命周期行为

作为验证边界行为的人，我希望操作指定任务的取消，并观察任务遇到超时时的实际反应。

怎样算做到：

- 对明确选中的目标服务和任务执行取消，能继续查看其实际后续状态及事件。
- 取消请求已发送，不直接等于执行已经停止或资源已经释放。
- 在准备好的超时场景中，能辨别超时相关事实及后续变化，不把它们压缩成一个含糊的失败标签。
- 关闭页面或停止 UI 不会替我取消任务；取消必须是我的显式操作。

暂停、恢复、强制重跑等其他生命周期操作尚未提出，不默认包含。

### US-07、US-08、US-09：已移出首版的资产管理需求

- **US-07** 原缓存浏览需求：延期，不提供通用资产列表。
- **US-08** 原历史制品版本选择器：延期；用户在普通任务参数中填写已知 URL/digest 仍可提交，不等于 UI 提供版本目录。
- **US-09** 原手动缓存清理需求：延期，不提供清理操作或相关治理入口。

原始场景和分析保留在[访谈记录](UseCases.md)，不再作为本 UI 的验收标准或实施前置。以后若有明确需要，可针对具体类型考虑独立工具型 UX；目前不定义通用资产抽象、TaskType 资产接口、插件系统或工具扩展槽位，也不替独立 idea 作废弃决定。

### US-10：收藏后原样再发，或作为模板修改

作为经常运行相似任务的人，我希望收藏完整任务输入，以后不用反复输入；对包含 artifacts 与 subject 的类型，也原样保留这些参数。

怎样算做到：

- 在任务列表和详情直接标星/取消标星；“只看收藏”覆盖当前 Endpoint 的全部本机星标，不仅过滤当前已加载的目录页。收藏与任务身份、Endpoint 关联，重复标星不产生多份收藏。
- 收藏没有独立页面或弹窗。未提交输入使用现有草稿流程；已有旧格式参数收藏不得静默删除，兼容访问不能把无 Task 身份的旧模板伪造成服务任务。
- 收藏保留完整类型输入，不只保留任务名称；URL、digest、artifacts、subject 等如存在便原样保存，不要求每种 Task 都有这些字段，不查询或管理它们引用的资产。
- 收藏面向同一台电脑上的持续使用，UI 重启后仍可使用，不为收藏引入账号体系或跨设备同步；不因 Service 清理任务历史而自动删除收藏，具体存储方式留到实现期。
- 同一调试工具可连接多个 Endpoint；收藏同时记住任务对应的 Endpoint，再发时不能静默改投当前选中的其他服务。
- 可以原样一键再发，也可以从收藏创建新输入，修改 subject 等内容后再发。
- 原样再发保留收藏中的 URL 及版本锁定信息，不根据上次实际解析结果自动补锁，也不自动解锁或改写 URL。
- 固定 URL 继续使用原固定引用；浮动 URL 未锁版本时允许取得更新内容，通常不锁版本；浮动 URL 已锁版本时仍按该引用提交，若发生版本不匹配就明确报告，不静默换版。
- 从收藏派生新任务，不自动修改原收藏；再次发起与重试原提交相区分。

记住目标不等于将后端凭据保存到收藏。原目标缺失或配置发生显式重新绑定时，停止快捷再发并说明原因，不能自动改投当前目标；具体标识与配置格式由实现收敛，不承诺凭 URL 字符串识别所有服务身份变化。

### US-11：查询 Endpoint 历史并从原参数重做

作为想复查以前行为的人，我希望查到这个 Endpoint 上的历史任务，不限于通过本工具提交的任务，并能套用原参数再次发起任务，不必重新拼输入。

怎样算做到：

- 历史列表覆盖目标 Endpoint 在当前权限和 Service 保留策略下可查询的全部历史任务，包括由命令行、代码或其他工具提交的任务，不以本机记录替代服务端历史。
- 基础查找支持按任务类型和服务接收时间 receivedAt 范围筛选；不以预约、实际开始、结束或客户端本地发起时间替代，不假装已经搜遍只加载的一页。
- 时间范围使用明确时区，包含下界、不包含上界；列表标明观察时刻和查询有效期，续页保持同一快照。列表摘要不含业务结果，详情和原参数独立读取；查询过期/失效时明确重新查询，不将新旧页拼成一个完整列表。
- 对能取得输入的历史任务，以当时填写的参数为模板：可以直接重做，也可以形成新的任务描述，修改并确认后再发；二者只有交互过程差异。
- 重做与收藏采用相同的引用语义：原来未锁版本就不自动补锁，原有 URL 和版本锁定原样保留，除非用户明确修改；不按上次实际解析版本自动生成新锁定。
- 新提交与原任务可区分，不把它解释为恢复原来那次执行。
- 保存期限、是否清理及是否定期清理由 Service 配置和治理，UI 不自定一套服务历史保留/清理策略，也不因此默认增加 UI 治理配置功能。
- 列表范围与不可用原因如实呈现：已被 Service 清理、不可访问和查询失败不冒充完整历史或成功重做。

这不要求恢复已清理的数据或绕过访问控制。服务端目录、时间边界及稳定分页已交付，UI 直接消费其契约；列表权限不等于发现类型、读取详情或原请求的权限。后端另有 updatedAt 筛选/排序，不因此自动扩展本 UI 首版的用户故事；按 Input 内部参数筛选仍是后续高级候选。

### US-12：浏览 Endpoint 的执行记录

作为调试者，我希望在执行 Tab 直接浏览当前 Endpoint 中获授权且保留的执行记录，无需先打开某个任务；正在执行与已结束的执行都可以查到，包括其他客户端触发的执行。

- 由服务端公开执行目录返回记录，不通过 UI 扫描历史事件、遍历任务详情或本机缓存伪造完整列表。
- 目录有明确排序、分页、查询时刻和失效处理，独立于任务目录与事件游标；查询遵守可信调用方 scope、授权和保留策略。
- 共享执行只出现一次；关联 Task 不泄漏其他 scope 或无权限的任务，摘要不暴露原输入、Prepared、结果或后端凭据。
- 列表与详情分开，Task / Execution 可互相定位；错误、权限不足、旧服务不支持和空结果分别显示，不悄悄退回“本机已观察”列表。
- 服务端存储与重启场景能保持目录正确；不是只给演示 fixture 增加私有接口。本轮由服务端补齐该缺口，不增加调度控制或资源拓扑大盘。

## 4. 共同边界

- UI 是独立、可选服务。后端没有 UI 也能工作；UI 不内嵌或启动 Task Engine，不接管后端生命周期。
- 通用任务操作不绑定某一种业务类型；资产管理不属于 Engine 或其通用 Web UI 的职责。具体任务可能没有资产，也可能共享资产；不以独立任务类型为由强加一套统一资产抽象。
- 只通过明确的公开能力访问后端。若服务缺少所需能力，先列出缺口并确定归属，不偷偷增加接口或虚构数据。
- 错误、连接状态和任务状态如实呈现；凭据不暴露给页面，不允许任意地址代理或任意文件访问。
- 中文、键盘可用、焦点清楚，窄屏能操作；不以营销页或装饰性大盘替代任务工作台。
- Tab、弹窗和常驻任务栏按键盘可操作；关闭弹窗/切换 Tab 保留本次草稿和列表上下文。结果用清楚的中文状态突出显示，观察连接时间不是“任务仍在运行”的标志。
- Task 终结不等于 Execution 已回收；只有充分公开证据才自动结束相应实时观察。停止流不能同时废掉历史分页，手动重新观察仍可用。
- 本次不加入文件上传、本机文件导入、业务执行器开发或生产运维管理；不影响其他会话、工作树或既有服务。

## 5. 接入边界与实现期细化

第一轮依赖已交付；本轮新增执行目录缺口明确由服务端负责，不靠猜测补齐服务事实，也不用于缩减范围：

| 事项 | 接下来怎样处理 |
| --- | --- |
| 类型与 schema 发现 | [Task Schema 与发现](../../../../01M66MRFCSDK99MAEN8RN3NKBH/outer/inner/ideal/Idea.md)已完成；消费 GET `/task-types` 与当前 revision，处理 412，不依赖动态制品元数据或资产管理 |
| 同机收藏保存在哪里 | 具体存储/文件格式由实现选择，但必须持久可用、目标关联明确，不跟随服务历史清理，也不保存后端凭据 |
| Endpoint 配置 | 由可信 UI Server 配置提供目标与凭据，浏览器只选择受控目标；明确处理配置删除/重新绑定，不增加任意地址代理 |
| Endpoint 历史查询 | [task-history-query](../../../../01M66TPNEMSQ8Y8SDSN2CDN6BA/outer/inner/ideal/Idea.md)已完成；独立 list 权限、固定快照与独立目录游标，不用本机索引顶替，不新增 UI 治理 |
| Endpoint 执行目录 | 本轮补齐公共协议、服务、存储和 HTTP；复用目录机制并维护 scope/授权/冻结分页及独立游标边界 |
