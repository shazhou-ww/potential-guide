# 任务操作面板：需求确认稿

版本：v0.1，待用户确认。

这是 [Idea.md](Idea.md) 的用户评审附件，用“用户故事 + 验收例子”整理已经谈到的需求，不是另一份独立契约。[访谈记录](UseCases.md)保留原始表达和分析过程。

本文确认的是产品要帮助你做什么、怎样判断做到了，不是确认界面设计、技术方案或已经交付。下面的验收例子是分析师根据访谈整理的确认建议，尚未经过用户逐项验收。全部故事属于本次需求基线；尚未划分首版与后续版本，也未决定开发优先级。

2026-10-30 的[能力与缺口调研](Research.md)补充源码证据及候选建议，不表示本需求已获接受，也不把技术缺口转换成范围删减。

## 1. 要解决什么问题

你已经有 Task Engine Server，希望不用每次写命令或代码发送 HTTP 请求，就能亲手尝试它；同时看清任务排队、合并、取消、超时等行为到底怎样发生。

日常以单条提交为主，偶尔批量创建任务做调度实验。还需要查看和管理任务类型的公共资产，复用常用输入，重做历史任务。

## 2. 从使用者的角度看全流程

| 我想做的事 | 我会经过的步骤 | 对应故事 |
| --- | --- | --- |
| 尝试一个任务 | 看服务支持哪些类型 → 按类型填表 → 提交 → 观察过程与结果 | US-01、US-02、US-04 |
| 做一次调度实验 | 准备一组任务 → 调整提交顺序 → 一次发送 → 观察排队与合并 → 尝试取消或超时 | US-03 至 US-06 |
| 使用和管理资产 | 看缓存及版本 → 选历史版本发起任务，或手动清理旧缓存 | US-07 至 US-09 |
| 少做重复输入 | 收藏常用任务 → 原样一键再发，或修改后发；也能从历史任务重做 | US-10、US-11 |

这里的“资产”指任务类型使用的 artifacts，例如 Checker、Objective 制品；“阶段”对应任务的 stage；“事件”是执行过程中产生的事实记录，不是界面猜测。

## 3. 用户故事与验收例子

### US-01：知道能运行什么，并按类型填表

作为尝试服务能力的人，我希望看见这个服务注册了哪些任务类型，并按所选类型填写对应表单，而不是自己记住输入格式。

怎样算做到：

- 服务支持的类型不同，显示的类型及表单也随之对应，不把 Check 或其他类型写死为唯一选择。
- 选择某种类型后，表单依据该类型的输入说明（schema）提供相应字段。
- 输入不符合要求，或取不到类型及输入说明时，明确说明问题，不编造可提交的表单。

### US-02：方便地提交一个任务

作为日常使用者，我希望填好后直接提交一个任务，不必先加入批量任务篮。

怎样算做到：

- 一份填写完整的输入可以直接提交，提交后能定位到对应任务并观察它。
- 提交失败会明确显示；无法确定是否已创建时，不冒充确定成功或失败。
- 重复点击或重试同一次提交不应意外多创建任务；主动再做一次则是新的提交。

### US-03：准备一篮任务，按顺序批量提交

作为做调度实验的人，我希望按类型逐个准备任务，像购物车一样加入待发送集合，调整顺序后一次点击发送。

怎样算做到：

- 加入任务篮时只是准备任务，尚未向服务创建任务。
- 发送前可调整顺序；发送时按这个顺序提交，不等前一任务完成才提交下一条。
- 某条提交失败，显示该条结果并继续提交后面的任务，不暂停整批等待处理。
- 提交顺序不承诺执行顺序；实际开始、合并和完成仍由服务调度。

### US-04：看清任务经历了什么

作为观察任务的人，我希望看见当前阶段及其变化、关键过程的起止、进度事件，并能展开事件详情，而不只是等一个最终结果。

怎样算做到：

- 任务运行时可查看当前 stage、阶段变化和关键过程的开始与结束；过程与阶段不混为一谈。
- 能查看中途的 progress events，以及所观察任务的各类事件详情，不只显示 UI 预选的几种事件。
- 能查看任务输入、可获得的状态快照、结果和故障；正常完成但业务结论为否，不显示成系统执行失败。
- 断线、旧数据或历史已过期会明确标识，不把不完整记录伪装成完整实时过程。

### US-05：观察排队、合并与资源分配

作为验证调度的人，我希望观察多个任务如何等待和获得执行资源，以及可合并任务是否真的合并执行。

怎样算做到：

- 在执行并发度有限时提交多个任务，能看清哪些在等待、哪些在执行，以及随后怎样变化。
- 对可以合并的任务，能依据服务提供的事实辨别任务与实际执行的关联，而不是因为结果相同就认定发生了合并。
- 不在没有服务证据时声称资源已经分配、共享或释放；缺少必要观察能力要显式指出并作为依赖解决。

本故事不默认增加“在 UI 调整执行器并发度或调度策略”的功能。

### US-06：尝试取消、超时等生命周期行为

作为验证边界行为的人，我希望操作指定任务的取消，并观察任务遇到超时时的实际反应。

怎样算做到：

- 对明确选中的目标服务和任务执行取消，能继续查看其实际后续状态及事件。
- 取消请求已发送，不直接等于执行已经停止或资源已经释放。
- 在准备好的超时场景中，能辨别超时相关事实及后续变化，不把它们压缩成一个含糊的失败标签。
- 关闭页面或停止 UI 不会替我取消任务；取消必须是我的显式操作。

暂停、恢复、强制重跑等其他生命周期操作尚未提出，不默认包含。

### US-07：查看某类任务的资产缓存

作为使用 Checker、Objective 等资产的人，我希望有地方查看缓存了哪些 artifacts、各是什么版本。

怎样算做到：

- 能识别缓存条目及其版本，并知道查看的是哪个服务或资产管理范围。
- 这些是任务类型管理的公共资产，不被误当作单个任务的临时状态。
- 查不到或无法连接时明确说明，不用空列表假装没有缓存。

### US-08：选择历史 artifact 版本运行任务

作为排查或对比行为的人，我希望指定一个历史版本的 artifact，用它运行某个任务。

怎样算做到：

- 选择历史版本后，发起的任务明确引用所选版本，不静默换成最新版本。
- 所选版本无法使用时明确说明，不自动替换成别的版本。
- 这是一次新任务提交；不承诺把整个运行环境也恢复为历史环境。

### US-09：手动清理旧缓存

作为管理本地缓存的人，我希望手动选择旧的缓存 artifacts 并触发清理。

怎样算做到：

- 清理范围明确指向资产所在环境中的缓存，不是浏览器电脑文件，也不是远程制品本身。
- 能知道哪些条目被清理、哪些未清理及原因，不把失败说成成功。
- 不提供任意路径删除功能；对仍在使用的资产怎样保护，需在此故事实施前补齐规则。

这里不默认包含自动清理、上传或远程制品删除。

### US-10：收藏后原样再发，或作为模板修改

作为经常运行相似任务的人，我希望收藏完整 artifacts 与 subject，以后不用反复输入。

怎样算做到：

- 收藏保留完整 artifacts 与 subject，不只保留一个任务名称或资产名称。
- 收藏面向同一台电脑上的持续使用，不为收藏引入账号体系，不提供跨设备同步；具体保存位置与保留时间仍待细化。
- 同一调试工具可连接多个 Endpoint；收藏同时记住任务对应的 Endpoint，再发时不能静默改投当前选中的其他服务。
- 可以原样一键再发，也可以从收藏创建新输入，修改 subject 等内容后再发。
- 从收藏派生新任务，不自动修改原收藏；再次发起与重试原提交相区分。

Endpoint 的记录方式、配置变更或原目标不可用时的处理尚未决定；记住目标不等于将后端凭据保存到收藏。

### US-11：从历史任务重做

作为想复查以前行为的人，我希望从以前做过的任务再次发起任务，不必重新拼输入。

怎样算做到：

- 对能取得输入的历史任务，可用其输入再次发起任务，而不是只打开旧结果。
- 新提交与原任务可区分，不把它解释为恢复原来那次执行。
- 历史记录来自哪里、覆盖哪些范围有明确标识，不把浏览器已知任务假装成服务器全量历史。

是否允许先编辑、引用变化的资产如何解析，留待本故事细化。

## 4. 共同边界

- UI 是独立、可选服务。后端没有 UI 也能工作；UI 不内嵌或启动 Task Engine，不接管后端生命周期。
- 通用任务操作不绑定某一种业务类型。资产能力归具体任务类型，不能为了资产管理把通用任务内核变成 Checker/Objective 管理器。
- 只通过明确的公开能力访问后端。若服务缺少所需能力，先列出缺口并确定归属，不偷偷增加接口或虚构数据。
- 错误、连接状态和任务状态如实呈现；凭据不暴露给页面，不允许任意地址代理或任意文件访问。
- 中文、键盘可用、焦点清楚，窄屏能操作；不以营销页或装饰性大盘替代任务工作台。
- 本次不加入文件上传、本机文件导入、业务执行器开发或生产运维管理；不影响其他会话、工作树或既有服务。

## 5. 已知但尚未决定的细节

这些不靠猜测补齐，也不用于悄悄缩减上面的需求：

| 事项 | 接下来怎样处理 |
| --- | --- |
| 类型与 schema 发现、资产管理的能力补充归属 | 本轮调研已确认缺少公开发现及资产管理接口；任务级调度关联已有，完整资源视图仍不足。见调研中的能力矩阵，再确认补充归属与实施安排 |
| 同机收藏保存多久、放哪里，历史任务从哪里获取 | 已确定收藏不需要账号体系或跨设备同步；细化保存与历史范围，不先限制为当前页面 |
| 收藏对应 Endpoint 如何识别，配置变更或原目标不可用时怎么办 | 已确定收藏须记住目标；细化目标绑定与失效处理，不静默改投其他服务，不保存后端凭据到收藏 |
| 在用缓存能否清理、清理前怎样核对 | 与资产所有者能力一起确定，实施前补充安全的可验证规则 |
| 收藏/历史任务引用变化地址时，使用原版本还是重新解析 | 调研确认新请求可重新解析变化地址，而恢复旧任务使用精确 Prepared；需决定再发语义及所需版本证据，不把“再发”说成环境完整复现 |
| 关键过程的具体名称、表单支持哪些复杂输入 | 对照真实协议与任务类型补齐例子，不让用户凭记忆定义已有协议 |

## 6. 后续工作怎么推进

需求确认后，先核实能力缺口，细化近期故事，再按能亲手试用的完整流程安排迭代；不是先写完所有后端再做页面。

分析师的初步建议是：先打通单任务闭环，再打通多任务调度实验，然后完善资产与复用流程。这只是排序建议，不是已确认的排期、工期或首版删减方案。

本次请确认：以上是否准确表达你要的任务操作面板，是否有误解或遗漏。确认的是这份需求基线，不代表功能已经实现或验收通过；未决细节仍会在相应故事开始前继续确认。
