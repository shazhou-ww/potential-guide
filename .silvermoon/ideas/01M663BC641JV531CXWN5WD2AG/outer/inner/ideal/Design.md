# 任务操作面板：交互设计

版本：接口对齐 v0.4，2026-10-31。基于首版需求及[最终接口核对](Research.md#当前接口核对)；草图仍是虚构样本，不代表 UI 已实现或验收。

这是 [Idea.md](Idea.md) 的交互讨论附件，不是实施契约或完整 UI 验收。下面明确区分已确认方向与 Agent 的设计细化。配套[离线草图](Wireframe.html)只展示虚构样本：导航和详情可展开，所有任务操作禁用，不连接服务、不保存数据、不执行清理。

## 1. 设计主张

**一个 Endpoint 下，以“统一提交任务栏 → Task → 关联 Execution”为清晰分区；历史查询与本次观察明确分开。**

首版保留：单条提交为主，多条按序发送且单条失败继续；观察真实事实；收藏与历史重做套用原参数；历史覆盖 Endpoint，由 Service 管理保留与清理。用户已移出资产浏览、版本选择器与缓存清理，不再把它们作为通用 Engine/Web UI 的职责或前置依赖。

2026-10-31 用户反馈已确定：

- **D-01**：提交内容、Task 与 Execution 分开成块，通过关联标识连接；替代第一版 C-01 将任务对照和执行摘要混放的组织方式。
- **D-02**：任务栏始终存在。直接提交是快捷创建一个单任务栏/批次并立即发送，和多条提交共用流程，而不是绕过任务栏的另一套逻辑。“任务栏”沿用此前“任务篮”的待发送集合含义，不是操作系统任务栏。
- **D-03**：首版不提供资产管理，也不要求所有 Task 提供统一资产能力。未来具体类型的独立工具 UX 仅作为可能方向，不预先设计插件、工具槽位或新的通用抽象。
- **D-04**：历史时间筛选采用 receivedAt（服务接收时间），已由独立[历史查询讨论](../../../../01M66TPNEMSQ8Y8SDSN2CDN6BA/outer/inner/ideal/Research.md)确认并发布至 primary；替代原 C-04 候选，不以预约、开始或结束时间改变任务归属。
- UX 细节由 Agent 以逻辑清楚为准自行收敛，不再逐项请求草图选择；用户待真实产品可用后再反馈不顺手之处。这不等于构想 gate 接受、实施或发布授权。

以下保留为 Agent 的设计细化，不需要本轮逐项审阅；若影响需求边界再单独说明：

- **C-02**：任务栏中的草稿/批次按 Endpoint 分区；快捷单条新建独立批次，不清空或发送已有多条草稿。切换目标不搬运或提交原目标的草稿。
- **C-03**：收藏默认按 Endpoint 分组；目标不匹配时先明确切换到原目标，不静默改投当前目标。

本轮不选前端框架、数据库、路由名称或视觉品牌，不设计账号体系、治理控制台或高级 Input 查询语言。

## 2. 页面与入口

| 入口 | 主要内容 | 不应被误解为 |
| --- | --- | --- |
| 工作台 | 清晰分开的提交任务栏、Task 区、Execution 区；每个实体区有自身列表、详情和事实 | Endpoint 全量任务目录，或全服务器资源大盘 |
| 创建面板 | 类型发现、仅按 Task 输入 Schema 提供字段/对象编辑；单条快捷提交或加入多条待发送集合 | 资产解析入口、写死 Check 的专用界面，或强迫手动入栏再发送 |
| 常驻提交任务栏 | 各 UI 提交批次的草稿、次序及逐条回执；快捷单条同样留有回执 | 服务端 Task/Execution、新的后端 Batch 实体或原子事务 |
| 历史 | Endpoint 可访问且仍保留的全部任务；类型/时间查询、分页、详情和重做 | 浏览器记住的任务，或默认永久保存的本机历史 |
| 收藏 | 同机保存的完整任务配方和 Endpoint；直接再发、编辑后再发 | 上次执行快照、账号云同步或自动锁版工具 |

所有真实操作持续显示目标；任务身份、事件 cursor、请求重试和回执均绑定原 Endpoint。收藏或草稿原目标不可用时展示原因，不能自动使用当前目标。Endpoint 的稳定标识与配置变更规则仍待收敛。

“本次观察集合”仅用于整理正在看的任务：提交成功后自动加入，从历史打开任务也可加入。离开页面不取消任务；重启后是否恢复观察集合尚未决定，不能将此集合当作历史来源。

三个区块各自回答一个问题：

1. **提交任务栏：准备发什么、提交是否成功。** 草稿和提交回执在此，不把网络提交中当作 Task 正在运行。
2. **Task 区：某个任务现在怎样。** 展示该 Task 的阶段、取消、超时、输入/结果及任务事件；取消操作只针对这里明确选中的 Task。
3. **Execution 区：关联的实际执行发生了什么。** 展示 executionId、开始/结束、progress 与回收事实及已观察的 Task 关联；不提供未提出的“取消 Execution”操作。

同一 Task 可链接到 Execution；多个 Task 可指向同一 Execution。Task 区只保留关联入口，不嵌入执行生命周期卡片；Execution 区不以其中一个 Task 的取消状态代表整个执行。完整公开事件仍可查看，但按事件所属对象明确分组。

## 3. 四条完整流程

### A. 日常单条提交

选择已配置 Endpoint → 发现类型 → 填写输入 → 快捷创建单条提交批次并发送 → 在任务栏取得回执 → 取得 Task 身份 → 在 Task 区观察并按需关联 Execution。

1. 日常主按钮是“提交任务”，它自动创建只含当前输入的单条批次并调用统一发送流程；次要入口是“加入任务栏”以便手动组合多条。用户无需额外手动入栏或二次确认发送。
2. 表单区分通用请求参数与类型输入，只消费 Task 公开输入 Schema。若其中的 subject 仅声明为 object，则提供通用对象编辑，不根据 URL 下载制品、读取 manifest 或猜测具体业务字段；如果 Schema 本身描述了嵌套属性，则照常生成相应字段。
3. URL、digest、artifacts 等如存在，仅是用户填写或从模板带入的参数。UI 不提供版本目录、自动解析/固定版本或资产管理动作；参数变化不自动覆盖收藏。
4. 获取不到 Task 输入 Schema 或遇到 renderer 真正不支持的结构，说明具体阻塞并保留输入。普通 object 可用对象字段编辑或局部 JSON 值编辑，不以手写整份任意 JSON 替代所有表单，也不把“缺少制品元数据”当作通用提交的前置阻塞；业务校验仍在原服务边界完成。
5. 收到成功回执后，在任务栏记录 taskId/requestId 并链接 Task 区。确定失败显示原因；响应丢失显示“提交结果未知”，查询或重试同一次提交保留原身份。未知期间不再次触发快捷新建批次来冒充原请求重试。

类型发现已提供 `revision`。新提交使用带引号的 If-Match 表达当前表单契约，412 时保留输入并提示契约变化；它与 Idempotency-Key、业务 digest 各自独立。此前结果未知时，随后收到 412 仍不能证明旧请求未创建，不能自动去掉 guard 或新建身份再发。

单条快捷不复用、清空或发送已有多条待发送草稿；它只是统一任务栏模型的单元素实例。这里的批次是 UI 本地组织概念，不需要新增服务端批量协议。收藏直接再发、历史直接重做也进入同一单条快捷流程；编辑后提交使用同一创建面板。

尚未确认的通用参数应与服务协议一起设计；尤其旧参数含资格时间或 series 时，不擅自改写用户输入，也不复制旧 requestId 充当新任务。

### B. 一次多任务调度实验

按类型准备草稿 → 加入同一 Endpoint 的多条任务栏批次 → 调整提交次序 → 一次发送 → 逐条呈现回执 → 在 Task 区对照已知任务，再通过关联查看 Execution。

栏中草稿发送前不是 Task。发送时逐条提交，不等待前一任务完成；失败或结果未知仍继续后项。发送后分别标为已创建、确定失败、结果未知，不提供会重发成功项的含糊“整批重试”。常驻的是任务栏入口与提交上下文，不要求展开所有历史批次占满屏幕。

对“确定失败”的修改再发和“结果未知”的原请求重试使用不同说明；顺序是提交顺序，不保证服务端执行顺序。多个 Endpoint 不混入一个发送批次是候选 C-02，不是新增跨服务事务需求。

#### 调度观察样例

以下是用于审阅呈现方式的虚构场景，不是执行证据，也不保证任意相同输入都会合并：

| 顺序 | 服务事实或条件 | UI 应表达什么 |
| --- | --- | --- |
| 1 | A、B 满足实际类型/版本、环境、scope、授权、Input 比较及事件时间/接收顺序条件，由服务绑定 E1；C 的输入不同且在等待资源 | A/B 同一 executionId 及绑定证据，C 为 queued；不以 Prepared 相等或相同结果猜合并 |
| 2 | 用户只取消 B，收到 canceledAt；A 仍拥有 E1 | B 保留阶段事实并另显示已取消，E1 不因 B 被取消就显示已释放 |
| 3 | C 已超过 deadline，尚未开始执行 | 显示 queued 与超时两个维度；不继续把 C 算作必会启动的有效排队请求 |
| 4 | A 随后完成，E1 稍后产生 reclaimed 事实 | 完成与物理回收分别记录，B 的冻结任务快照不被改写为完成 |

草图工作台截取步骤 3 的状态；它不是交互执行模拟器。

实施前按实际服务契约配置场景。主线 `0d54f74a0efc7a0432b6efb49d487dc2c467db6e` 已引入 `terminated-after-eligible`、接收/匹配事件顺序及 Input 判等语义；不沿用旧 `completed-after-eligible` 或 Prepared 相等作为 UI 的共享判断规则，也不替服务计算新的绑定。

### C. 查询历史并重做

打开历史 → 选类型与时间范围 → 服务端查询/分页 → 打开任务 → 直接重做，或“编辑后重做”进入创建面板。

- 查询覆盖服务端授权与保留范围，不只过滤已经加载的页面；无记录、权限拒绝、功能不支持和网络失败分别呈现。没有列表接口时明确“历史查询能力尚不可用”，不拿本次观察集合填空。
- 时间字段明确标为“服务接收时间（receivedAt）”；映射 createdFrom/createdBefore，含下界不含上界，输入时间必须带明确时区。默认按 created-desc 查询，不伪造总条数、全量状态统计或实时性。
- 目录返回 tasks、observedAt、expiresAt、next；成员、顺序和摘要冻结，页内状态不会因观察时钟推进或另开 SSE 自动变化。详情是独立实时查询，摘要没有业务结果；不能为了表格一列而批量假造或混入详情结果。
- 续页携带原过滤条件，目录游标不与事件 cursor 混用；只有 next 决定是否有后续页。遇到 410/query_expired 提示重新查询，不把新查询第一页追加到旧快照；400、401/403、413、429 分别如实说明，不显示成功的空列表。
- 直接重做与编辑后重做使用同一份原用户参数作为模板；未锁版本仍未锁，已锁仍保留，不使用历史 Prepared 改写输入。
- 新提交身份与原 Task 分开，可展示“由哪个任务重做”的 UI 导航关系，但不暗示服务已有这一溯源字段。
- 原参数来自 GET `/requests/:requestId`，不来自目录摘要；summary.version 是历史绑定，不注入新请求。新的提交可基于当前发现契约检查兼容性，但不静默改写原参数或加业务版本锁。
- 原请求已被清理、无权限或不兼容时显示具体原因，不用空表单假装可原样重做。保留与定期清理由 Service 治理；这里没有历史删除/保留期设置按钮。
- Input 内部参数筛选明确留作后续高级候选，不是本轮基础查询的一部分。

### D. 收藏与参数复用

收藏有“直接再发”和“编辑后再发”两个动作；二者都保留配方中的 URL、锁定信息和目标，编辑派生不自动改收藏。固定 URL 的不变性是来源契约，不靠界面猜路径中是否有版本号。

收藏保存完整类型输入和目标，不预设输入一定含资产。参数中即使有制品引用，通用 UI 也不查询其缓存或可用版本；相关失败由实际服务按原契约返回后如实呈现。保留 URL/锁定信息不等于资产管理。

原资产场景 US-07 至 US-09 已从草图、导航及首版验收中移出。具体业务资产可能由多个 Task 类型共享；其管理和未来专用工具 UX 不在本 UI 中预建。

## 4. 观察面板如何避免误导

| 信息层 | 展示方式 | 判断依据 |
| --- | --- | --- |
| 连接/观察 | 最后成功获取时间、断流/重连/失败及历史缺口提示 | 真实请求与流结果；旧快照不能继续标为实时 |
| 提交任务栏 | 草稿、单/多条批次、逐项提交回执及 Task 入口 | UI 提交意图与真实回执；结果未知不是执行故障 |
| Task | stage、准备/绑定、取消时间、deadline/超时、输入与结果；关联执行入口 | 原始快照及已核实投影语义；取消、超时不是替换 stage 的单一状态 |
| Execution | executionId、开始/结束、绑定、回收事实；列出已观察的关联任务 | 服务事件；只声称已观察的 owners，不假装枚举所有 owner 或 worker |
| 业务结论 | 结果详情，与通用执行故障分开 | 只有有依据的类型解释才显示“业务不满足”；普通类型保留原始结果 |
| 事件 | Task 与 Execution 各自区块中的时间线及完整公开字段；所属对象明确 | sequence/cursor 和公开载荷，不隐藏可获取事件，也不声称包含服务内部隐藏数据 |

历史分页与 SSE 按协议衔接，去重不等于完整性证明。新订阅不会自动获得全部旧事件；回看需读取可用历史。未获得 reclaimed 证据只说明未确认回收，不等于资源一定仍占用。

宽屏在各实体区块内部并排列表与详情；窄屏顺序阅读并可回到列表，Task 与 Execution 仍保持分区，表格只在自身区域滚动。常驻任务栏以紧凑摘要呈现，不遮挡主体和键盘导航目标。按钮与状态都有文字，不只靠颜色；事件详情使用可键盘展开的控件。草图只能验证阅读与导航，真实焦点管理、动态状态通知和交互可访问性需实施后验证。

## 5. 能力依赖与责任边界

| 能力 | 当前证据/归属 | 对设计的约束 |
| --- | --- | --- |
| 提交、已知任务/请求查询、取消、历史事件及 SSE | [当前接口核对](Research.md#当前接口核对)；终结匹配依赖已 completed，客户实际 Endpoint 版本仍需核对 | 可接入闭环，不改内核调度、Input 判等或取消语义 |
| Task 类型及输入契约发现 | [task-type-schema-discovery](../../../../01M66MRFCSDK99MAEN8RN3NKBH/outer/inner/ideal/Idea.md)已 completed；GET `/task-types` 与提交 If-Match 已交付 | 等待前置已满足，本 UI 仍需独立构想决定；不继承其 gate 授权，也不把过期契约失配当作幂等查询 |
| Endpoint 全量历史与类型/时间查询 | [task-history-query](../../../../01M66TPNEMSQ8Y8SDSN2CDN6BA/outer/inner/ideal/Idea.md)已 completed；GET `/tasks`、权限/范围/冻结分页均已交付 | type + receivedAt 的基础入口直接消费真实目录；单独处理 list 权限、query_expired 与最新详情，不退回本机列表 |
| 本机收藏、草稿、观察集合与页面交互 | 本 UI 的职责；收藏须记住 Endpoint，持久化细节待定 | 不读 Task Server 内部数据库；不存后端凭据；不因 Service 历史清理删收藏 |
| 全池/worker 拓扑、全局实时统计 | 尚非已确认需求，缺公开观测能力 | 草图不提供装饰性统计卡或假资源图；如将来确需，另行明确证据与归属 |

原[资产管理讨论](../../../../01M66N2BDVY4B6VAHVEEVB94EW/outer/inner/ideal/Idea.md)仅保留历史记录，不是通用 UI 前置；其生命周期由对应会话维护，本会话不重复操作。Schema 发现不提供资产元数据；未来具体工具另议。

## 6. 需求覆盖与后续反馈方式

| 故事 | 草图/流程覆盖 |
| --- | --- |
| US-01、US-02 | 创建面板：按类型输入、快捷单条批次、统一提交与失败/未知处理 |
| US-03 | 常驻任务栏：草稿、排序、按序发送、逐条回执；不受快捷单条干扰 |
| US-04 至 US-06 | 独立 Task/Execution 区块：多任务对照、各自事实与事件、明确关联和取消对象 |
| US-07 至 US-09 | 已移出首版，不计入本 UI 验收，不预留资产页面或不可用占位入口 |
| US-10 | 收藏：同机/Endpoint 配方、直接和编辑后再发 |
| US-11 | 历史：Endpoint 全量范围、类型/时间筛选、原参数重做、Service 治理边界 |

本轮按用户反馈落实分区和统一任务栏，不再请求用户逐项选择草图布局。其余 UX 由 Agent 在既定需求内保持逻辑清楚，真实产品可用后再由用户反馈具体不顺手之处；需求边界、服务协议或生命周期 gate 的必要决定仍独立处理。

三轮交付范围、前置契约和完成标准集中在[实施计划](../Implementation.md)，本设计不维护第二份排期或执行清单。

这轮交付是构想候选的准备材料。未制作连接真实后端的 UI，未执行功能验收、真实清理或发布；可以对准确候选记录 Agent 的 submitIdeal 供审阅，但不记录用户 accept，不把草图或本轮校验当作下游实现证据。
