# 任务操作面板：第一轮交互设计

版本：候选 v0.1，2026-10-30。基于本 worktree 对齐的 `472d148fff56289e0706f4b72b32df4eb529f0e1` 及[需求确认稿](Requirements.md)。

这是 [Idea.md](Idea.md) 的交互讨论附件，不是实施契约或已经确认的 UI。配套[离线草图](Wireframe.html)只展示虚构样本：导航和详情可展开，所有任务操作禁用，不连接服务、不保存数据、不执行清理。

## 1. 设计主张

**一个 Endpoint 下，以“创建 → 观察 → 复用”为主线；历史查询与本次观察明确分开。**

已确认的需求保持不变：单条提交为主；任务篮按序发送且单条失败继续；观察真实事实；类型资产独立管理；收藏与历史重做套用原参数；历史覆盖 Endpoint，由 Service 管理保留与清理。

以下都是本轮候选，不因出现在草图中就视为用户决定：

- **C-01**：工作台采用任务对照列表与选中任务详情并排布局，创建面板从工作台进入；宽屏同屏，窄屏按顺序展开。
- **C-02**：任务篮与草稿按 Endpoint 分区；切换目标不搬运或提交原目标的草稿。
- **C-03**：收藏默认按 Endpoint 分组；目标不匹配时先明确切换到原目标，不静默改投当前目标。
- **C-04**：历史初版以“提交时间”作为筛选口径候选，界面显式标注；最终需结合用户习惯与服务契约确认，不声称已经选定。

本轮不选前端框架、数据库、路由名称或视觉品牌，不设计账号体系、治理控制台或高级 Input 查询语言。

## 2. 页面与入口

| 入口 | 主要内容 | 不应被误解为 |
| --- | --- | --- |
| 工作台 | 当前 Endpoint、本次观察集合、任务对照、选中任务的事实与事件；新建任务和任务篮入口 | Endpoint 全量任务目录，或全服务器资源大盘 |
| 创建面板 | 类型发现、按类型表单、所选制品 subject 字段、提交与加入任务篮 | 写死 Check 的专用界面，或必须先入篮才能提交 |
| 任务篮 | 未发送草稿、提交次序；发送后的逐条回执 | 已经创建的 Task，或全有全无批量事务 |
| 历史 | Endpoint 可访问且仍保留的全部任务；类型/时间查询、分页、详情和重做 | 浏览器记住的任务，或默认永久保存的本机历史 |
| 收藏 | 同机保存的完整任务配方和 Endpoint；直接再发、编辑后再发 | 上次执行快照、账号云同步或自动锁版工具 |
| 类型资产 | 所属 Endpoint/类型/资产管理范围、缓存及精确版本、使用与受限清理 | 任意文件管理器、远程制品删除或通用 Engine 内核资产表 |

所有真实操作持续显示目标；任务身份、事件 cursor、请求重试和回执均绑定原 Endpoint。收藏或草稿原目标不可用时展示原因，不能自动使用当前目标。Endpoint 的稳定标识与配置变更规则仍待收敛。

“本次观察集合”仅用于整理正在看的任务：提交成功后自动加入，从历史打开任务也可加入。离开页面不取消任务；重启后是否恢复观察集合尚未决定，不能将此集合当作历史来源。

## 3. 四条完整流程

### A. 日常单条提交

选择已配置 Endpoint → 发现类型 → 填写输入 → 直接提交 → 取得 Task 身份 → 在工作台观察。

1. 日常主按钮是“提交任务”，次要入口是“加入任务篮”；不强迫经过任务篮。
2. 表单区分通用请求参数、类型输入及动态 subject 字段。Check/Probe 仅作演示，字段取自相应契约，不按类型名猜测。
3. 选择资产的某个精确版本会把该引用带入草稿；普通 URL 输入不自动固定到上次解析版本。参数变化不自动覆盖收藏。
4. 获取不到 Schema、制品元数据或遇到 renderer 不支持的结构，说明具体阻塞，保留输入；不以伪造字段、空对象或唯一 JSON 编辑框冒充按类型表单完成。
5. 收到成功回执后展示 taskId/requestId 并开始观察。确定失败显示原因；响应丢失显示“提交结果未知”，查询或重试同一次提交保留原身份。未知期间不悄悄把同一草稿改为新提交。

尚未确认的通用参数应与服务协议一起设计；尤其旧参数含资格时间或 series 时，不擅自改写用户输入，也不复制旧 requestId 充当新任务。

### B. 一次多任务调度实验

按类型准备草稿 → 加入同一 Endpoint 任务篮 → 调整提交次序 → 一次发送 → 逐条呈现回执 → 在工作台对照已知任务。

篮中条目发送前不是 Task。发送时逐条提交，不等待前一任务完成；失败或结果未知仍继续后项。发送后分别标为已创建、确定失败、结果未知，不提供会重发成功项的含糊“整篮重试”。

对“确定失败”的修改再发和“结果未知”的原请求重试使用不同说明；顺序是提交顺序，不保证服务端执行顺序。多个 Endpoint 不混入一个发送批次是候选 C-02，不是新增跨服务事务需求。

#### 调度观察样例

以下是用于审阅呈现方式的虚构场景，不是执行证据，也不保证任意相同输入都会合并：

| 顺序 | 服务事实或条件 | UI 应表达什么 |
| --- | --- | --- |
| 1 | A、B 满足实际输入、Prepared、scope、环境与时间匹配条件，绑定 E1；C 的输入不同且在等待资源 | A/B 同一 executionId 及绑定证据，C 为 queued；不从相同结果猜合并 |
| 2 | 用户只取消 B，收到 canceledAt；A 仍拥有 E1 | B 保留阶段事实并另显示已取消，E1 不因 B 被取消就显示已释放 |
| 3 | C 已超过 deadline，尚未开始执行 | 显示 queued 与超时两个维度；不继续把 C 算作必会启动的有效排队请求 |
| 4 | A 随后完成，E1 稍后产生 reclaimed 事实 | 完成与物理回收分别记录，B 的冻结任务快照不被改写为完成 |

草图工作台截取步骤 3 的状态；它不是交互执行模拟器。

### C. 查询历史并重做

打开历史 → 选类型与时间范围 → 服务端查询/分页 → 打开任务 → 直接重做，或“编辑后重做”进入创建面板。

- 查询覆盖服务端授权与保留范围，不只过滤已经加载的页面；无记录、权限拒绝、功能不支持和网络失败分别呈现。没有列表接口时明确“历史查询能力尚不可用”，不拿本次观察集合填空。
- 时间字段有明确标签；草图使用“提交时间（候选）”，不是已经确定的规则。列表和分页不伪造总条数、全量状态统计或实时性。
- 直接重做与编辑后重做使用同一份原用户参数作为模板；未锁版本仍未锁，已锁仍保留，不使用历史 Prepared 改写输入。
- 新提交身份与原 Task 分开，可展示“由哪个任务重做”的 UI 导航关系，但不暗示服务已有这一溯源字段。
- 原请求已被清理、无权限或不兼容时显示具体原因，不用空表单假装可原样重做。保留与定期清理由 Service 治理；这里没有历史删除/保留期设置按钮。
- Input 内部参数筛选明确留作后续高级候选，不是本轮基础查询的一部分。

### D. 收藏与资产

收藏有“直接再发”和“编辑后再发”两个动作；二者都保留配方中的 URL、锁定信息和目标，编辑派生不自动改收藏。固定 URL 的不变性是来源契约，不靠界面猜路径中是否有版本号。

资产入口显示明确的类型与管理范围。选中历史精确版本 → 带引用创建任务；不能把“可见版本”直接当作“当前可用且有权使用”，实际不可用时应明确失败。

清理候选交互是先列出选中标识、目标环境及保护信息，再由用户显式确认，资产所有者返回逐项结果。确认界面只是意图核对，不是无竞态安全保证；最终在用/并发保护在资产侧。本轮不定义自动清理、目录布局或“旧版本”的自动判定算法。

资产独立 idea 已记录磁盘持久缓存目标；UI 不再把服务重启视为必然丢失缓存，但也不承诺已清理、从未缓存或未授权的任意旧版本都可取得。

## 4. 观察面板如何避免误导

| 信息层 | 展示方式 | 判断依据 |
| --- | --- | --- |
| 连接/观察 | 最后成功获取时间、断流/重连/失败及历史缺口提示 | 真实请求与流结果；旧快照不能继续标为实时 |
| Task | stage、准备/分配/执行起止、取消时间、deadline/超时、输入与结果 | 原始快照及已核实投影语义；取消、超时不是替换 stage 的单一状态 |
| Execution | executionId、开始/结束、绑定、回收事实；列出已观察的关联任务 | 服务事件；只声称已观察的 owners，不假装枚举所有 owner 或 worker |
| 业务结论 | 结果详情，与通用执行故障分开 | 只有有依据的类型解释才显示“业务不满足”；普通类型保留原始结果 |
| 事件 | 简短时间线及可展开的完整公开事件；必要时按 Task/Execution 范围看详情 | sequence/cursor 和公开载荷，不声称包含服务内部隐藏数据 |

历史分页与 SSE 按协议衔接，去重不等于完整性证明。新订阅不会自动获得全部旧事件；回看需读取可用历史。未获得 reclaimed 证据只说明未确认回收，不等于资源一定仍占用。

宽屏把对照列表与详情放在一起；窄屏顺序阅读并可回到列表，表格只在自身区域滚动。按钮与状态都有文字，不只靠颜色；事件详情使用可键盘展开的控件。草图只能验证阅读与导航，真实焦点管理、动态状态通知和交互可访问性需实施后验证。

## 5. 能力依赖与责任边界

| 能力 | 当前证据/归属 | 对设计的约束 |
| --- | --- | --- |
| 提交、已知任务/请求查询、取消、历史事件及 SSE | [源码调研](Research.md) E1–E5：现有公开协议；客户实际 Endpoint 版本仍需核对 | 可设计闭环，不改内核调度或取消语义 |
| Task 类型及输入契约发现 | 独立 [task-type-schema-discovery](../../../../01M66MRFCSDK99MAEN8RN3NKBH/outer/inner/ideal/Idea.md)，仍为准备材料 | 类型列表和表单受该契约支撑；草图不是接口已存在的证明 |
| 缓存、精确版本、subject 元数据及清理 | 独立 [task-type-artifact-management](../../../../01M66N2BDVY4B6VAHVEEVB94EW/outer/inner/ideal/Idea.md)，已记录磁盘持久化目标，管理规则待收敛 | 不复制存储/授权/在用保护设计；只消费明确能力 |
| Endpoint 全量历史与类型/时间查询 | 需求已确认，现有路由无此列表；需要独立的通用服务侧工作，尚未在本轮创建新 idea 或 session | 必要依赖，不能退回本机列表；时间口径、分页和可见范围须协商，不预先编造路由 |
| 本机收藏、草稿、观察集合与页面交互 | 本 UI 的职责；收藏须记住 Endpoint，持久化细节待定 | 不读 Task Server 内部数据库；不存后端凭据；不因 Service 历史清理删收藏 |
| 全池/worker 拓扑、全局实时统计 | 尚非已确认需求，缺公开观测能力 | 草图不提供装饰性统计卡或假资源图；如将来确需，另行明确证据与归属 |

## 6. 需求覆盖与审阅焦点

| 故事 | 草图/流程覆盖 |
| --- | --- |
| US-01、US-02 | 创建面板：按类型输入、直接提交、失败/未知处理 |
| US-03 | 任务篮：草稿、排序、按序发送、逐条回执 |
| US-04 至 US-06 | 工作台：多任务对照、独立状态维度、Execution 关联、事件详情 |
| US-07 至 US-09 | 类型资产：范围、版本、带入输入、清理确认与逐项结果 |
| US-10 | 收藏：同机/Endpoint 配方、直接和编辑后再发 |
| US-11 | 历史：Endpoint 全量范围、类型/时间筛选、原参数重做、Service 治理边界 |

首要审阅点是 **C-01 的工作台组织是否符合实际调试习惯**：让创建入口、多个任务对照和选中任务详情靠近，而不是每提交一个任务就离开列表进入单独详情页。其他候选逐项讨论，不一次要求用户决定全部布局、存储和接口。

这轮交付仅为讨论材料。未制作连接真实后端的 UI，未执行功能验收、真实清理或发布；不记录 submit/accept，不把草图和本轮校验当作下游实现证据。
