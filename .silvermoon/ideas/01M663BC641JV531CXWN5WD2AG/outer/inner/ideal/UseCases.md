## 分析与待确认假设

- 分析：产品不应仅被收窄为单任务 HTTP 请求编辑器；调度观察需要理解多个任务与执行资源之间的关系及变化。
- 待确认：客户是否需要同时观察排队、运行、资源占用/释放、执行共享等事实，以及哪些最重要。不能把这些例子直接写成已确认功能。
- 待核实：公开协议能否提供所需调度事实；本轮未核实源码。任务状态不一定能证明资源分配或物理释放，不能以推测图形冒充事实。
- 既有边界：仍只依赖公开协议。若必要事实尚不可得，应将缺口带回讨论，不擅自扩展 Task Server 或混入其他任务类型的实施。
- 当前未知：典型调度实验、观察对象和范围、实时与事后复盘需求、成功判断、使用频率、优先级，以及“168 task”的含义。

### 第二轮：调度实验与观察内容

客户明确提出三个实验方向：

1. 并发与排队：创建多个任务并发，在 executor 并发度有限时观察排队。
2. 合并执行：可合并的任务合并执行。
3. 生命周期管理：取消等各种生命周期管理。

客户明确希望看到：

> 这个任务的当前stage的变化。

> 关键过程：看这些关键过程的起始和终止。

> 进度事件：查看任务中间的progress events。

> 任务事件详情：任务所有的events都可以去查看它的详情。

这是观察内容的需求表达，不是对现有协议事件覆盖范围的核验，也不表示每个关键过程都有独立 stage。

客户说明：任务发起需要提供 input，每个 Server 注册的是确定的几种任务。客户不确定服务是否已有注册类型与 schema 的元数据发现能力，认为可能尚未提供；这不是对现有源码的核验结论。

客户明确需求：

> 按类型生成表单：按照不同类型的任务input，给出相应的填写form。

> 元数据发现：看看都注册了哪些任务、它们的schema分别是什么样的——这个可能是一个需要补的能力。

| ID | 客户明确表达的需要 | 尚待确认 |
| --- | --- | --- |
| R-09 | 按不同任务类型的 input 提供相应填写表单 | 所需 schema 表达能力、字段说明与校验、复杂输入及使用引导待细化；不把手写 JSON 作为唯一入口 |
| R-10 | 发现目标 Server 注册的任务类型及各自 schema | 现有公开协议是否支持待核实；若缺失，需要另行明确服务侧能力补充的归属和契约，不擅自扩展后端 |

分析：类型来自各 Server 的实际注册，UI 不应硬编码 Check/Probe 或预设所有 Server 具有同一组类型。表单生成依赖可信的输入契约；不能靠任务名猜字段，也不能伪造不存在的元数据接口。

范围影响：此前“仅依赖现有公开协议”的可行性需要核实。客户已提出可能补充元数据发现的需要，但尚未决定接口设计、实施归属或允许修改哪个服务；应显式讨论这个依赖，不把它藏进 UI 实现，也不自动改变其他 idea。

尚未确定：是否需要查看原始 schema、是否保留 JSON 编辑/预览入口、表单引导程度，以及一份 input 如何复用为多次提交。此前 UC-02 的 JSON 编辑只是候选，不覆盖客户已提出的按类型表单需求。

| ID | 客户明确表达的需要 | 尚待确认 |

分析：加入集合只是准备请求，不应自动等同于后端已经创建 Task；客户描述了“加入后统一发送”的工作流。以“待发送任务篮”作为暂用术语，区分草稿与服务端任务。

需求澄清点：购物车式批量不是简单指定同一 input 的重复次数。不同条目可按类型准备，但客户尚未明确混合类型批次的具体限制；不能据此推导新的后端批量接口。

下一轮聚焦排序语义：客户调整顺序是为了方便组织请求、控制提交先后，还是希望影响实际执行先后；如有调度期望，需再区分观察与控制。

### 第五轮：排序只控制提交顺序

客户原话：

> 对，就只是提交顺序，执行的话还是由这个server来调度的，里面的优先级啊什么的也是会影响实际的调度顺序的。

确认：任务篮顺序只表达提交先后；实际执行顺序仍由 Server 调度，可能受优先级等因素影响。UI 不应串行等待一个任务完成后才提交下一个，也不保证按列表顺序开始或完成执行。

客户提及优先级是解释服务调度行为，不等于已经要求新增优先级控制组件或更改 Server 调度策略。如何保证实际提交先后而不混淆点击顺序、发起顺序与服务端接收事实，属于后续协议与交互设计问题。

接下来待访谈：批量提交中部分失败或响应未知时的期望，以及任务创建后如何在面板里观察、选择与操作。暂不为这些问题代填答案。

| R-15 | 批量中某一条提交失败，继续后续条目的提交 | 不增加失败暂停、整批回滚、要求人工处理后才能继续等特殊流程 |

分析：无需设计复杂的批量事务或异常编排功能。仍应如实显示各条提交结果；继续后续提交不表示将失败伪装成成功，也不意味着自动重试失败条目。网络响应丢失时，该条能否确认创建属于结果准确性问题，不应借此强加阻塞整批的流程。

### 第七轮：任务类型资产、收藏与历史重做

客户说明这些场景的实现方式尚未想好，先提出需求：

> 它们不属于通用task server自身要观察管理的范畴，而是具体某一个任务类型下面管理的一些全局资产；现在比如说缓存了哪些、版本是怎样。

> 对于我常用的一些任务，比如做regulation时的artifacts、subject，我应该可以把它收藏起来，直接点一下就可以让它重新发一个任务出去，一键可发；而且对于以前历史上做过的一些任务，也可以让它重做。

| ID | 客户明确表达的需要 | 尚待确认 |
| --- | --- | --- |
| R-16 | 有地方查看 Check 相关 Checker、Objective artifacts 的缓存资产、已缓存内容及版本 | 第八轮补充历史版本选择与旧缓存清理；资产所属实例/范围、可用接口与信息粒度待核实，不推断上传或下载管理 |
| R-17 | 收藏完整 artifacts 与 subject，之后原样一键重新发起任务 | 内容经第九轮确认；保存位置、保留时间、目标绑定及版本解析语义仍未决定，不沿用“仅当前页面会话”作为限制 |
| R-18 | 对以前历史上做过的任务进行重做 | 历史来源、可检索范围、是否允许编辑后重做，以及原版本复用语义待确认；不假装已有服务器全量任务历史接口 |

职责边界：R-16 指向具体任务类型管理的全局资产，不是每个 Task 的局部状态，也不是通用 Task Server 天然负责的管理面。尚未决定如何接入或扩展，不能因此在通用内核中硬编码 Checker/Objective 资产能力。

分析：R-17 的一键再发和 R-18 的重做是再次发起任务的使用意图，应与网络故障后重试同一次提交、查询旧结果、恢复旧执行相区分。新提交身份及幂等键处理是后续正确性设计，不应让“重做”意外仅返回旧任务；是否可合并复用执行仍遵守 Server 语义，不承诺每次都产生独立物理执行。

版本问题待确认：收藏或历史请求可能引用固定 artifact 版本，也可能引用会变化的地址。客户尚未选择“固定原版本”或“重新解析当前版本”，不能承诺可重复执行等同于原环境复现。

Agent 候选方向：界面可以区分通用任务操作与按类型提供的资产入口；这只是职责分离建议，不是已选定插件架构、服务拆分或首版范围。

下一轮先采访 R-16 的目的：看到缓存内容与版本后，客户想做什么判断或操作。收藏的持久化、版本语义和历史范围另行追问，不一次堆成技术问卷。

### 第八轮：选历史 artifact 运行与手动清理缓存

客户原话：

> 指定用某一个历史版本的artifacts去跑一个特定的任务。

> trigger手动清理缓存，删掉一些本地标的一些旧的缓存artifacts。

| ID | 客户明确表达的需要 | 尚待确认 |
| --- | --- | --- |
| R-19 | 选择一个历史版本的 artifacts 来运行指定任务 | 历史版本从哪些来源列出、以何种精确标识绑定、与任务表单如何关联待设计；不能静默换成最新版本 |
| R-20 | 手动触发清理，删除一些旧的本地缓存 artifacts | 选择单项/批量的方式、在用资产的保护和清理结果呈现待澄清；不等于任意文件删除、自动淘汰策略或删除远程制品 |

分析：R-19 是主动选择历史资产版本后发起任务，与从某次历史任务取回请求再重做是两个入口；可有交集，但不能相互代替。选定历史 artifact 并不保证 Node/运行环境也完全回到历史状态。

边界：这里的“本地缓存”指资产管理服务所在环境中的缓存候选，不推断为浏览器电脑文件。具体缓存归属、服务与访问接口尚未核实；清理应通过资产所有者的受限能力，不能据此开放任意路径或文件系统访问。

待澄清：运行中或已准备任务可能仍引用缓存。删除缓存是否允许、由谁判断可删除、如何显示受保护条目均未决；本轮没有授权实际清理或修改其他会话资源。

### 第九轮：收藏原样再发与模板修改

客户原话：

> 包含完整的artifacts加subject就可以了。

> 可以支持一键再发，也可以以它为模板创建新的，修改后再发，比如说修改一下subject再发。

确认两条使用路径：

1. 收藏保留完整 artifacts 与 subject，直接原样一键再发。
2. 以收藏为模板创建新任务，修改内容（例如 subject）后再发。

| ID | 客户明确表达的需要 | 边界 |
| --- | --- | --- |
| R-21 | 从收藏创建新的任务草稿，修改后再发 | 是从收藏派生新的任务输入，不等于自动修改原收藏；是否提供编辑收藏功能尚未讨论 |

分析：收藏既是可直接使用的任务配方，也是新任务的起点；只收藏资产标识、不保留 subject，不能满足此需求。客户没有要求额外保存完整执行状态、事件或结果，也没有要求复制所有生命周期/调度参数。

仍未决：收藏如何命名、保存在哪里、是否跨页面/服务重启保留，历史任务从哪里获取，以及引用的资产版本如何固定。此轮明确了收藏内容与两个动作，不自动解决这些存储或版本问题。

## 后续访谈方法

- 每轮只围绕一个主题，用一至两个开放问题追问具体经历，不让客户先选择预设功能。
- 先了解目标、现有做法与困难，再了解频率、影响、协作对象和成功标志；根据客户回答选择下一问，不机械发完整问卷。
- 听到具体场景后，区分客户原话与分析师解释，复述“谁在什么情况下，为了什么，要达成什么”，请客户纠正。
- 客户难以表达时，可提供少量对比场景或方案启发，但明确标为建议，保留“都不是”和新增解释的空间。
- 只有形成真实用例后，才讨论主流程、异常、信息需求、优先级及非目标，再讨论 UI、连接和部署选择。
- 每轮更新本文件：客户原话/事实、分析解释、待确认假设、未决问题。没有回答不产生需求结论；没有明确同意不改变 gate。

以下保留早先分析，供后续对照与选择，不作为已经采集完成的需求。

## 候选定位与参与者

面向开发者的可选任务调试工作台，不是营销页面、任务管理后台或 Check 专用页面。核心流程为提交请求、观察执行、检查结果、定位异常。

| 参与者 | 目标 | 边界 |
| --- | --- | --- |
| 调试开发者 | 提交通用任务并排障 | 只能操作所选目标下获准访问的资源 |
| UI 部署者 | 配置目标与凭据、控制 UI 访问 | 后端配置来自可信启动环境，不由浏览器指定 |
| Task Server / 执行器开发者 | 验证新类型及协议行为 | 新业务类型不应要求修改 UI |

不预设团队管理员、审批者或普通业务用户，不据此扩张管理功能。

## 前序任务描述中的边界

以下来自前序任务描述，不是本轮访谈新增结论。实现授权仍未取得；需求讨论可显式修订范围，但不能把未回答视为取消安全约束。

- Web UI Server 与 Task Engine Server 是不同服务，独立监听、启动和退出。后端无需 UI；UI 不内嵌或启动 TaskEngine。
- 仅依赖通用 Task Server 公开协议，不抢占 Probe 的工作范围，不硬编码 check-only host 或业务 type。
- UI 关闭、浏览器断开和事件流结束不取消任务。取消必须是针对明确 endpoint 与 Task 的显式操作。
- 无全量任务列表协议时，不假装提供全局列表。可以展示明确标注的本次浏览器已知任务。
- 不内置 Checker 执行器，不增加上传或本机文件导入；`file:` 指向后端所在主机，不是浏览器电脑。
- 不搬入其他会话的未提交工作，不改变原 checkout、Check/Probe 工作树或运行进程，不发布 npm 包。

## 候选用例清单

下表为 Agent 提议的能力清单；R-01、R-02 是客户目标，不等于对表中具体交互的确认。各能力与真实实验的对应关系、必要程度和优先级仍待访谈，不默认全部进入首版。

| ID | 用户目标与主流程 | 异常与必须保留的语义 |
| --- | --- | --- |
| UC-01 | 选择配置好的 endpoint，查看连接信息 | 浏览器不能指定任意代理地址；切换后旧目标的响应、任务和事件不能混入当前目标 |
| UC-02 | 编辑任意类型 JSON Task 并提交，获取标识 | JSON 语法正确不等于请求被后端接受；校验、鉴权与服务端错误明确显示 |
| UC-03 | 提交超时或响应丢失后安全重试 | 同一逻辑提交保留 Idempotency-Key；重复点击、重试原请求、创建新任务可区分；结果未知不是确定失败 |
| UC-04 | 按已知 Task ID 或 Request ID 查询原始请求、快照、结果和故障 | 两类 ID 不混淆；按协议区分未找到、拒绝访问及连接失败，不推测服务端隐藏的信息 |
| UC-05 | 观察任务快照与事实事件时间线 | 连接、事件流、任务状态分开；stage、canceledAt、timeout 等独立维度保留 |
| UC-06 | 按 taskId / executionId / seriesId 查询历史并分页 | 查询范围可见，保留原始事件及 sequence；无记录、查询失败和历史过期不混淆 |
| UC-07 | 从已有 cursor 恢复断开的事件流 | 在正确目标与范围内去重；history_expired 与历史缺口明确呈现，不静默跳到最新假装连续 |
| UC-08 | 核对当前目标与 Task 后主动取消，再查看实际状态 | 请求被接受不等于任务已停止；处理已完成、取消与完成竞态、权限不足及请求结果未知 |
| UC-09 | 返回当前浏览器已知的任务继续调试 | 明确标为本次浏览器已知任务，不宣称完整或等同服务器全局列表 |
| UC-10 | 启动 UI 接入现有后端，结束后关闭 UI | 只释放 UI 自己拥有的连接与资源，不取消任务或关闭后端 |
| UC-11 | 观察多个任务与执行资源的分配及边界操作后的变化 | 对应 R-02；实验、范围与展示形式待访谈；只展示协议能够证明的事实，不从任务状态推断实际资源已释放 |
| UC-12 | 发现所选 Server 注册的任务类型及 input schema，按类型填写表单发起任务 | 对应 R-09、R-10；具体交互待讨论，发现协议与 schema 表达范围待核实；不能以硬编码类型或猜测字段替代发现 |
| UC-13 | 偶尔按类型逐个加入待发送任务篮，调整提交顺序后一次点击发送；单条失败继续后续提交 | 对应 R-11 至 R-15；日常可直接单条提交；草稿不等于后端任务，Server 决定执行顺序，不暗示原子批量 |
| UC-14 | 查看具体任务类型下的全局资产缓存及版本，选择历史版本发起任务，手动清理旧缓存 | 对应 R-16、R-19、R-20；通用内核不承担业务资产职责；在用资产保护、范围和管理接口待澄清 |
| UC-15 | 收藏完整 artifacts 与 subject，原样一键再发，或以收藏作模板修改后发起新任务 | 对应 R-17、R-21；持久化、目标及版本绑定待确认，模板派生不自动修改原收藏；与重试同一次提交区分 |
| UC-16 | 从历史任务再次发起任务 | 对应 R-18；历史来源、查询范围及输入/版本复用待确认；不承诺全局枚举或旧执行恢复 |

## 候选风险分析

### 提交结果未知与请求修改

响应丢失时任务可能已经创建。保留原请求及幂等键供重试，显示“提交结果尚未确认”，不能自动生成新键再次提交。修改请求后，不应无意识地沿用旧提交身份；键生成、锁定、编辑与新建的具体交互仍需讨论。

### 业务否定结果不是执行故障

`completed` 加上 Check 结果 `ok: false` 可以是正常业务结论。分别显示执行状态、取消/超时信息、结果与故障，不把任意业务字段映射成通用执行失败。

### 后端失联与旧数据

保留旧快照供排障，同时标明最后获取时间和错误，不暗示它仍为实时数据。恢复连接不自动重提任务；不存在独立探活协议时，不虚构“连接正常”的证据。

### 目标切换与迟到响应

释放旧目标的观察连接，隔离迟到响应。取消、重试、cursor 与去重状态绑定正确目标及范围；不能仅依靠当前界面选中的名称决定操作归属。

### 历史与实时流交接

分页与订阅交接依赖协议的 cursor/sequence 语义。去重不能代替完整性证明；协议无法证明连续或历史已经过期时，应显式提示缺口。

## 安全与资源要求

- 默认 loopback；非 loopback 暴露应明确要求认证配置或拒绝。UI Server 是特权代理，需处理 Host、Origin、跨站修改请求及访问控制。
- 后端地址和凭据只来自可信启动配置；浏览器仅选择不含秘密的 endpoint ID。不将 token 放入 URL、前端 bundle、localStorage、日志或仓库。
- 代理限制路径、方法、请求头和重定向，防止任意 URL/端口代理、SSRF、凭据泄露及跨 endpoint 混用。
- 请求体、并发连接、流数量与超时受限；SSE 不无限缓冲。浏览器断开释放代理流而不取消任务，UI 退出及时关闭本服务拥有的连接。
- 采用能携带鉴权的 fetch 流，不将 token 塞到 EventSource query。
- 错误显式呈现，不吞掉错误、不返回伪装成成功的默认结果。资源数值和认证机制留待方案讨论，不假装已确定。

## 候选方案与未决取舍

以下是 Agent 建议，不是用户已接受的设计。

| 议题 | 当前候选 | 尚需讨论的取舍 |
| --- | --- | --- |
| 服务组织 | 独立应用置于 `apps`，提供静态前端及受限 HTTP/SSE 代理，使用启动配置的目标列表 | 是否采用此部署与连接方式；不提前修改 workspace |
| 工作流中心 | 早期单任务调试候选需结合已采集的多任务观察、类型资产与收藏需求调整 | 如何组织这些入口，不提前决定页面或扩展架构 |
| 调试记录生命周期 | 早期“仅当前页面会话”建议不能作为收藏与历史重做的既定限制 | 收藏保存位置、保留时间、历史来源及允许保存的内容仍待采访 |
| 暴露范围 | 优先本机调试；未配置认证时禁止非 loopback 暴露 | 远程访问是否首版交付，UI 身份与后端 caller 如何关联 |
| 提交身份 | 原请求重试保留键，新逻辑提交使用新键 | 手工指定键、修改请求、新建任务的交互和冲突提示 |
| 首版范围 | 综合已采集的 R-01 至 R-21 及候选用例讨论，不沿用早期 UC-01 至 UC-10 清单作为默认范围 | 哪些用例必须首版交付，具体 UI 契约尚未定稿 |

共享后端凭据不等于多用户授权；不能宣称用户隔离而实际只映射为同一 caller。

## 候选界面方向

以请求编辑、可读快照、事实时间线为核心，连接/流/任务状态清晰分离。中文、键盘焦点明确、可访问表单、窄屏可用；避免装饰性 dashboard，不依赖外部 CDN 或字体。

布局、配色、字体和交互原型尚未决定。明确用例取舍后，再按 frontend-design 做简短设计方案并讨论，不把视觉建议倒推成需求。

## 协议依据与待核实项

当前只阅读了[任务服务文档](../../../../../../docs/task-server.md)，基于本工作树更新到的主线 `8b7d48a2f1f44889c043a54bafa026af1dad3c71`；这不是对最新发布包的核验。

文档包含 `startTaskServer`、CLI、`POST /tasks` 与 Idempotency-Key、`GET /tasks/:id`、取消、history、SSE 与 Last-Event-ID；创建返回 202，断开连接不取消 Task。鉴权包括每请求 resolveCaller 与每操作/stream pull authorize。

实施前仍需核实实际路由、Request ID 查询返回形状、JSON Task 契约、execution/series 查询、分页与 cursor 语义、错误状态和最新发布提交。不得仅依据讨论稿编造协议，也不为 UI 擅自扩充后端路由。

## 候选验证场景

- 两个真实独立进程、不同端口；无 UI 时后端可运行，停止 UI 后任务继续。
- 真实服务覆盖提交、同键重试、查询、取消、历史分页、SSE、重连、后端断连及错误；新通用任务类型无需修改 UI。
- 正常业务否定结果不误标执行故障；历史过期、缺口和陈旧快照明确可见。
- 目标切换不串数据或操作；地址与凭据不能被浏览器任意控制，访问及资源边界有效。
- 获准实施后完成相关测试、pnpm check、浏览器实测与截图检查；验证资源明确拥有并清理，不干扰其他会话。
