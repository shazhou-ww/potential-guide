# Implementation

准备阶段的轻量种子，可随讨论调整；不是开工授权。需求见[构想](ideal/Idea.md)及[需求确认稿](ideal/Requirements.md)。

## Steps

### I-S01: 核实协议与交互边界

获准实施后核对实际公开协议、最新发布提交与现有前端工具，列明类型/schema 发现、调度事实、资产及 Endpoint 全量历史查询能力缺口，确定归属；历史保留/清理归 Service 配置治理。补齐近期故事的未决规则，给出简短设计与迭代建议后再实施。

### I-S02: 实现独立调试闭环

按已确认范围逐步实现独立 UI、受限连接边界、统一任务栏的单/多条提交、清晰分区的 Task/Execution 观察、类型资产入口、收藏、Endpoint 历史查询与原参数重做；遵循已有工程约定，不引入业务专用执行器，不擅自扩展通用内核或缩减需求。

### I-S03: 验证行为并更新文档

补充直接相关测试与使用文档，运行 pnpm check，验证接口、错误、可访问性和资源回收边界，不修改无关包。

## Acceptance criteria

### I-AC01: 通用任务操作正确

以测试证明需求确认稿 US-01 至 US-11 及补齐规则符合实际协议；单条快捷与多条复用提交流程且不互相误发，提交/再发身份正确；Task 与 Execution 的事实和操作分区明确，排队、合并和生命周期可观察，资产操作与收藏有效。历史包含其他客户端提交的获授权且仍保留的任务，直接/编辑后重做遵守原参数及锁版本规则；业务否定结果不误标系统故障，类型表单不靠硬编码业务输入。

### I-AC02: 访问与资源边界有效

以边界及失败路径测试证明目标隔离、凭据保护、访问控制、受限代理和断连清理有效，不以断流取消后端任务。

### I-AC03: 工程质量可复核

pnpm check 通过；直接相关文档和测试对应候选行为，记录真实结果而非将未执行项标为完成。
