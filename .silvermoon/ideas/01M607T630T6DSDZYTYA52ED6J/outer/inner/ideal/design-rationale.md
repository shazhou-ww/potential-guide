# Check 制品的设计逻辑

## 为什么独立于 npm 和源码仓库

自包含 worker 解决的是运行时依赖封闭问题；npm 解决的是某种包生态的安装和分发问题，Git 保存的是可审查的源码历史。三者不是同一个约束。

源码、原始 References、构建配置和必要的依赖锁定信息仍入 Git；构建产物作为压缩包交付，不作为源码提交。GitHub Release asset 是首选分发渠道，但制品本身不能绑定 GitHub，也不需要 registry。

当前[打包设计](../../../../../../docs/pilot-packages.md)已经不要求生成 worker 入库，但仍采用 npm Objective 包。本文是后续演进目标，不宣称新格式已经实现。

## 制品包含什么

Check 制品包含自己的 manifest、自包含 JavaScript worker、显式运行资源及 `references/`。manifest 需要说明格式、稳定身份、入口、输入/结果契约及可报告的 problems；具体字段留到实施阶段结合现有协议确定。

References 描述 Check 自身和各个 problem 的通用解释、诊断及修复知识；不是执行资源的别名，也不是运行观察。后续 Objective 可以继承并在自己的作用域提供场景化内容。

## 为什么按内容而不是版本范围消费

来源回答“去哪里取”，digest 回答“只允许哪份内容”。可展示的版本号不是解析规则，也不能代替摘要。远程对象被替换时必须拒绝，而不是把新字节解释为同一版本。

压缩包传输摘要、解压后逻辑制品摘要和 Host 执行 revision 可能具有不同覆盖范围，实施时必须明确区分并验证映射，不能混用。References 也属于制品内容；说明变化会改变制品摘要，但不必改变字节未变的 Host 执行内容 revision。

摘要证明内容一致，不证明发布者可信。来源授权、认证、重定向及下载/提取限额应明确，不在日志中暴露凭据，也不能把任意下载代码称作安全沙箱。

## 执行边界不变

制品准备层负责获取、校验、缓存和物化；[Check Host](../../../../../../packages/check-host/README.md)仍只接受规范目录和执行 revision。禁止向任意 `node_modules` 回退，禁止消费时隐式安装依赖或执行构建脚本。

现有私有目录、链接拒绝、完整内容校验、预算、取消和清理约束继续有效。只读缓存不是权限安全的替代品。

## 分步交付

本项证明独立 Check 从构建到执行成立。下一项才负责 Objective 组合、References 覆盖和业务消费；第三项负责内置内容迁移及正式 Release。离线全集导出、镜像和签名体系不是本项前提。
