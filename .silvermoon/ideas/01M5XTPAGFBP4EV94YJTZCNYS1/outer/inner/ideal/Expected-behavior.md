# 预期行为：YAML 状态树与 transition

本文支持 [构想契约](./Idea.md)，描述预期而非已实现功能。
具体形态见 [用例与输出示例](./Examples.md)；字段名、函数签名及脚本名仍是设计示意。

## 1. 当前方案

**固定 YAML 是状态树和说明的唯一来源。** YAML 只指定一个 Binding TS 文件，
按 state/检查 ID 与函数导出名的固定规则关联后，同一数据可以：

- 生成或运行时展开 Node Test 测试。
- 输出终端树和 Markdown。
- 生成可离线查阅的静态 HTML 及人工操作路径。

不再要求人手写另一棵 BDD 树，也不通过包装 describe/it 来执行声明、收集文档。
BDD/hook 只是执行适配的底层机制，不是数据模型中的必需术语。
若生成测试源码，它是只读派生产物，不能手改；也可以直接运行时注册测试。
两种方式在实施阶段选择，不维护两份事实来源。

## 2. 三个概念

| 概念 | 含义 | 人工对应 |
| --- | --- | --- |
| state | 已达到的运行状态，可包含正常或故障状态 | 现在处于什么状态 |
| transition | 从父 state 进入子 state 的副作用函数，返回 after | 怎样进入，以及这一步拥有的资源怎样收尾 |
| state 的检查 | 当前状态上的只读探针，按 ID 绑定函数 | 去哪里看，预期看到什么 |

树上的每条边是一条 transition；每个节点是一种 state。
节点可有多个检查，以及通向不同子状态的转移。
真实服务可能有循环或汇合，这里仅描述有限测试路径，不新增图调度器。

节点 ID 既提供稳定定位，也参与推导对应的函数导出名；无需另外声明 transition ID 或 use。
同一实现可以通过 Binding TS 的导出别名复用到不同 state，各次调用仍独立持有 after。

## 3. transition 的进入与收尾

概念签名：

```ts
type After = () => void | Promise<void>;
type Transition<C> = (context: C) => After | Promise<After>;
```

调用 transition 本身就是 before：执行副作用，并完成必要的状态准入确认。
成功返回的 after 由执行器保存；它用闭包捕获这一步真实拥有的资源。
YAML 中的 before/after 是人工说明，不是另两条可执行函数绑定。

```text
state A
  transition AB：执行进入操作，返回 after AB
state B
  transition BC：执行进入操作，返回 after BC
state C
  当前检查
  after BC
  after AB
```

- after 是资源清理，不是业务状态的逆向转移。
- 无需收尾的 transition 可以显式返回空操作；不虚构恢复到父状态的动作。
- 每次检查重新建立自己的 context 和整条前置路径，兄弟检查不共享可变执行状态。
- 成功拿到 after 后，必须先登记，再执行本 state 的探针或后续 transition。
- after 仅对本次获取的资源负责，不能按进程名清理其他实例或删除未知目录。

## 4. 失败时怎样执行

| 情况 | 预期行为 |
| --- | --- |
| transition 返回前抛错 | 本次不继续进入子状态；该函数自行收尾部分初始化，执行器继续释放祖先已登记的 after |
| state 的检查失败 | 本次记录失败并收尾；兄弟或后代的独立测试仍重新建立自己的路径，不自动整树 Blocked |
| 成功进入预期故障 state | 继续检查故障现象及恢复路径；故障状态不是测试框架失败 |
| 某个 after 失败 | 继续逆序执行剩余 after，同时保留清理错误 |
| 检查失败且清理也失败 | 原始错误与清理错误均可见，不相互覆盖、不报告成功 |
| 平台不适用 | 测试按适配规则跳过；文档保留节点及原因 |

函数尚未返回 after 时，执行器不知道新资源的收尾方式。
因此部分初始化责任必须落实在 transition 及其资源获取 helper 中，
不能假设最外层 after 总能发现并处理这些资源。

在祖先状态上注册的其他检查，不会自动变成后代路径的准入步骤。
必须成立的前置条件应由 transition 确认，并写进它的 before 说明。
自动测试适配应保持 Node Test 原有的测试隔离与失败语义；
本方案明确补充的是返回 after 的资源释放约定，而非失败依赖调度。

## 5. 数据与实现的边界

- YAML 描述 state、检查、进入/收尾说明、平台及必要的声明式选项。
  顶层只写一个 binding 文件路径，不逐项声明函数映射或独立 transition ID，
  不包含 JavaScript 表达式、任意脚本或第二套结构。
- Binding TS 按固定命名导出 transition/检查函数，不需要注册表对象。
  transition 必须返回 after，检查不得用副作用建立后续状态。
- YAML 重复键、重复或歧义节点身份、非法字段、缺失必需说明要明确诊断。
- 自动测试入口在开始副作用之前验证预期导出存在且为函数；错误指明 state、
  预期符号和 Binding TS 路径，不猜测近似名字。
  transition 的返回值只能在调用后确认；未返回 after 应报告契约错误，不悄悄补空操作。
- 文档消费者只读取 YAML，不为了验证导出而导入 Binding TS 或业务实现。
  它可以验证数据结构，但不能假装已经证明运行时绑定存在或测试通过。
- 展示标题可修改，稳定定位不随标题改变；说明中的命令只是文本，不自动执行。

### 固定关联规则

| YAML 定义 | Binding TS 导出 | 职责 |
| --- | --- | --- |
| `state.id: ready` | `transition_ready(context)` | 进入 ready，返回本次 after |
| ready 中 `checks[].id: idle` | `check_ready_idle(context)` | ready 的 idle 探针 |
| ready 的 after 说明 | 不另导出符号 | 对应 transition_ready 返回的闭包 |

根 state 也遵守同一规则，用自己的 transition 建立初始 fixture；
没有进入副作用的 state 也必须显式提供返回空操作的 transition。
state ID 在单份 YAML 内唯一，检查 ID 在所属 state 内唯一。
为避免分隔符和函数名转换歧义，示例约定 ID 仅含 ASCII 字母和数字、以字母开头。
标题可用自然语言，不受这一命名限制。

binding 路径相对于 YAML 文件解析，而非进程工作目录；
它是文件路径，不是可求值的表达式。改 state/检查 ID 就是修改代码绑定契约，
要同步修改导出符号，不能当作单纯改标题。
封装自动调用返回的 after，不再推导独立的 `after_ready` 导出。

所有数据加载、测试适配注册及 Binding TS 导入都应避免提前初始化业务。
文档消费者允许读取 YAML、写入指定文档输出，不得创建 fixture、调用 transition、
执行检查、调用 after 或启动 Host。

## 6. 人工状态操作视图

人工视图展示 state tree，而不是以每个 it 为叶子的测试执行树。
每个 state 只出现一份正文，内容为：

1. 到达路径及如何从父状态进入：给出原始命令或 API 操作。
2. 在此状态观察：看哪里、预期现象是什么、怎样确认已达到状态。
3. 可以继续转向哪些状态：链接下一状态的操作说明。
4. 结束操作与资源释放：真实的关闭/取消/目录删除，不使用 after 作为人类页面标题。

数据层可以保留 before/after 字段及检查 ID；这些是自动化映射与说明存储方式，
不意味着页面要展示测试函数名或重复输出每个探针的 setup/teardown 路径。
旧检查锚点可以继续定位状态内的观察段，主导航只呈现状态。

进入操作和收尾说明与同一 transition 放在一起，避免分别维护两个函数绑定。
人工步骤必须解释失败或部分进入时怎样收尾，不能只覆盖成功路径。
进入后的临时检查、命令参数、fixture 准备、屏障保持及释放方式也必须写清楚；
“调用某个 helper”不是可交付的人工说明。人工操作必须独立于 Test Tree，
不能用手册专用的测试包装器命令来替代服务本身的操作。
服务没有通用 CLI 时，应明确说明限制，使用原始公开 SDK 或 HTTP 接口，
而不是虚构 start/run/cancel 命令。可透明准备演示业务输入，但不能导入测试 fixture/helper。

## 7. 展示与安全边界

- 终端树和 Markdown 清晰显示 state、transition 和检查的关系。
- HTML 提供可折叠状态树、稳定节点定位、到达路径和状态观察；不依赖启动服务。
- 命令块保留格式并方便复制，但打开页面或点击节点不能执行命令。
- 不执行说明中的脚本，不将任意原始 HTML 当作可信页面内容注入。
- 所有操作使用独立场景及自有资源，不连接用户默认 Host，不暴露 bearer token。
- 未运行、平台不适用、说明错误与测试失败分别表达；文档存在不代表验证成功。

## 8. 应验证的代表行为

1. 从同一 YAML 得到一致的自动测试路径与三种文档视图。
2. transition 与 after 计数证明进入为正序、释放为逆序且每次获取只释放一次。
3. 部分进入失败、探针失败、单个 after 失败，都不会跳过其他应执行的清理。
4. HTML 生成不导入 Binding TS，transition、检查和 after 的调用计数均为零。
5. 缺失或非函数导出在执行前明确失败；无效 YAML 在消费入口明确失败。
6. 同一实现通过导出别名复用于不同 state，结果与节点定位仍独立；改标题不改变身份。
7. 预期 worker 故障后仍能走恢复 transition，不因 state 名为 Failed 自动剪枝。
8. 人工命令不导入或调用测试框架、绑定、fixture 或专用手册包装器；
   按说明使用服务公开接口，能够直接进入和观察相应状态。
9. 即使一个 state 有多个检查，页面仍只有一个 state 正文，观察项在其中列出；
   人类标题不出现 transition 函数名、before/after/it。

这些是之后应证明的预期结果，不是本轮已完成的自动化或人工验证记录。
