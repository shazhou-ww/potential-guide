# 预期行为：可执行状态树与人工手册

本文支持 [构想契约](./Idea.md)，描述我们希望使用者观察到的行为，
不是已实现功能的说明，也不提前锁定包装器签名、YAML schema 或包布局。
具体形态见 [用例与输出示例](./Examples.md)。

## 1. 一棵树，两种运行方式

| 场景 | 自动测试模式 | 文档模式 |
| --- | --- | --- |
| 读取 YAML 说明 | 关联标题和说明，验证引用有效 | 使用相同的标题、说明和稳定键 |
| describe 声明回调 | 按 Node Test 语义声明 suite | 遍历声明以收集子节点，不注册实际测试 |
| beforeEach / afterEach | 注册真实 hook，按原生语义执行 | 只记录函数引用、文档和所属层级 |
| it | 注册并执行探针 | 只记录检查点，不调用探针 |
| 测试环境及 Host | 由 hook 创建并清理 | 不创建 fixture，不启动 CLI、Host 或辅助进程 |
| 产物 | 自动测试结果 | 终端树、Markdown 或静态 HTML |

文档模式允许读取定义与 YAML，并写入用户指定的文档产物；
“没有副作用”专指不触发被测业务及测试 fixture 的初始化和清理。
输出文档本身不代表运行或验证过测试。

包装器不是任意 JavaScript 的沙箱。测试定义模块必须遵守声明期无业务副作用：
导入实现模块、加载依赖、执行 describe 回调时都不能偷偷创建目录、连接 Host
或执行命令。支持文档模式之前，必须排除这些导入及声明期行为。

## 2. 节点、边和探针各自表达什么

- describe 描述一个已到达的运行状态；正常状态和预期故障状态都可以成为节点。
- 子层 beforeEach 表达从父状态进入子状态的操作，并进行必要的状态准入确认。
- it 表达在当前状态上的只读探针，不承担建立后续状态的任务。
- afterEach 表达资源收尾，不要求把状态逆向回滚成父状态。
- 一次测试从外到内重建前置路径，执行当前探针，再按 Node Test 语义收尾。
  兄弟探针使用独立 fixture，不共享上一个探针执行后留下的可变状态。

例如“Running → 请求取消 → Cancelling → 清理完成 → Cancelled”中，
Cancelling 必须有稳定可观察的窗口。自动化使用握手或屏障；
人工说明也必须解释怎样保持和释放该状态，不能用固定 sleep 代替确认。

## 3. 失败及清理

| 情况 | 预期行为 |
| --- | --- |
| 父层 beforeEach 失败 | 本次测试不执行依赖该前置条件的子层 setup 和探针；其他测试仍按原生语义重新建立路径 |
| 父层某个 it 失败 | 不自动阻断兄弟或后代测试；it 不是依赖调度节点 |
| 成功进入预期故障状态 | 继续执行故障状态探针和恢复转移；故障状态不等于测试失败 |
| setup 只完成一部分 | 已获得的资源仍有明确清理责任，不假设完整 fixture 一定存在 |
| 清理失败 | 明确保留失败诊断，不把测试或人工复验标为成功 |
| 平台不适用或显式跳过 | 自动模式保留原生 skip；文档保留可见节点并标注条件，不静默删掉分支 |

不增加“失败一次，后代全部 Blocked”的执行器。
文档说明也不应虚构这种与 Node Test 不同的依赖关系。

清理操作按资源所有权组织，不要求每层都放 afterEach。
父子层都注册清理时，展示内到外的层级关系；同一层内多个 hook 的顺序
遵循 Node Test 的实际语义，不自行把注册列表反转。
失败时哪些清理仍可执行，也必须与实际实现一致。

## 4. YAML 与结构如何关联

- BDD 树文件是层次结构的唯一来源；YAML 仅提供标题、Markdown 说明及适用条件。
- YAML 使用简短稳定键，加载时保留文档命名空间，避免靠展示标题关联。
- 改标题不应破坏节点链接；重复标题可以存在，但同一路径中的节点身份不能歧义。
- 一段操作说明可以在不同路径复用。说明条目的身份与树中每次出现的节点身份
  需要区分，避免复用说明后生成重复 HTML 锚点。
- 缺失条目、重复 YAML 键、无效字段或无法唯一定位的节点应明确诊断，
  指明文件与条目，不用默认空说明伪装成完整手册。
- YAML 字符串是文档，不求值、不执行命令、不自动读取它链接的额外文件。

树文件仍显式绑定真实函数；YAML 不指定要动态调用的函数，也不再描述另一份树。
树结构和 YAML 不一致时应在生成或验证时暴露，而不是靠人观察页面猜测。

## 5. 人工说明需要包含哪些内容

每条转移或探针按需给出：

- 操作目的及前置状态。
- 需要填写的变量、fixture 来源、平台与权限要求。
- 实际命令或 UI 操作，执行位置和明确的参数。
- 去哪里看结果，以及可判定的预期现象。
- 如何确认操作已经完成；等待应有边界。
- 失败时怎样收尾，哪些资源由本场景拥有。

实现阶段交付的手册不能只说“调用某个 helper”或“确认状态正确”。
如果需要演示 fixture 或驱动命令，手册必须提供其准备及调用方式。
设计示例中的占位符不是现有可运行命令，不能作为人工复验已完成的证据。

不得默认连接用户日常使用的 Host、终止未记录的进程，或复制包含 bearer token
的描述文件到报告。危险操作应明确目标、所有权和后果，不在打开页面时自动执行。

## 6. 两种阅读视图

### 总览树

展示全部状态、转移和探针，以及跳过条件或平台限制。
终端和 Markdown 保留清晰缩进；HTML 可以折叠、查找并通过稳定链接定位节点。
节点标题用于快速浏览，长说明在展开或选中后阅读。

### 单路径操作手册

选择一个 it 时，组合：

1. 从外到内的 beforeEach 操作和其中的准入确认。
2. 当前 it 的检查说明。
3. 从内到外的 afterEach 收尾说明。

父层其他 it 不自动插入为必经检查，否则人工步骤会与自动执行语义不同。
如果某个父状态必须先验证，应该明确写在其 hook 的准入说明中。
同一场景的手动复验也应从独立环境开始，不假设之前选中的路径已经执行。

## 7. HTML 及结果展示的边界

- 页面是可离线打开的静态文档，不依赖启动开发服务器或连接实际 Host。
- 命令块保留格式并方便复制；复制不等于执行。
- 文档中的 HTML、脚本或链接不能取得执行测试代码的能力；不将任意原始 HTML
  直接作为可信页面内容注入。
- 平台不适用、说明不完整、自动测试未运行和测试失败是不同状态，不混为一种颜色或结论。
- 第一版不要求实现运行结果仪表盘；以后叠加结果时也要标明时间、候选版本和平台，
  不把文档树的存在当成自动测试通过。

## 8. 讨论中的验收例

1. 收集一个含嵌套 hook 和探针计数器的最小树，所有计数保持零且 fixture 未创建。
2. 正常执行同一棵树，确认 hook 顺序与失败语义仍符合 Node Test。
3. 缺失 YAML 条目时生成失败，报出具体引用，而不是少生成一个分支。
4. 选择“取消后资源已释放”，得到完整有序步骤和清理说明，而不是一段孤立断言。
5. 注入 worker 退出后，手册继续展示故障确认和恢复路径，不要求把预期失败改成成功。
6. 重命名展示标题后，原有节点身份及文档关联仍稳定；同一说明复用时各路径仍能单独定位。

这些是预期行为的具体例子，不代表已经执行过验证或已增加实现阶段任务。
