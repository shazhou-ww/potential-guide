# 开发机健康五层标准

本文件支持 [Idea.md](./Idea.md)。五层表示累计的健康保证，不是安装流水线；最终健康必须具有全部必要检查的有效证据，低层条件失效时应退回相应状态。

## L1 可管理

确认 Agent 能在[既定授权范围](./scope-and-authority.md)内自主维护目标：

- 环境身份、运行环境类别和实际账号与目标一致；日常执行账号专用且非 root。
- HOME、工作区和临时目录存在，归属和访问权限符合用途，不依赖操作者的个人 HOME。
- 非交互 sudo 能力满足约定的系统维护范围。
- 以 Agent 实际非交互运行环境检查权限和 PATH，不能用控制机或管理员会话的成功代替。

## L2 系统可用

确认基础环境不会直接阻断开发：

- 必要目录可读写，文件系统没有意外只读；可用磁盘空间及 inode 满足目标预算。
- 包管理器数据库和事务状态正常；正常进行中的安装或包管理锁不直接等于损坏。
- DNS、明确要求的网络端点和时间状态满足开发需要。网络受限、离线策略和检测超时需区分，不能以任意公网网站不可达判定整机损坏。
- 必要服务可用。“必要”由实际开发需求决定，不要求所有环境都有 systemd 或相同服务。

磁盘、inode、网络超时等预算应明确单位、适用范围和可重复验证的边界值。当前构想不指定未经验证的统一数字；实施时需固定默认策略并测试阈值两侧及临界值。

## L3 开发就绪

Git 是公共基线。首批支持以下四种栈；目标明确选择必需栈，全栈设备要求四种都通过，未选择的栈不得被宣称已验证。

| 技术栈 | 必要能力 | 最小证明 |
| --- | --- | --- |
| TypeScript | Node.js、选定包管理器、可用的 TypeScript 编译器及明确版本约束 | 编译并运行最小 TypeScript 程序，核对输出 |
| Python | Python 3、隔离环境能力及选定依赖管理工具 | 创建隔离环境，以该环境的解释器运行并核对输出 |
| C++ | 编译器、头文件、标准库、链接器，及约定的 CMake／构建后端 | 配置、编译、链接并运行最小程序，核对输出 |
| Rust | rustup、rustc、Cargo，及目标所需链接器／系统库 | 离线构建并运行无外部依赖的最小 crate，核对输出 |

不要求同时安装所有同类工具，例如 pip、uv、Poetry 或 GCC、Clang；不要求 TypeScript 必须全局安装。检查不能通过临时自动下载、安装工具来掩盖缺失。

所有验证均由指定账号在实际执行环境中完成，使用独占临时目录，限制执行时间及输出，处理失败清理。仅有版本输出不代表构建链路可用；成功退出但输出不符也不算通过。

## L4 工作有序

- HOME 内项目、配置、缓存、临时数据和运行状态各有明确归属及目录规则；整洁不等于文件少，也不要求无意义地迁移工具标准目录。
- 工作成果可定位；未提交修改是需要保护的状态，不是健康失败或必须提交的理由。
- 检查已知任务的超期临时目录、构建残留和失控后台任务；依据所有权、任务活动状态及保留期限判断。
- 活动开发服务器、正常编译和仍被引用的缓存不得因存在时间长而直接判定为垃圾。
- 对未知文件或无法确认归属的进程，不自动删除或终止；需要明确诊断或补充归属信息。

## L5 持续健康

- 观测磁盘、inode、缓存和日志的增长及剩余容量风险，而非仅看当前快照。
- 识别持续异常的资源占用、重复失败的必要服务或维护任务；正常繁忙不是不健康。
- 关注适用的软件安全更新、系统重启需求和维护失败，并在不破坏活动工作的条件下处理。
- 维护后复查受影响的基础条件和开发能力，防止“清理成功但工具链损坏”。

趋势结论必须声明采样窗口、最少样本数、证据新鲜度及判定策略。无历史或样本不足时明确报告证据不足，不得宣称长期健康已经验证。容器内优先使用容器资源限制和可见指标，不能将宿主总内存当作容器额度。

## 环境差异

- 原生 Linux：检查约定范围内的系统服务、更新及重启需求。
- WSL：检查 Linux 发行版能力；时钟、资源和内核可能来自宿主，不要求 Linux 自行维护 Windows 或证明宿主健康。
- 容器：检查容器内部包管理和必要进程，不要求系统级 init、宿主时钟管理、内核升级或宿主重启；镜像重建／容器替换需求不能被误写为检查已自主完成。

## 观测与复查规则

每个检查应能说明观测对象、实际证据、问题原因和恢复条件。至少区分：

- 健康条件满足。
- 检查正常完成，但发现待修复问题。
- 无法完成检查，如权限不足、超时、执行错误或不支持的平台。
- 按明确环境／需求规则不适用，并记录理由；不能借此隐藏失败。

这些是语义要求，不预设 Pilot 协议新增状态。当前协议如何承载诊断与不适用信息由实施契约确定，调用故障不得伪装成健康通过。

身份、容量和读写等轻量检查可频繁运行；完整构建在首次接管、相关变更后和定期复查时执行；趋势检查依赖多次观测。复用结果必须有明确的有效期和失效条件，不能因历史上通过而永久保留健康等级。
