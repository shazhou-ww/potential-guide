# 管理范围与授权

本文件支持 [Idea.md](./Idea.md)，定义目标对象、授权和维护责任，不定义具体实现。

## 目标对象

目标不是“安装好工具”，而是持续保持一个指定环境内、由 Agent 管理的开发账号及相关系统处于健康可用状态。首次整备和日常维护共用同一套健康标准。

每个目标必须明确环境身份、专用账号、HOME、工作区、临时目录以及系统管理范围。检查需要确认实际执行身份，不能只相信配置的用户名；账号独立性还需要接管时声明其专用用途，不能只凭用户名推断。

| 环境 | 纳入范围 | 不自动纳入范围 |
| --- | --- | --- |
| 原生 Linux | 约定的 Linux 设备、专用账号及系统维护 | 其他设备、外部服务和其他人的数据 |
| WSL | 指定发行版内的 Linux 用户、工具链和文件系统 | Windows 宿主配置、宿主重启、挂载的 Windows 用户数据 |
| Linux 容器 | 指定容器内的用户、工具链、文件系统和容器可见资源 | 宿主内核、Docker 服务、其他容器和宿主文件 |

首版不支持原生 Windows 和 macOS。WSL 内运行 Docker 时，目标若为容器，仍按容器范围判定，不因其宿主是 WSL 而扩大权限。
环境类别应明确并与实际观测核对；无法识别或平台不支持必须显式报告，不能默认按原生 Linux 通过。Linux 发行版能力也不能假定完全相同。

## 持续管理授权

指定账号全权交由 Agent 管理。在接管时约定的目标范围内，安装软件、调整配置、整理目录、清理可回收资源和修复系统无需逐项追加用户授权。该契约不是对本次文档编写环境的实际操作授权。

Agent 以专用非 root 用户开展日常开发，具备满足维护范围的非交互 sudo 能力。仅属于某个用户组、存在 sudo 命令，或能以交互密码提权，都不足以证明无人值守维护能力。容器默认 root 也不代替专用账号要求。

检查应有界、非交互地验证授权，不修改 sudo 配置，不索取或读取密码，不以安装软件来试探权限。不能确认权限时报告无法验证；能执行一个受限 sudo 命令不等于具备全部维护权限。

## 维护责任与数据保护

- Agent 对用户目录秩序、开发工具可用性及管理范围内的系统健康负责，不只对某一次开发任务负责。
- 授权不等于要求立即执行所有可用操作。维护需考虑活动构建、开发服务、数据持久性和中断风险，不能为更新而随意中断工作。
- 不覆盖未提交改动，不自动提交或丢弃用户工作，不将未知文件视为垃圾。清理应依据已知归属、生命周期和活动状态。
- 对可能破坏数据的修复，先采用可恢复、可核验的方式；无法确认安全清理的对象应保留并报告阻塞，不把请求人工批准当作常规维护流程。
- 保存必要的操作、结果和失败诊断，不记录秘密。修复后必须重新观测，不以执行命令成功代替健康恢复。

## Pilot 与 Agent 的职责边界

Pilot 的 check 负责观测、诊断和有界的隔离能力验证，不安装软件、修改持久配置、清理现有用户内容或修复系统。最小构建允许在独占临时目录内创建测试产物，并负责清理。

Agent 根据观测和指导执行修复；首次达到健康不结束该目标，后续观测仍可能降级。周期调度、历史保存和修复执行是配套运行能力，不应假称单次 check 已完成长期维护。

现有 pguide setup Objective 检查 pguide 安装、配置和 ACP 就绪，不证明通用开发机健康。本目标与它保持职责区分；不要求通用开发机健康检查本身必须调用模型或产生费用。具体组合关系留待实施阶段确定。
