## 需求方向

同一治理对象的后到请求可能利用已经开始的工作，不必要求 execution 在自己 eligible 后才开始。
用户认为 `completed` 名称未覆盖取消、超时与失败，应以独立 idea 讨论一般终结语义。
这不意味着上述不同层次的终结已决定合并，也不意味着改一个枚举名即可满足需求。

## 已明确的语义

用户于 2026-10-30 确认的以下语义继续有效；最新破坏升级授权不替代精确 revision 的门禁：

- `terminated` 指 Execution 的逻辑终结，成功完成与失败都属于执行结果。
  失败结果不等于成功成果。
- 取消表示意图上不再需要这个 Task 的结果，不再参与结果匹配。
  超时与成功或失败是独立维度：超过期限后不再保证一定给出结果，但并不禁止后来给出结果。
  Task 可以超时成功或超时失败，不能仅因超时排除迟到结果。
  取消时间和超时界线都不是 Execution 的终结时间。
- 单个 Task 不再需要结果，不代表其他 owner 也不需要共享执行；
  Execution 的逻辑终结与物理退出、回收保持分离。
- 新 Task 的实际生效时间不能早于接收时间：
  `effectiveEligibleAt = max(requestedEligibleAt ?? receivedAt, receivedAt)`。
  提供过去时间时按接收时间生效，提供未来时间时保留未来时间。
- 结果匹配与超时期限统一使用这个生效锚点：
  `deadlineAt = effectiveEligibleAt + timeoutMs`。
  例如 10:30 收到请求、请求填写 10:15、期限为十分钟，则从 10:30 生效、10:40 为期限界线；
  这个界线用于时效判断，不是结果匹配窗口的硬上界。
  该限制同时排除接收前的成功或失败结果，不仅针对失败。
- 兼容判定基于 Task 类型和 Input：同一类型、相同 Input 的 Task 在同一组内按规则匹配，
  不依赖准备是否完成或 Prepared 的结果。这不授权越过身份和权限边界。
- 从引擎视角，绑定发生在 Execution start 或 terminate 时：
  start 时匹配可绑定的 `started-after-eligible` Task；
  terminate 时匹配可绑定的 `terminated-after-eligible` Task，成功和失败都参与该规则。
  前者在绑定之后接收执行失败；后者的失败终结与绑定属于同一逻辑处理。
- 生效时间下界包含等号：对应的 start 或 terminate 事件时间满足
  `eventTime >= effectiveEligibleAt` 即通过下界判定，不再使用当前实现的严格 `>`。
  Task 仍须在该事件发生时已接收并满足匹配条件，不能把未超时作为普遍的结果接纳前提；
  后接收的 Task 不能仅凭相同时间戳倒查绑定，时间戳相等不替代事件先后关系。
- 此前“Task 已生效，但尚未准备好，因而等到执行失败后才可判定兼容”的例子撤回：
  它错误地把当前 Prepared 兼容限制作为目标语义前提。
  按上述规则，该 Task 不需要等准备完成，可在 Execution terminate 时参与匹配，
  无需为这个例子另设历史失败补绑定政策。
- 此前“取消或超时都不再匹配结果”的记录和
  `effectiveEligibleAt <= terminatedAt <= deadlineAt` 的建议已按用户澄清纠正：
  deadline 不限制结果适用性。若期限为 10:10，10:11 成功为成功且超时，
  10:11 失败为失败且超时；不能把这两种情况都归成无结果。

## 已收敛的准备决定

- 保留严格超过 deadline 才标记超时的现行边界；恰好相等不超时。
  迟到观察与重放使用可靠事件时间，而不是结算、查询或重启时间重新计算已经发生的结果。
- 超时撤去新的准备、排队启动及防压力替换保障，但不自动取消已经运行的工作，
  不撤销结果资格；仍可获得符合事件规则的迟到成功或失败。
  保留独立执行时限及物理回收边界，不承诺无限运行。
- 共享需求与结果绑定分开：终结策略在绑定前仍可保护兼容执行，
  不用伪造 `running` 或提前绑定来表示需求。单个请求超时或取消不能撤掉其他有效需求的保护。
- 仅接受 `started-after-eligible` 与 `terminated-after-eligible`，
  拒绝旧 `completed-after-eligible`；默认仍为 started 策略，没有别名或双语义期。
  新契约使用新存储，旧格式明确报错并提示另用新存储，旧数据不改写、不自动删除。
- 原始请求保留用户时间及省略字段；首次接收确定生效时间与 deadline，
  幂等重试和新格式重启都不重新锚定。同毫秒内仍以持久事件先后决定是否已接收，
  不能在完成后把新 Task 倒查绑定到历史执行。
- Regulate 众筹、预算、execution join、资源接续不是本项交付；
  只适配现有内部消费者，不修改其他 Idea 或把其未来能力写成已存在的依赖。
